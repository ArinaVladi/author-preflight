# TypeScript: основы типизации и компиляции

JavaScript многое позволяет сделать без предварительной проверки данных.

Например, когда мы передаём в функцию строку вместо числа, обращаемся к свойству, которого нет, и программа всё равно запустится. Редактор может что-то подсказать, линтер — заметить подозрительную конструкцию, но некоторые проблемы обнаружатся только во время выполнения.

Например:

```text
TypeError: Cannot read properties of null
```

В небольшом проекте с этим сравнительно легко справляться. Пока кода немного, разработчик примерно помнит, что находится в каждой переменной, какие поля есть у объектов и что возвращают функции.
С ростом проекта это становится сложнее. Данные переходят из одного модуля в другой, функций становится больше, а после перерыва уже не всегда очевидно, может ли конкретное значение оказаться `null`. Переименование одного свойства заставляет искать все места, где использовалось старое имя. Чтобы понять, что принимает функция, приходится читать её реализацию или искать примеры вызова.

Рассмотрим функцию:

```javascript
function renderUser(user) {
  cardTitle.textContent = user.name;
  cardText.textContent = user.email;
}
```

Из логики программы понятно, что `user` должен быть объектом. У него должны быть свойства `name` и `email`. Более того, код рассчитывает, что значения этих свойств подходят для вывода на страницу.

Но где записаны эти требования? Пока — нигде.

Для описания данных и используется **TypeScript**. Он решает одну из главных проблем JavaScript: ошибки обнаруживаются слишком поздно, уже в браузере. TypeScript переносит большую часть ошибок на этап написания кода, помогая ловить их ещё в редакторе.

Прежде чем переходить к TypeScript, попробуй спрогнозировать поведение четырёх небольших примеров. Ответы пока можно не проверять: к каждому вопросу мы вернёмся по ходу темы.

1. Тип есть, а данные неправильные.

Есть функция:

```typescript
function add(a: number, b: number) {
  return a + b;
}
```

Проект успешно прошёл проверку и работает в браузере. Но во время выполнения каким-то образом в `add` вместо числа попала строка.

Что произойдёт: TypeScript остановит программу с ошибкой типа или сработают обычные правила JavaScript?
Этот вопрос мы разберем уже во втором разделе.

2. Можно ли поверить серверу?

Опишем пользователя:

```typescript
interface User {
  id: number;
  name: string;
}
```

Затем получим данные:

```typescript
const user: User = await response.json();
```

Но сервер неожиданно вернул:

```javascript
{
  message: "Something went wrong"
}
```

Поймает ли TypeScript такое несовпадение?

Если нет, кто должен проверить, что с сервера действительно пришёл `User`? Этот вопрос мы обсудим также во втором разделе.

3. Почему компилятор мешает работать с DOM?

Рассмотрим привычный код:

```typescript
const button = document.querySelector(".btn");

button.addEventListener("click", () => {
  console.log("click");
});
```

TypeScript может не разрешить вызвать `addEventListener`.

Почему?

Это излишняя осторожность компилятора или в программе действительно существует ситуация, в которой такой код небезопасен?

4. Важнее имя типа или его устройство?

Есть два интерфейса:

```typescript
interface Point {
  x: number;
  y: number;
}

interface Coords {
  x: number;
  y: number;
}
```

И функция:

```typescript
function printCoords(coords: Coords) {
  console.log(coords.x, coords.y);
}
```

Можно ли передать в неё значение типа `Point`?

```typescript
const point: Point = {
  x: 10,
  y: 20
};

printCoords(point);
```

На все вопросы мы будем давать ответы по ходу лонгрида.

## 1. Зачем нужен TypeScript

На прошлой неделе в проекте появились инструменты, которые помогают проверять код до запуска.

Например, линтер может заметить неиспользуемую переменную:

```javascript
const userName = "Alex";
```

Или обратить внимание на нежелательное сравнение:

```javascript
if (value == 10) {
  // ...
}
```

Это полезная проверка, но у неё есть граница. Линтер анализирует правила написания и отдельные потенциально проблемные конструкции, однако он не знает всех договорённостей о данных в программе.

Рассмотрим функцию:

```javascript
function calculateTotal(price, quantity) {
  return price * quantity;
}
```

Где-то в программе появляется вызов:

```javascript
calculateTotal("много", 3);
```

С точки зрения синтаксиса это допустимый JavaScript. Но из смысла программы известно больше: `price` и `quantity` должны быть числами.

Линтер сам по себе этого требования не знает.

В TypeScript его можно записать:

```typescript
function calculateTotal(
  price: number, // типизируем примитивом число
  quantity: number // типизируем примитивом число
): number { // результат также должен быть числом
  return price * quantity;
}
```

Теперь вызов

```typescript
calculateTotal("много", 3);
```

приводит к ошибке ещё до выполнения программы.

Почему?

Компилятор располагает двумя фактами:

```typescript
price: number
```

означает, что первый аргумент должен быть числом;

а

```typescript
"много"
```

имеет строковый тип.

Две части программы противоречат друг другу, и TypeScript может это заметить.

Важно, что правило не появилось из воздуха. Компилятор не догадался, что цена обязательно должна быть числом. Это правило записали мы сами, а компилятор только сверяет с ним остальную программу.

### Когда знание о данных живёт только в голове

Представим приложение со списком задач:

```javascript
const task = {
  id: 17,
  title: "Повторить DOM",
  completed: false
};
```

Из устройства приложения понятно следующее:

- `id` — число;
- `title` — строка;
- `completed` — логическое значение.

Пока проект небольшой, эту структуру нетрудно помнить.

Затем появляется функция:

```javascript
function renderTask(task) {
  // ...
}
```

Потом ещё одна:

```javascript
function saveTask(task) {
  // ...
}
```

И ещё:

```javascript
function toggleTask(task) {
  // ...
}
```

Каждая функция рассчитывает на одну и ту же форму `task`, но в JavaScript эта договорённость нигде не зафиксирована.

Можно написать комментарий:

```javascript
// task содержит id, title и completed
function saveTask(task) {
  // ...
}
```

Для человека это полезная подсказка. Но комментарий не способен проверить следующий вызов:

```javascript
saveTask({
  id: 17,
  name: "Повторить DOM"
});
```

Тип — способен. Для описания структуры объекта будет использован **интерфейс**

```typescript
interface Task { // описываем поля объекта
  id: number;
  title: string;
  completed: boolean;
}

function saveTask(task: Task) {
  // ...
}
```

TypeScript не заменяет понимание данных. Наоборот, сначала нужно понять, каких данных ожидает программа, и только после этого это знание можно выразить через типы.

### TypeScript полезен не только тогда, когда код неправильный

Обсуждение TypeScript часто сводится к фразе «он помогает ловить ошибки». Это верно, но описывает только часть пользы.

Рассмотрим уже знакомый тип:

```typescript
interface Task {
  id: number;
  title: string;
  completed: boolean;
}
```

И функцию:

```typescript
function renderTask(task: Task) {
  task.
}
```

После точки редактор уже знает возможные свойства объекта:

```text
completed
id
title
```

Не нужно вспоминать, называлось ли поле `completed`, `complete` или `isCompleted`. Информация уже записана в программе.

При большом проекте это становится особенно заметно. Типы позволяют редактору подсказывать доступные свойства, параметры функций и возвращаемые значения.

Тот же механизм помогает при рефакторинге.

Допустим, структура задачи меняется:

```typescript
interface Task {
  id: number;
  title: string;
  isCompleted: boolean;
}
```

Все старые обращения:

```typescript
task.completed
```

теперь противоречат новой модели данных.

Компилятор может показать места, которые нужно изменить.

Без информации о типах такое переименование часто превращается в поиск по проекту с надеждой, что ни одно использование не осталось незамеченным. С типами несоответствие становится видимым.

Поэтому автодополнение и безопасный рефакторинг — не отдельные бонусы TypeScript, а прямое следствие того, что знание о данных записано в самом коде.

### Зачем тогда использовать в проекте линтер?

Линтер и TypeScript не конкурируют друг с другом. Они отвечают на разные вопросы.

Линтер может спросить:

> Не нарушено ли здесь правило написания кода?

TypeScript может спросить:

> Совместимы ли данные, которые сюда передаются, с данными, которые здесь ожидаются?

Например:

```typescript
function getUserName(user: User) {
  return user.nmae;
}
```

Опечатка в имени свойства важна не потому, что слово `nmae` само по себе запрещено. Проблема в другом: у значения типа `User` такого свойства нет.

Именно это знание появляется благодаря типам.

Поэтому TypeScript продолжает линию инструментов, уже появившихся в проекте. Сначала часть проблем находилась только после запуска. Затем линтер начал ловить некоторые ошибки раньше. Теперь добавляется ещё один уровень проверки — информация о данных и операциях над ними.

### TypeScript не заменяет JavaScript

При этом TypeScript не отменяет правила самого JavaScript.

По-прежнему важно понимать, что произойдёт здесь:

```javascript
"5" + 2
```

как работают объекты и массивы, области видимости, функции, DOM, события и асинхронный код.

TypeScript добавляет поверх JavaScript дополнительный этап проверки.

Но насколько далеко распространяется эта проверка? На этот вопрос мы ответим в следующем разделе. А пока перейдём к практике.

### Практика

Открой проект прошлой недели и выбери одну функцию, которая принимает объект или несколько аргументов.

Пока переписывать функцию не нужно.

Сначала ответь на несколько вопросов.

1. Каких данных ожидает функция?
2. Какие значения допустимы для каждого параметра?
3. Может ли какое-либо значение отсутствовать?
4. Что возвращает функция?
5. Что произойдёт сейчас, если передать данные неправильной формы?
6. Способен ли линтер обнаружить такую ошибку?

Затем найди ещё два места, где устройство данных понятно автору проекта, но никак не выражено в самом коде.

Именно эти места позже станут кандидатами на типизацию.

### Если кратко

TypeScript добавляет к JavaScript статическую проверку типов.

Типы позволяют записать знания о данных так, чтобы ими мог пользоваться не только человек, но и инструменты: компилятор, редактор, автодополнение и средства рефакторинга.

При этом TypeScript не угадывает смысл программы. Информацию о данных сначала должен понимать разработчик.

## 2. Компиляция, tsconfig и стирание типов

Теперь разберём механизм, без которого остальные возможности TypeScript легко понять неправильно.

Создадим небольшой файл:

```typescript
function greet(name: string): string {
  return `Привет, ${name}!`;
}

const userName: string = "Аня";

console.log(greet(userName));
```

В нём появилась информация, которой не было бы в обычном JavaScript. Эта информация нужна TypeScript Compiler — `tsc`. Сначала компилятор анализирует программу и проверяет, согласуются ли её части между собой.

Например,

```typescript
const userName: string = 42;
```

противоречит записанному типу: переменная объявлена как строковая, но получает число.

Однако браузер не умеет выполнять TypeScript как систему типов. В конечном счёте приложению нужен JavaScript.

После компиляции исходный пример будет выглядеть примерно так:

```javascript
function greet(name) {
  return `Привет, ${name}!`;
}

const userName = "Аня";

console.log(greet(userName));
```

Типовая информация была нужна во время проверки, но в готовый JavaScript не попала. Это называют **стиранием типов**.

И это не просто особенность устройства TypeScript. Из неё следует главное ограничение всей системы типов:

> **TypeScript проверяет программу до запуска. В рантайме типов TypeScript уже нет.**

### Что происходит во время проверки

Рассмотрим функцию:

```typescript
function add(a: number, b: number): number {
  return a + b;
}
```

Если вызвать её так:

```typescript
add("10", 5);
```

компилятор видит противоречие.

Функция объявляет:

```typescript
a: number
```

А фактически передаётся:

```typescript
"10"
```

то есть строка.

Ошибка появляется **до выполнения программы**. Такой этап называют **compile-time** — временем проверки и компиляции.

Теперь посмотрим, что остаётся после удаления типов:

```javascript
function add(a, b) {
  return a + b;
}
```

Это обычная JavaScript-функция.

И здесь можно вернуться к первому вопросу-прогнозу.

Предположим, что проверенный код уже оказался в браузере, но во время выполнения в функцию каким-то образом попала строка:

```javascript
add("10", 5);
```

Что произойдёт?

JavaScript выполнит операцию по своим обычным правилам:

```text
"105"
```

TypeScript не остановит выполнение программы и не выдаст новую ошибку типа. К этому моменту его типов уже не существует.

### Compile-time и runtime — две разные части жизни программы

Разницу удобно представить как последовательность:

```text
пишем TypeScript
        ↓
tsc анализирует программу
        ↓
проверяются типы
        ↓
типовая информация стирается
        ↓
получается JavaScript
        ↓
JavaScript выполняется в браузере
```

В верхней части схемы работает TypeScript.

Нижняя часть — это **runtime**, то есть непосредственное выполнение программы.

Например,

```typescript
const age: number = "двадцать";
```

можно обнаружить на этапе проверки.

Это проблема compile-time.

А вот

```javascript
JSON.parse("{сломанный json}");
```

может завершиться ошибкой уже при выполнении программы.

Это проблема runtime.

TypeScript помогает заранее рассуждать о коде, но не превращается в систему, которая проверяет тип каждого значения в браузере.

### Откуда тогда берутся данные, которые компилятор не проверил?

Возникает закономерный вопрос. Если весь исходный код прошёл проверку, почему неправильное значение вообще может оказаться внутри программы?

Потому что программа взаимодействует с внешним миром.

Например, получает ввод пользователя:

```typescript
const value = input.value;
```

Читает данные из `localStorage`:

```typescript
const saved = localStorage.getItem("user");
```

Ищет элементы в DOM:

```typescript
const element = document.querySelector(".button");
```

Разбирает JSON:

```typescript
const data = JSON.parse(text);
```

Или получает ответ сервера:

```typescript
const response = await fetch("/api/user");
const data = await response.json();
```

Компилятор способен анализировать исходный код, но не может заранее знать, что сервер отправит завтра, что пользователь введёт в форму или что окажется в `localStorage`. Отсюда появляется граница, к которой будем возвращаться ещё несколько раз:

> **TypeScript проверяет утверждения программы о данных, но не проверяет сам внешний мир.**

Вернёмся ко второму вопросу из начала темы.

Есть описание пользователя:

```typescript
interface User {
  id: number;
  name: string;
}
```

После запроса появляется код:

```typescript
const user: User = await response.json();
```

На первый взгляд, всё надёжно: переменная имеет тип `User`, поэтому хочется считать, что ответ сервера тоже проверен.

Но запись

```typescript
: User
```

сама по себе не способна проверить объект, пришедший по сети.

Если сервер вернул:

```json
{
  "message": "User not found"
}
```

тип `User` не добавит в этот объект `id` и `name`.

Он также не создаст в JavaScript скрытую проверку:

```javascript
if (typeof data.id !== "number") {
  // ...
}
```

Такой код должен существовать в программе явно, если проверка действительно нужна во время выполнения.

Поэтому здесь важно различать два действия:

```text
типизация
→ описывает и статически проверяет ожидания программы

валидация
→ проверяет реальные данные во время выполнения
```

TypeScript занимается первым, а за второе отвечает выполняющийся код.

### Знакомая модель из Python — но не совсем та же

Тем, кто уже встречал аннотации типов в Python, часть механизма может показаться знакомой.

Например:

```python
def add(a: int, b: int) -> int:
    return a + b
```

Отдельный инструмент, например `mypy`, может проверить, соответствует ли программа этим аннотациям.
В обоих случаях статическая проверка выполняется отдельным инструментом и сама по себе не означает автоматической runtime-валидации каждого значения. Но сходства инструментов заканчивается быстро. В Python аннотации остаются в программе во время выполнения как метаданные: их можно прочитать, например, через `__annotations__`. В TypeScript при получении JavaScript типы **физически стираются**, и во время выполнения от них не остаётся ничего.

Поэтому

```typescript
const user: User
```

не является инструкцией браузеру «проверяй, чтобы здесь всегда был `User`».

Браузер этого `User` вообще не увидит.

### Подключаем TypeScript к проекту «Полки»

Прежде чем разбирать настройки, подключим TypeScript к проекту недели 10. Все практики из этой темы и домашка выполняются в нём.

Сначала установим компилятор как зависимость для разработки:

```bash
npm install -D typescript@5.9.3
```

Версия указана явно не случайно. С августа 2026 года команда без версии ставит TypeScript 7 — новый компилятор, переписанный на Go. Он быстрее, но пока не даёт программного интерфейса, через который с TypeScript работают другие инструменты, и ESLint с ним не работает. В домашке ESLint будет проверять TS-файлы, поэтому весь курс живёт на 5.9.3.

Не запускай `npx tsc`, пока пакет не установлен: `npx` не найдёт компилятор в проекте и предложит скачать посторонний пакет с именем `tsc`, который к TypeScript отношения не имеет.

Дальше по шагам.

1. Создай в корне проекта, рядом с `package.json`, файл `tsconfig.json` с базовым конфигом — он приведён и разобран в следующем подразделе.
2. Переименуй файлы приложения в `src` из `.js` в `.ts`: `main.js` → `main.ts`, `data.js` → `data.ts`. Конфиги инструментов (`vite.config.js`, `eslint.config.js`) можно оставить на JavaScript.
3. В `index.html` поправь точку входа: `<script type="module" src="/src/main.ts"></script>`.
4. Добавь в `package.json` скрипт `"typecheck": "tsc --noEmit"` — зачем он нужен отдельно от сборки, разберём ниже в этом разделе.

Vite умеет работать с `.ts`-файлами без дополнительных плагинов, поэтому `npm run dev` продолжит работать сразу после переименования. А вот `npm run typecheck` почти наверняка покажет ошибки. Это нормально: разделы 3–8 как раз о том, как их читать и исправлять.

### Как компилятор узнаёт правила проекта: используем `tsconfig.json`

Для одного маленького файла настроек почти не требуется. В настоящем проекте компилятору нужно сообщить, как именно работать с кодом.

Для этого используется файл `tsconfig.json`.

На этой неделе нет задачи изучить все его возможности. Достаточно нескольких настроек из программы и понимания того, **зачем каждая из них существует**.

Так выглядит базовый `tsconfig.json` «Полки» — тот же, что выдан в домашке:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "strict": true,
    "noEmit": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "types": ["vite/client"]
  },
  "include": ["src"]
}
```

Сначала рассмотрим настройки из программы недели — `target`, `module`, `outDir`, `lib` и `strict` в связке с вопросами, на которые каждая отвечает. Остальные строки нужны, чтобы TypeScript работал в паре с Vite, о них сразу после.

### `target`: какой JavaScript должен получиться?

```json
"target": "ES2022"
```

TypeScript-код в конечном счёте превращается в JavaScript.

`target` задаёт целевую версию JavaScript, на которую ориентируется компилятор.

То есть эта настройка отвечает на вопрос:

> **На возможности какой версии JavaScript может рассчитывать итоговый код?**

Важно не путать `target` с «версией TypeScript» или строгостью проверки типов. Это настройка результата компиляции.

### `module`: как работать с модулями?

В проекте уже могут использоваться:

```typescript
export
```

и:

```typescript
import
```

Настройка:

```json
"module": "ESNext"
```

определяет, как компилятор должен работать с модульной системой.

На этом этапе достаточно понимать назначение параметра. Полный каталог модульных режимов здесь не нужен.

### `outDir`: куда помещать результат?

```json
"outDir": ".type-erasure"
```

Если `tsc` создаёт JavaScript-файлы, `outDir` задаёт каталог для результата.

Например,

```text
src/
  main.ts
  utils.ts
```

может превратиться в

```text
.type-erasure/
  main.js
  utils.js
```

Таким образом, настройка отвечает на простой вопрос:

> **Куда складывать скомпилированный код?**

В базовом конфиге «Полки» `outDir` нет, и это не забыто. JavaScript для браузера в нашем проекте собирает Vite и складывает его в `dist`. Если бы `tsc` тоже писал туда свои файлы, они перемешались бы со сборкой. Поэтому в рабочем конфиге стоит `"noEmit": true`: `tsc` только проверяет типы и ничего не создаёт. `outDir` понадобится, когда мы специально захотим посмотреть, что `tsc` делает с кодом, — в практике этого раздела и в домашке результат складывается в отдельную папку `.type-erasure`.

### `lib`: какие возможности среды известны компилятору?

В браузере доступны сущности, которых нет в самом ядре языка JavaScript:

```typescript
document
window
HTMLElement
```

TypeScript должен знать, какие API доступны в среде выполнения и какие у них типы.

Например,

```json
"lib": ["ES2022", "DOM"]
```

позволяет учитывать стандартные возможности ECMAScript и браузерный DOM.

Позже значение этой настройки станет особенно понятным при типизации элементов страницы.

### Остальные строки базового конфига

Эти настройки не входят в список из программы, но без них TypeScript и Vite будут работать несогласованно. Разбирать их глубоко не нужно, достаточно понимать, зачем нужна каждая.

- `"moduleResolution": "Bundler"` — искать импортированные модули так же, как их ищет сборщик. Благодаря этому `import { formatPrice } from "./catalog-utils"` работает без расширения файла.
- `"noEmit": true` — только проверять, не создавать JavaScript. Файлы для браузера делает Vite.
- `"isolatedModules": true` — запрещать конструкции, которые нельзя правильно скомпилировать, глядя на один файл. Vite компилирует каждый файл отдельно и о соседних ничего не знает.
- `"types": ["vite/client"]` — подключить типы, которые добавляет Vite, например для `import "./style.css"`.
- `"include": ["src"]` — проверять всё, что лежит в `src`.

Отдельно про `"verbatimModuleSyntax": true`. Эта настройка требует явно помечать импорты, которые нужны только для типов:

```typescript
import type { Product } from "./types";
import { formatPrice } from "./catalog-utils";
```

Интерфейс `Product` после компиляции исчезнет, импортировать в JavaScript будет нечего, и `import type` сообщает об этом и компилятору, и Vite. Если написать обычный импорт, `tsc` остановится с ошибкой:

```text
error TS1484: 'Product' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
```

На эту ошибку почти все натыкаются в первый же час работы с типами, поэтому лучше знать о ней заранее.

### `strict`: не придирка, а отказ от опасных догадок

Особенно важна настройка:

```json
"strict": true
```

Название может создать впечатление, что это особый режим повышенной строгости — что-то необязательное для тех, кто хочет добиться «идеального» кода.

В рамках этой темы будем относиться к нему иначе:

> **`strict` — нормальный режим работы с TypeScript.**

Его смысл не в том, чтобы добавить как можно больше ошибок. Он заставляет компилятор не делать слишком оптимистичных предположений там, где информации недостаточно.

Например:

```typescript
const button = document.querySelector(".button");
```

Элемент может существовать на странице, а может отсутствовать.

Значит, безопасная модель должна учитывать оба варианта.

Или функция получает параметр:

```typescript
function greet(name) {
  return `Hello, ${name}`;
}
```

Если о `name` ничего не известно, строгая проверка заставит прояснить это место вместо того, чтобы молча отказаться от полезной проверки.

Технически `strict` — это не одна проверка, а группа флагов, которые включаются вместе. Три из них ты встретишь уже на этой неделе:

- `strictNullChecks` — `null` и `undefined` становятся отдельными вариантами типа. Отсюда `Element | null` у `querySelector`;
- `noImplicitAny` — параметр без типа, о котором компилятор ничего не может вывести, становится ошибкой, а не молчаливым `any`. Отсюда ошибка на `function greet(name)` выше;
- `useUnknownInCatchVariables` — переменная в `catch` получает тип `unknown`, а не `any`. Об этом в разделе 7.

Полный список — в описании флага `strict` в [справочнике по `tsconfig`](https://www.typescriptlang.org/tsconfig/#strict).

Поэтому `strict` стоит включать с самого начала работы над проектом.

Если сначала написать значительную часть кода без строгих проверок, а затем включить их, легко получить десятки ошибок одновременно. При включённом `strict` новые вопросы возникают постепенно и каждый можно разобрать отдельно.

Почти всегда полезно начинать разбор с одного вопроса:

> **Чего именно компилятор здесь не знает?**

### Проблема сборки в Vite

В проекте с Vite есть важная особенность. Специально создадим ошибку:

```typescript
const age: number = "двадцать";
```

С точки зрения TypeScript здесь явное противоречие. Но после запуска сборки можно обнаружить, что Vite всё равно способен собрать проект.

На первый взгляд, это странно: если TypeScript проверяет программу до запуска, почему сборка не остановилась?

Причина в разделении обязанностей между инструментами.

Vite занимается сборкой приложения и умеет обрабатывать TypeScript-файлы, но его сборка сама по себе не является полноценной проверкой типов через `tsc`.

Поэтому в проекте нужна отдельная команда:

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit"
  }
}
```

Теперь

```bash
npm run typecheck
```

запускает TypeScript Compiler именно для проверки программы.

Флаг:

```text
--noEmit
```

означает:

> **проверить код, но не создавать выходные JavaScript-файлы.**

Получается полезное разделение:

```text
Vite
→ собирает приложение

tsc --noEmit
→ проверяет типы
```

Поэтому успешный

```bash
npm run build
```

ещё не означает, что успешно пройдёт

```bash
npm run typecheck
```

Это разные задачи.

### Ошибку компилятора нужно сначала прочитать

Теперь специально создадим противоречие:

```typescript
function calculateTotal(
  price: number,
  quantity: number
): number {
  return price * quantity;
}

calculateTotal("100", 2);
```

Компилятор сообщит примерно следующее:

```text
Argument of type 'string' is not assignable
to parameter of type 'number'.
```

Сообщение можно прочитать почти буквально:

> Аргумент типа `string` нельзя передать параметру типа `number`.

В этот момент есть соблазн сформулировать задачу так:

> «Как убрать ошибку TypeScript?»

Но сама ошибка — не главная проблема. Она только показывает противоречие между двумя частями программы.

Полезнее другой вопрос:

> **Почему фактические данные не совпадают с нашей моделью?**

Возможно, ошибка действительно в вызове:

```typescript
calculateTotal(100, 2);
```

Но возможна и другая ситуация: цена действительно приходит из формы строкой:

```typescript
"100"
```

Тогда изменение аннотации только ради исчезновения красного подчёркивания не решает задачу. Нужно определить, в какой момент строковое значение должно стать числом и что делать, если преобразование невозможно.

Компилятор не всегда знает правильное с точки зрения логики приложения решение.

Он сообщает другое:

> **Две части программы сейчас не согласуются друг с другом.**

Задача разработчика — понять, какая из них неверно описывает реальность.

Именно поэтому чтение сообщений `tsc` — отдельный навык, а не неприятное дополнение к TypeScript.

### Практика

Теперь можно вернуться к проекту прошлой недели.

На этом этапе не требуется типизировать приложение целиком. Сначала нужно встроить проверку типов в рабочий процесс и увидеть границу между компиляцией и выполнением.

#### Шаг 1. Проверь конфигурацию

Если шаги из подраздела «Подключаем TypeScript к проекту “Полки”» выполнены, в корне проекта уже лежит `tsconfig.json`.

Найди в нём настройки:

```text
target
module
strict
outDir
lib
```

Для каждой попробуй сформулировать одним предложением:

> «Эта настройка нужна, чтобы…»

Цель упражнения — не запомнить значения из примера, а понимать назначение параметров.

#### Шаг 2. Включи строгую проверку

Убедись, что используется:

```json
"strict": true
```

Если после этого появились ошибки, не отключай настройку. Выбери одну ошибку и попробуй определить, какой информации не хватает компилятору.

#### Шаг 3. Добавь отдельную команду проверки типов

В `package.json` понадобится скрипт:

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit"
  }
}
```

Запусти:

```bash
npm run typecheck
```

#### Шаг 4. Специально сломай тип

В одном из `.ts`-файлов временно добавь:

```typescript
const count: number = "пять";
```

После этого сравни результаты:

```bash
npm run build
```

и:

```bash
npm run typecheck
```

Ответь на два вопроса:

- какая команда отвечает за сборку приложения;
- какая действительно проверяет типы.

После эксперимента ошибку нужно исправить.

#### Шаг 5. Посмотри, куда исчезают типы

Возьми небольшой файл:

```typescript
function double(value: number): number {
  return value * 2;
}

const result: number = double(5);

console.log(result);
```

Положи его не в `src`, а в отдельную папку, например в `experiments/double.ts`. В рабочем `tsconfig.json` стоит `noEmit`, поэтому для этого опыта понадобится отдельный маленький конфиг. Создай рядом с `package.json` файл `tsconfig.emit.json`:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "strict": true,
    "outDir": ".type-erasure",
    "rootDir": "experiments",
    "types": []
  },
  "files": ["experiments/double.ts"]
}
```

Выполни:

```bash
npm exec -- tsc -p tsconfig.emit.json
```

Флаг `-p` говорит компилятору, какой конфиг взять вместо `tsconfig.json`. Результат появится в `.type-erasure/double.js`, эту папку стоит добавить в `.gitignore`. Сравни `.ts`-файл с получившимся JavaScript.

Найди в итоговом `.js`:

```typescript
: number
```

Если всё работает так, как описано выше, найти эту конструкцию не получится.
Это и есть стирание типов в самом наглядном виде.

### Если кратко

Модель работы TypeScript можно свести к одной схеме:

```text
TypeScript-код
       ↓
проверка типов
       ↓
стирание типов
       ↓
JavaScript
       ↓
runtime
```

Из неё следуют несколько принципов, которые понадобятся во всех следующих разделах.

TypeScript проверяет код до запуска.

В браузере выполняется JavaScript, а типов TypeScript там уже нет.

Аннотация типа не является runtime-проверкой значения.

Внешние данные не становятся безопасными только потому, что рядом с переменной написано имя типа.

Успешная сборка Vite сама по себе не означает успешную проверку типов.

И наконец, сообщение компилятора — не препятствие, которое нужно как можно быстрее убрать.

Это информация о противоречии в программе.

Поэтому при следующей ошибке TypeScript стоит сначала задать три вопроса:

> **Что здесь знает компилятор?**  
> **Откуда он это знает?**  
> **Какие две части программы сейчас не согласуются друг с другом?**

В следующем разделе разберём, как сообщать компилятору информацию о значениях с помощью базовых типов и аннотаций — и почему во многих местах TypeScript уже знает достаточно, поэтому дополнительная аннотация только создаёт шум.

## 3. Базовые типы, аннотации и вывод типов

В предыдущем разделе появилась главная модель работы TypeScript: компилятор проверяет код до запуска, а затем типовая информация стирается. Теперь можно разобраться, откуда эта информация вообще берётся.

Самый очевидный способ — написать тип самостоятельно:

```typescript
const courseName: string = "TypeScript";
const lessonsCount: number = 12;
const isPublished: boolean = true;
```

Здесь разработчик явно сообщает компилятору:

```text
courseName → string
lessonsCount → number
isPublished → boolean
```

Такая запись называется **аннотацией типа**.

Но означает ли это, что каждую переменную в TypeScript нужно снабжать аннотацией? Нет.
В большинстве простых случаев компилятор уже располагает необходимой информацией.

Рассмотрим две записи. Первая:

```typescript
const lessonsCount: number = 12;
```

Вторая:

```typescript
const lessonsCount = 12;
```

Во втором случае `: number` отсутствует. Но значение `12` никуда не исчезло.

Компилятор видит его и может самостоятельно сделать вывод о типе переменной.

Если затем написать:

```typescript
lessonsCount.toUpperCase();
```

TypeScript сообщит об ошибке.

Почему, если `: number` нигде не написано?

Потому что компилятор **вывел тип из значения**.

Это называется **выводом типов** (type inference).

Если навести курсор на `lessonsCount`, редактор покажет не `number`, а `12`. Для `const` компилятор выводит самый точный тип — конкретное значение: переменная никогда не изменится, значит, в ней всегда будет `12`. У `let lessonsCount = 12` тип будет `number`, потому что позже туда можно записать другое число. Такие типы-значения подробно разберём в разделе 6.

Аннотация становится особенно полезна там, где компилятор **не может получить нужное знание самостоятельно** или где важно явно зафиксировать границу между частями программы.

Хороший пример — параметры функции.

### Параметр функции: откуда узнать его тип?

Есть JavaScript-функция:

```javascript
function formatPrice(price) {
  return `${price} ₽`;
}
```

Что такое `price`? Число? Строка? Объект?

Внутри самой функции нет достаточной информации, чтобы уверенно ответить.

Можно посмотреть на вызов:

```javascript
formatPrice(1500);
```

и предположить, что ожидается число. Но функция может вызываться в другом месте:

```javascript
formatPrice("1500");
```

TypeScript не должен угадывать намерение автора.

Поэтому границу функции полезно описать явно:

```typescript
function formatPrice(price: number) {
  return `${price} ₽`;
}
```

Теперь известно:

> Всё, что хочет попасть в эту функцию через `price`, должно соответствовать `number`.

И вызов

```typescript
formatPrice("1500");
```

становится противоречием, которое компилятор способен обнаружить.

Тип результата тоже можно указать:

```typescript
function formatPrice(price: number): string {
  return `${price} ₽`;
}
```

Но посмотрим на реализацию:

```typescript
return `${price} ₽`;
```

TypeScript уже видит, что шаблонная строка создаёт строковое значение. Поэтому он способен вывести тип результата самостоятельно:

```typescript
function formatPrice(price: number) {
  return `${price} ₽`;
}
```

В обоих случаях результат будет известен как строка.

Зачем тогда вообще указывать возвращаемый тип?

Иногда это полезно как явный контракт функции.

Представим:

```typescript
function calculateTotal(
  price: number,
  quantity: number
): number {
  return price * quantity;
}
```

Запись `: number` фиксирует ожидание: эта функция должна возвращать число.

Если реализация случайно изменится:

```typescript
function calculateTotal(
  price: number,
  quantity: number
): number {
  return `${price * quantity} ₽`;
}
```

компилятор сразу покажет противоречие между обещанным результатом и реальным.

Поэтому возвращаемый тип часто полезен для функций, которые являются заметными границами программы, даже если TypeScript технически способен вывести его сам.

Внутри небольших локальных выражений, напротив, обычно разумно доверять выводу типов.

Можно использовать простое рабочее правило:

> **На границах программы типы чаще стоит записывать явно. Внутри — позволять TypeScript выводить их там, где информации уже достаточно.**

### Базовые типы

Чтобы начать типизацию проекта, не нужен большой каталог типов. Для большинства первых задач достаточно нескольких базовых вариантов.

Строки:

```typescript
let title: string;
```

Числа:

```typescript
let price: number;
```

Логические значения:

```typescript
let isCompleted: boolean;
```

Массивы:

```typescript
let tags: string[];
let prices: number[];
```

Здесь запись

```typescript
string[]
```

означает массив строк, а

```typescript
number[]
```

— массив чисел.

Если попытаться добавить неправильное значение:

```typescript
const prices: number[] = [100, 200, "бесплатно"];
```

TypeScript обнаружит несовпадение.

### Когда важна не просто коллекция, а позиция

Иногда массив используется не как коллекция однотипных значений, а как структура с заранее известными позициями.

Например, координата:

```typescript
const position: [number, number] = [10, 25];
```

Такая запись называется **кортежем**, или tuple.

В данном случае известно не только то, что внутри находятся числа, но и то, что ожидается две позиции.

Другой пример:

```typescript
const userInfo: [string, number] = ["Анна", 21];
```

Первая позиция должна быть строкой, вторая — числом.

Кортежи пригодятся там, где смысл значения действительно связан с позицией. Использовать их вместо обычных объектов только ради краткости обычно не требуется.

### `null` и `undefined`

Особое внимание стоит уделить двум значениям:

```typescript
null
undefined
```

В JavaScript они часто означают отсутствие данных, но это отсутствие может быть принципиально важным.

Например:

```typescript
const savedName = localStorage.getItem("name");
```

Кажется естественным ожидать строку. Но что произойдёт, если значения с ключом `"name"` в хранилище нет? Метод вернёт `null`.

Значит, честная модель должна учитывать оба варианта:

```text
string или null
```

В TypeScript возможность нескольких вариантов записывается через `|`:

```typescript
let userName: string | null;
```

Подробно такие типы разберём позже. Пока важна сама идея:

> Если значение действительно может отсутствовать, тип не должен скрывать эту возможность.

### Что означает `void`

Некоторые функции выполняют действие, но не возвращают полезного результата.

Например:

```typescript
function logMessage(message: string): void {
  console.log(message);
}
```

`void` показывает, что от функции не ожидается значение, которое затем будет использовано как результат вычисления.

Типичный пример — функция, которая что-то выводит, меняет состояние интерфейса или выполняет другое действие без полезного `return`.

При этом нет необходимости добавлять `: void` ко всем таким функциям: TypeScript часто способен вывести это самостоятельно.

И снова работает тот же принцип: аннотация нужна не ради количества аннотаций, а для того, чтобы делать контракт функции понятнее.

### А как типизировать объект?

Можно описать форму объекта прямо на месте:

```typescript
const task: {
  title: string;
  completed: boolean;
} = {
  title: "Изучить TypeScript",
  completed: false
};
```

TypeScript теперь знает, что объект должен содержать строковый `title` и логический `completed`.

Но если такая структура используется во многих функциях, то постоянно повторять её неудобно:

```typescript
function renderTask(task: {
  title: string;
  completed: boolean;
}) {
  // ...
}
```

```typescript
function saveTask(task: {
  title: string;
  completed: boolean;
}) {
  // ...
}
```

Для повторно используемых структур существуют отдельные способы дать типу имя. К ним перейдём в разделе про `interface` и `type`.

Пока важно увидеть сам принцип: объект тоже описывается через то, **какие свойства в нём ожидаются и какие значения в них находятся**.

### Практика

Открой проект прошлой недели и выбери две-три функции, которые участвуют в основной логике приложения. В «Полке» это, например, `formatPrice`, функция создания карточки товара и обработчик добавления в корзину.

Начни с их параметров.

Например, если есть функция:

```javascript
function addTask(title) {
  // ...
}
```

определи, что известно о `title`, и перенеси это знание в код:

```typescript
function addTask(title: string) {
  // ...
}
```

Проделай то же с остальными параметрами выбранных функций.

Затем посмотри на возвращаемые значения. Если функция возвращает значимый для программы результат, попробуй явно записать его тип.

После этого изучи локальные переменные внутри тех же функций.

Например:

```typescript
const normalizedTitle = title.trim();
const isEmpty = normalizedTitle.length === 0;
```

Наведи курсор на `normalizedTitle` и `isEmpty` в редакторе и посмотри, какие типы вывел TypeScript.

Если тип уже определён правильно, добавлять

```typescript
const normalizedTitle: string = title.trim();
const isEmpty: boolean = normalizedTitle.length === 0;
```

не требуется.

Попробуй, наоборот, удалить несколько очевидных аннотаций из собственного кода и проверить:

```bash
npm run typecheck
```

Если проверка по-прежнему проходит и редактор правильно знает тип переменной, значит7, компилятору было достаточно информации без явной аннотации.

В конце выбери одну из функций и объясни:

> Какие типы здесь были указаны явно, какие TypeScript вывел самостоятельно и откуда в каждом случае появилась эта информация?

### Если кратко

Типовая информация не обязательно должна быть записана рядом с каждым значением.

Если TypeScript видит:

```typescript
const count = 5;
```

он уже способен понять, с каким значением работает.

Поэтому задача состоит не в том, чтобы расставить как можно больше `: string`, `: number` и `: boolean`. Гораздо важнее понимать источник информации. Например, у параметров функций и важных возвращаемых значений, поэтому явная аннотация помогает зафиксировать контракт. Внутри функции часто можно довериться выводу типов.

## 4. `any`, `unknown`, `never` и строгость

До сих пор примеры были довольно удобными.

Если написано:

```typescript
const price = 1200;
```

компилятор знает достаточно.

Если функция объявлена так:

```typescript
function formatPrice(price: number) {
  // ...
}
```

тоже понятно, с какими данными она должна работать.

Но в реальном приложении регулярно возникают значения, о которых известно гораздо меньше.

Например, пришёл ответ сервера:

```typescript
const data = await response.json();
```

Что находится в `data`? До выполнения запроса достоверного ответа нет. И здесь важно не заставить TypeScript «поверить» в удобный вариант, а честно записать степень знания о данных.

### Тип `any`

Рассмотрим значение типа `any`:

```typescript
let data: any;
```

С ним можно сделать почти что угодно:

```typescript
data.name;
data.user.profile.email;
data.toUpperCase();
data();
data * 10;
```

Компилятор практически перестаёт задавать вопросы.

На первый взгляд, это удобно.

Появилась ошибка типов:

```typescript
const user = getSomething();
```

Можно написать:

```typescript
const user: any = getSomething();
```

И многие ошибки исчезнут.

Но вместе с ошибками исчезает и проверка.

Представим:

```typescript
let user: any = {
  name: "Анна"
};

console.log(user.nmae.toUpperCase());
```

В имени свойства допущена опечатка:

```text
nmae
```

Но `any` разрешает обращение к любому свойству.

Ошибка снова обнаружится только в runtime.

Проблема становится заметнее, когда такое значение передаётся дальше по программе.

Например:

```typescript
const responseData: any = await response.json();

const userName = responseData.user.profile.name;
```

Что известно о `userName`? Если исходное значение было `any`, компилятор теряет возможность надёжно рассуждать и о многих последующих операциях.

Можно продолжить:

```typescript
const upperName = userName.toUpperCase();
```

И TypeScript не сможет защитить программу, даже если в реальности `name` окажется числом или вообще будет отсутствовать. Один участок без проверки начинает влиять на код вокруг него. Поэтому `any` особенно опасен не как отдельная строка, а как источник данных для остальных частей программы.

Использовать `any` только для того, чтобы компилятор перестал показывать ошибку, — плохая стратегия.

### Тип `unknown`

Есть другой тип:

```typescript
let data: unknown;
```

По смыслу он тоже допускает, что внутри может находиться что угодно.

Например:

```typescript
data = "hello";
data = 42;
data = false;
data = { name: "Анна" };
data = null;
```

Но между `any` и `unknown` есть принципиальная разница.

С `any` TypeScript говорит:

> «Здесь может быть что угодно».

С `unknown`:

> **«Значение существует, но пока неизвестно, что именно это такое».**

Поэтому такой код не пройдёт проверку:

```typescript
let data: unknown;

console.log(data.name);
```

Нельзя и так:

```typescript
data.toUpperCase();
```

И так тоже:

```typescript
data + 10;
```

Это не потому, что TypeScript знает, что операции неправильные. Наоборот. Он **не знает достаточно, чтобы подтвердить их безопасность**.

### `any` и `unknown`: одна ситуация, разные результаты

Сравним два фрагмента:

```typescript
let value: any = "hello";

console.log(value.toUpperCase());
```

и

```typescript
let value: unknown = "hello";

console.log(value.toUpperCase());
```

Первый вариант компилятор пропустит.

Второй — нет.

Но если в `unknown` фактически лежит строка, почему нельзя вызвать `toUpperCase()`?

Потому что тип описывает не скрытую истину, которую знает автор примера, а **знание, доступное компилятору в конкретной точке программы**.

Записано:

```typescript
value: unknown
```

Значит, TypeScript должен исходить из того, что точный тип значения пока неизвестен.

Чтобы получить право на строковую операцию, нужно сначала это знание уточнить:

```typescript
if (typeof value === "string") {
  console.log(value.toUpperCase());
}
```

Внутри `if` ситуация изменилась.

Проверка

```typescript
typeof value === "string"
```

дала компилятору новую информацию.

До неё:

```text
value → unknown
```

Внутри ветки:

```text
value → string
```

Поэтому `unknown` не мешает работать с данными. Он требует сначала доказать, что нужная операция безопасна.

Позже подробно разберём, как TypeScript сужает типы на основании таких проверок.

Вернёмся к вопросу из начала темы:

```typescript
interface User {
  id: number;
  name: string;
}
```

Есть запрос:

```typescript
const response = await fetch("/api/user");
```

И ожидается, что сервер вернёт пользователя.

Самая опасная мысль здесь звучит так:

> «Мы знаем, что endpoint возвращает пользователя, значит, данные уже можно считать `User`.»

Но TypeScript не видел ответ сервера.

Сервер может вернуть ожидаемый объект:

```json
{
  "id": 12,
  "name": "Анна"
}
```

А может вернуть:

```json
{
  "message": "User not found"
}
```

Или вообще данные другой формы.

Само описание:

```typescript
interface User
```

ничего не проверяет в runtime.

Поэтому внешний результат безопаснее принять как неизвестный:

```typescript
const raw: unknown = await response.json();
```

Теперь TypeScript не позволит сразу написать:

```typescript
console.log(raw.name);
```

Сначала программа должна проверить данные.

Например, начать с самых общих условий:

```typescript
if (typeof raw === "object" && raw !== null) {
  // Теперь известно хотя бы то,
  // что raw — непустой объект.
}
```

Полную проверку объекта разберём позже вместе с сужением типов. Сейчас важен принцип:

> **Внешние данные сначала проверяются, и только после этого им можно доверять внутри программы.**

Именно здесь проходит граница между статической типизацией и runtime-валидацией.

### Неизвестность лучше ложной уверенности

Представим два варианта:

```typescript
const data: any = await response.json();

console.log(data.user.name.toUpperCase());
```

и

```typescript
const data: unknown = await response.json();

console.log(data.user.name.toUpperCase());
```

В первом случае компилятор почти наверняка не остановит потенциально опасную цепочку обращений.

Во втором — остановит.

Может показаться, что `unknown` создаёт дополнительную работу. Но сообщение об ошибке здесь полезно: программа действительно ещё не доказала, что у полученного значения есть `user`, внутри него есть `name`, а `name` является строкой.

`unknown` заставляет код отразить реальное положение дел.

Данные неизвестны — значит, сначала нужна проверка.

И только после проверки можно выполнять операции, требующие конкретного типа.

### Тип `never`

У `any` и `unknown` сравнительно легко увидеть практический смысл:

```text
any     → проверку отключаем
unknown → пока не знаем
```

`never` описывает другую ситуацию:

> **Такого значения в этой точке программы вообще не должно существовать.**

Рассмотрим функцию:

```typescript
function fail(message: string): never {
  throw new Error(message);
}
```

Она никогда не возвращает значение.

Выполнение функции заканчивается:

```typescript
throw new Error(message);
```

Поэтому тип результата — `never`.

Другой смысл `never` проявляется, когда логика программы исключила все возможные варианты.

Условно:

```typescript
function handleValue(value: string | number) {
  if (typeof value === "string") {
    console.log(value.toUpperCase());
    return;
  }

  if (typeof value === "number") {
    console.log(value.toFixed(2));
    return;
  }

  // Здесь не должно остаться возможных значений.
}
```

Изначально `value` мог быть строкой или числом.

После проверки строки остаётся число.

После проверки числа вариантов больше нет.

Идея `never` понадобится позже, когда появятся типы с несколькими строго заданными состояниями и нужно будет убедиться, что обработаны все варианты.

Пока достаточно различать:

```text
any
→ значение может быть каким угодно, проверка отключена

unknown
→ значение может быть каким угодно, но сначала нужно выяснить каким

never
→ допустимого значения здесь быть не может
```

### Практика

Вернись к проекту с прошлой недели и найди места, где данные приходят не из полностью контролируемого TypeScript-кода.

Это могут быть:

- ответ `fetch`;
- данные из `localStorage`;
- пользовательский ввод;
- результат разбора JSON;
- данные, полученные из DOM.

Выбери одно такое место.

В «Полке» недели 10 таких мест пока почти нет: каталог лежит в `data.js` и не приходит с сервера. Чтобы потренироваться на настоящем ответе, загрузи каталог через `fetch("/api/products.json")`, положив файл из материалов домашки в `public/api/`. Это задача 7 из домашки, так что код пригодится.

Сначала ответь:

> **Что о значении действительно известно в момент его появления в программе?**

Если форма данных ещё никак не проверена, не начинай с желаемого типа.
Для ответа сервера, например, можно явно зафиксировать границу:

```typescript
const raw: unknown = await response.json();
```

Теперь попробуй выполнить операцию, которую раньше код делал сразу:

```typescript
console.log(raw.name);
```

Запусти:

```bash

```

Не исправляй ошибку с помощью `any`.

Сначала прочитай сообщение компилятора и объясни:

> Почему TypeScript не разрешает эту операцию? Какой информации ему не хватает?

После этого добавь простую runtime-проверку, подходящую для выбранных данных.

Если ожидается строка:

```typescript
if (typeof raw === "string") {
  console.log(raw.toUpperCase());
}
```

Если ожидается число:

```typescript
if (typeof raw === "number") {
  console.log(raw.toFixed(2));
}
```

Если ожидается объект, начни хотя бы с проверки:

```typescript
if (typeof raw === "object" && raw !== null) {
  // Работа с проверкой объекта продолжится
  // в разделе про сужение типов.
}
```

После этого временно замени `unknown` на `any` и сравни поведение компилятора.

Какие ошибки исчезли? Стало ли от этого известно больше о реальном значении?

### Если кратко

`any`, `unknown` и `never` нужны не для того, чтобы добавить ещё три пункта в список типов. Они описывают принципиально разные отношения программы к знанию о значении.

**`any`** означает, что TypeScript практически перестаёт проверять операции с этим значением.

**`unknown`** означает, что тип пока неизвестен, поэтому перед использованием значение нужно исследовать и проверить.

**`never`** означает, что допустимого значения в этой точке программы быть не должно.

Для внешних данных особенно важно не создавать ложную уверенность.

Ответ сервера, значение из хранилища или другой внешний ввод не становятся проверенными только потому, что в TypeScript-коде рядом написано имя ожидаемого типа.

## 5. `interface`, `type` и структурная типизация

В предыдущих разделах типы уже использовались для параметров функций, массивов и внешних данных. Но в реальном проекте значительная часть информации обычно хранится не в отдельных строках и числах, а в объектах.

Например:

```typescript
const task = {
  id: 12,
  title: "Подготовить презентацию",
  completed: false
};
```

О таком значении известно больше, чем просто «это объект».

Важно, что у него есть определённые свойства:

```text
id → number
title → string
completed → boolean
```

И если задачи используются в разных частях программы, эту форму удобно описать один раз.

Для этого можно использовать `interface`:

```typescript
interface Task {
  id: number;
  title: string;
  completed: boolean;
}
```

Теперь тип можно использовать в разных функциях:

```typescript
function renderTask(task: Task) {
  // ...
}

function saveTask(task: Task) {
  // ...
}

function toggleTask(task: Task) {
  // ...
}
```

Во всех трёх случаях TypeScript знает одну и ту же договорённость: значение должно иметь свойства `id`, `title` и `completed` соответствующих типов.

Если попытаться передать объект другой формы:

```typescript
renderTask({
  id: 12,
  name: "Подготовить презентацию",
  completed: false
});
```

компилятор обнаружит, что обязательного свойства `title` нет.

Здесь снова работает уже знакомая модель:

> **Тип записывает знание о данных так, чтобы компилятор мог сравнивать с ним остальные части программы.**

### TypeScript смотрит прежде всего на форму

Вернёмся к четвёртому вопросу из начала темы.

Есть два интерфейса:

```typescript
interface Point {
  x: number;
  y: number;
}

interface Coords {
  x: number;
  y: number;
}
```

И функция:

```typescript
function printCoords(coords: Coords) {
  console.log(coords.x, coords.y);
}
```

Создадим значение:

```typescript
const point: Point = {
  x: 10,
  y: 20
};
```

Можно ли передать его в `printCoords`?

```typescript
printCoords(point);
```

Да.

Хотя тип называется `Point`, а функция ожидает `Coords`, TypeScript видит, что их структура совместима:

```text
Point
x: number
y: number

Coords
x: number
y: number
```

Компилятор сравнивает то, **что есть внутри значения**, а не только названия типов.

Такой принцип называется **структурной типизацией**.

Упрощённо его можно сформулировать так:

> **Если значение имеет нужную форму, оно может быть совместимо с ожидаемым типом, даже если типы называются по-разному.**

### Почему это может быть непривычно после классов

При работе с классами легко привыкнуть к другой интуиции: важным кажется не только устройство объекта, но и то, экземпляром какого класса он является.

TypeScript во многих ситуациях с объектными типами рассуждает иначе.

Например:

```typescript
interface Named {
  name: string;
}

const student = {
  id: 7,
  name: "Мария",
  course: "Frontend"
};

function printName(value: Named) {
  console.log(value.name);
}

printName(student);
```

`student` содержит больше свойств, чем требует `Named`.

Но функции нужен только

```typescript
name: string
```

И такое свойство у объекта есть.

Значит, для этой операции данных достаточно.

Компилятор как будто задаёт вопрос:

> «Есть ли у значения всё, чем функция собирается пользоваться?»

Если ответ положительный, типы могут быть совместимы.

### Лишние свойства: небольшая тонкость

Структурная типизация не означает, что TypeScript полностью игнорирует дополнительные свойства.

Рассмотрим:

```typescript
interface User {
  id: number;
  name: string;
}
```

Есть объект:

```typescript
const admin = {
  id: 1,
  name: "Анна",
  role: "admin"
};
```

Такой вызов допустим:

```typescript
function printUser(user: User) {
  console.log(user.name);
}

printUser(admin);
```

У `admin` есть всё, что требуется от `User`.

Но если передать объектный литерал напрямую:

```typescript
printUser({
  id: 1,
  name: "Анна",
  role: "admin"
});
```

TypeScript сообщит об ошибке:

```text
Object literal may only specify known properties, and 'role' does not exist in type 'User'.
```

Это дополнительная проверка объектных литералов, которая помогает находить опечатки и случайно переданные поля.

Например:

```typescript
printUser({
  id: 1,
  name: "Анна",
  roel: "admin"
});
```

`roel` вполне может оказаться обычной опечаткой.

Поэтому такое поведение не противоречит структурной типизации. Компилятор просто строже проверяет объект, который создаётся непосредственно в месте использования.

Для начала достаточно запомнить две идеи:

> Существующее значение может содержать дополнительные свойства, если в нём есть всё необходимое.

> При создании объектного литерала непосредственно на месте TypeScript дополнительно проверяет неожиданные поля.

### А что такое `type`?

Форму объекта можно описать и с помощью `type`:

```typescript
type Task = {
  id: number;
  title: string;
  completed: boolean;
};
```

Такой тип можно использовать почти так же:

```typescript
function renderTask(task: Task) {
  console.log(task.title);
}
```

Возникает естественный вопрос:

> Когда нужен `interface`, а когда `type`?

На первой неделе TypeScript не требуется изучать длинную таблицу различий.

Практического правила пока достаточно:

> **`interface` удобно использовать для описания объектов и их расширения.**

> **`type` понадобится, когда тип нужно составить не только как форму объекта — например, из нескольких допустимых вариантов.**

В следующем разделе `type` как раз станет особенно полезен.

### Расширение интерфейса

Иногда одна структура является расширенной версией другой.

Например:

```typescript
interface User {
  id: number;
  name: string;
}
```

Для администратора нужны те же поля плюс дополнительные:

```typescript
interface Admin extends User {
  permissions: string[];
}
```

Теперь `Admin` содержит:

```text
id
name
permissions
```

Это позволяет не повторять общую часть структуры.

Например:

```typescript
const admin: Admin = {
  id: 1,
  name: "Анна",
  permissions: ["edit", "delete"]
};
```

Но здесь важно не превращать типизацию в создание сложной иерархии заранее.

Расширение имеет смысл, когда в данных проекта действительно существует отношение:

```text
есть общая структура
+
к ней добавляется новая информация
```

Если такой связи в данных нет, создавать её только ради использования `extends` не требуется.

Для компилятора значение подходит не потому, что у его типа «правильное имя», а потому, что оно содержит необходимые свойства нужных типов. Это и есть структурная типизация.

## 6. Композиция: `union`, `intersection`, литералы и `enum`

### Литеральное значение

До сих пор тип чаще отвечал на вопрос:

> Какое это значение?

Например:

```typescript
string
```

Или:

```typescript
number
```

Но реальные данные не всегда имеют только один допустимый вариант.

Представим состояние загрузки:

```typescript
let status = "loading";
```

Позже:

```typescript
status = "success";
```

Или:

```typescript
status = "error";
```

Для JavaScript это просто строки.

Но из логики приложения известно больше.

Допустимы только несколько конкретных значений:

```text
idle
loading
success
error
```

Строка

```typescript
"laoding"
```

не является новым состоянием приложения.

Это опечатка.

Пока переменная имеет обычный тип `string`, компилятор не знает этой договорённости:

```typescript
let status: string = "loading";

status = "laoding";
```

С точки зрения `string` всё правильно: `"laoding"` действительно строка.

Значит, проблема не в базовом типе, наша модель просто недостаточно точна.

В TypeScript типом может быть не только

```typescript
string
```

но и конкретное строковое значение:

```typescript
"loading"
```

Например:

```typescript
let status: "loading";
```

Теперь переменная может содержать только одну строку:

```typescript
status = "loading";
```

А

```typescript
status = "success";
```

уже не подходит.

Один вариант слишком ограничен, но несколько литеральных типов можно объединить.

### Union: одно значение, несколько допустимых типов

Оператор `|` означает:

> Значение может соответствовать одному из перечисленных вариантов.

Например:

```typescript
type Status =
  | "idle"
  | "loading"
  | "success"
  | "error";
```

Теперь:

```typescript
let status: Status = "idle";

status = "loading";
status = "success";
status = "error";
```

допустимы.

А:

```typescript
status = "laoding";
```

приведёт к ошибке.

Компилятор знает не просто:

```text
status → string
```

а гораздо точнее:

```text
status →
"idle"
или
"loading"
или
"success"
или
"error"
```

Это даёт сразу два полезных эффекта. Во-первых, TypeScript способен ловить опечатки. Во-вторых, редактор может предлагать только допустимые варианты. Таким образом, литеральные типы превращают договорённость: «Здесь используются только четыре специальные строки» в проверяемое правило программы.

Объединять можно и обычные типы.

Например:

```typescript
let id: string | number;
```

Такое значение может быть:

```typescript
id = 15;
```

или:

```typescript
id = "15";
```

Но нельзя написать:

```typescript
id = true;
```

Похожая запись уже встречалась раньше:

```typescript
string | null
```

Union — не отдельная экзотическая возможность. Он используется каждый раз, когда реальная модель данных допускает несколько вариантов.

Однако `union` создает вопрос.

Представим:

```typescript
function printId(id: string | number) {
  console.log(id.toUpperCase());
}
```

TypeScript не разрешит такой код.

Почему?

В `string` метод `toUpperCase()` есть.

Но `id` может быть и `number`.

Компилятор знает:

```text
id → string ИЛИ number
```

А код пытается выполнить операцию, безопасную только для одного варианта. Поэтому до выбора строковой операции нужно сначала выяснить, какой вариант находится в переменной.

Например:

```typescript
function printId(id: string | number) {
  if (typeof id === "string") {
    console.log(id.toUpperCase());
  }
}
```

Внутри проверки компилятор уже знает больше.

Этот механизм называется **сужение типов** и он станет центральным в следующем разделе.

### Состояние интерфейса тоже является данными

Особенно полезны литеральные union-типы для состояния интерфейса.

Без них состояние может быть записано так:

```typescript
let status = "loading";
```

И затем проверяться:

```typescript
if (status === "succes") {
  // ...
}
```

Опечатка легко останется незамеченной.

Можно сделать модель точнее:

```typescript
type Status =
  | "idle"
  | "loading"
  | "success"
  | "error"
  | "empty";
```

Теперь состояние интерфейса становится ограниченным набором допустимых значений.

### Union может объединять и объектные формы

Допустим, состояние описывается не только строкой.

При успешной загрузке нужны данные:

```typescript
{
  status: "success",
  data: tasks
}
```

При ошибке — сообщение:

```typescript
{
  status: "error",
  message: "Не удалось загрузить задачи"
}
```

При загрузке ни того ни другого пока нет:

```typescript
{
  status: "loading"
}
```

Эти варианты можно объединить:

```typescript
interface Task {
  id: number;
  title: string;
  completed: boolean;
}

type LoadState =
  | {
      status: "loading";
    }
  | {
      status: "success";
      data: Task[];
    }
  | {
      status: "error";
      message: string;
    };
```

Теперь TypeScript знает не только набор состояний, но и то, **какие данные существуют в каждом состоянии**.

Например, объект:

```typescript
const state: LoadState = {
  status: "success",
  data: []
};
```

корректен.

Но

```typescript
const state: LoadState = {
  status: "success",
  message: "Ошибка"
};
```

не соответствует модели.

Для `success` ожидается `data`, а `message` относится к другому варианту.

Это гораздо точнее модели вроде:

```typescript
interface State {
  status: string;
  data?: Task[];
  message?: string;
}
```

В такой структуре легко создать бессмысленную комбинацию:

```typescript
{
  status: "loading",
  data: [...],
  message: "Ошибка"
}
```

То есть все свойства формально существуют, но их сочетание не соответствует реальному состоянию приложения.

Union позволяет моделировать не просто поля по отдельности, а **допустимые комбинации данных**.

К этой конструкции вернёмся в следующем разделе: поле `status` позволит TypeScript понимать, какой именно вариант объекта находится в конкретной ветке программы.

### Intersection: когда нужны свойства сразу нескольких типов

Оператор

```typescript
&
```

выражает другую идею.

Если union означает:

```text
одно ИЛИ другое
```

то intersection означает:

```text
одно И другое одновременно
```

Представим две структуры:

```typescript
interface Identifiable {
  id: number;
}

interface Timestamped {
  createdAt: string;
}
```

Тип

```typescript
type StoredItem = Identifiable & Timestamped;
```

означает, что значение должно удовлетворять обеим структурам.

Например:

```typescript
const item: StoredItem = {
  id: 15,
  createdAt: "2026-09-09"
};
```

Если оставить только одно свойство:

```typescript
const item: StoredItem = {
  id: 15
};
```

тип уже не подходит.

Intersection удобен, когда одна сущность действительно объединяет требования нескольких структур.

Например:

```typescript
interface TaskData {
  title: string;
  completed: boolean;
}

interface EntityMeta {
  id: number;
}

type Task = TaskData & EntityMeta;
```

Для `Task` нужны свойства обеих частей.

Но, как и с расширением интерфейсов, не стоит дробить каждую небольшую структуру на несколько типов без необходимости. Композиция полезна тогда, когда части действительно имеют самостоятельный смысл в модели проекта.

<a id="pipe-and-ampersand"></a>

### `|` и `&`: различаем и не путаем

Их удобно различать через смысл данных.

```typescript
type Id = string | number;
```

означает:

> Значение может быть строкой **или** числом.

А

```typescript
type Task = TaskData & EntityMeta;
```

означает:

> Объект должен соответствовать `TaskData` **и одновременно** `EntityMeta`.

Поэтому перед выбором оператора полезно не вспоминать символ, а сформулировать правило обычными словами:

> Здесь допустим один из нескольких вариантов?

Тогда нужен union.

> Здесь нужны требования сразу нескольких структур?

Тогда возможен intersection.

### `enum`

В существующем TypeScript-коде можно встретить ещё один способ описывать ограниченный набор вариантов:

```typescript
enum Status {
  Idle,
  Loading,
  Success,
  Error
}
```

Тогда:

```typescript
let status: Status = Status.Loading;
```

Есть и строковые `enum`:

```typescript
enum Status {
  Idle = "idle",
  Loading = "loading",
  Success = "success",
  Error = "error"
}
```

`enum` входит в язык TypeScript, поэтому важно уметь узнавать такую конструкцию в чужом коде.

Но для простых состояний в современном TypeScript часто достаточно литерального union:

```typescript
type Status =
  | "idle"
  | "loading"
  | "success"
  | "error";
```

На этой неделе такого сравнения достаточно.

У `enum` есть особенность, которая отличает его от всех рассмотренных типов: он не исчезает после компиляции. Union `Status` после `tsc` пропадает без следа, а `enum` превращается в настоящий объект. Вот что получается из `enum Status { Idle, Loading }`:

```javascript
var Status;
(function (Status) {
    Status[Status["Idle"] = 0] = "Idle";
    Status[Status["Loading"] = 1] = "Loading";
})(Status || (Status = {}));
```

Значит, `enum` — одновременно тип и значение, которое существует в браузере: его можно перебрать в цикле, а по числу получить имя (`Status[0] === "Idle"`). Если такой объект во время выполнения не нужен, литеральный union проще: он ничего не добавляет в сборку. Почему в последние годы `enum` советуют реже, разберём в «★ Глубже».

### Как выбрать модель

Представим обычную строку:

```typescript
let status: string;
```

Она говорит компилятору очень мало:

> Здесь может находиться любая строка.

Если реальное правило программы другое:

> Здесь может находиться только `idle`, `loading`, `success` или `error`,

лучше записать именно это:

```typescript
type Status =
  | "idle"
  | "loading"
  | "success"
  | "error";
```

Тип становится полезнее не потому, что он сложнее, а потому, что он **точнее отражает реальные данные**.

Это общий принцип TypeScript:

> **Хороший тип описывает не все теоретически возможные значения JavaScript, а те значения, которые допустимы по логике программы.**

### Практика

Вернись к проекту недели 10 и найди строковое значение, которое используется как ограниченный набор вариантов. В «Полке» это, например, `category` товара: в каталоге всего четыре категории — `"electronics"`, `"clothing"`, `"books"` и `"home"`. Состояния загрузки каталога появятся вместе с `fetch` в домашке.

- другая строка, для которой допустимо только несколько заранее известных значений.

Например, в проекте может встречаться:

```typescript
let status = "loading";
```

а позже:

```typescript
status = "success";
```

Если по логике программы набор значений ограничен, замени общий `string` на литеральный union:

```typescript

  | "loading"
```

Набор вариантов должен соответствовать реальной логике проекта, а не примеру из лонгрида.

После эксперимента верни корректное значение.


Например:

```typescript
type LoadStatus =

```

Если проекту для разных состояний нужны разные данные, попробуй пойти на шаг дальше.

Например:

Используй реальные поля и типы из собственного проекта.

Затем попробуй создать невозможную комбинацию. Например, состояние `success` без данных или `error` с полями успешного результата.

Запусти проверку и разбери сообщение компилятора.

Главный вопрос здесь:

> **Какую невозможную для приложения ситуацию теперь способен обнаружить TypeScript?**

Посмотри на интерфейсы, созданные в предыдущем разделе.

Есть ли две структуры, требования которых действительно объединяются в одном объекте?

Если да, попробуй составить тип через intersection:

```typescript
type Combined = First & Second;
```

Проверь, что значение должно содержать необходимые свойства обеих частей.

Если естественного примера в проекте нет, добавлять intersection только ради выполнения задания не требуется.

Выбери один union из проекта и найди место, где код работает с его значением.

Например:

```typescript
type Status =
  | "loading"
  | "success"
  | "error";

function renderStatus(status: Status) {
  // ...
}
```

Добавь проверки отдельных вариантов:

```typescript
function renderStatus(status: Status) {
  if (status === "loading") {
    // ...
  }

  if (status === "error") {
    // ...
  }
}
```

Наведи курсор на `status` внутри разных веток. Посмотри, меняется ли информация, которую показывает редактор.

Пока не нужно подробно разбирать механизм.

Зафиксируй наблюдение:

> После проверки конкретного значения TypeScript знает о переменной больше, чем до проверки.

### Если кратко

Не все данные удобно описывать одним базовым типом.

Иногда значение допускает **один из нескольких вариантов**:

```typescript
string | number
```

Или:

```typescript
"loading" | "success" | "error"
```

Для этого используется union.

Литеральные типы позволяют записать не просто «это строка», а **какие именно строки допустимы**. Благодаря этому опечатки и невозможные состояния становятся видимыми для компилятора.

Intersection выражает другую идею: значение должно удовлетворять требованиям нескольких типов одновременно.

`enum` тоже позволяет описывать ограниченный набор значений и часто встречается в существующем TypeScript-коде, но для многих простых случаев удобно использовать литеральные union-типы.

Главный вопрос остаётся прежним:

> **Что известно о реальных данных программы?**

Если известно, что статус может быть только одним из четырёх значений, тип `string` слишком широкий. Если состояние ошибки всегда содержит сообщение, а успешное состояние — данные, полезно записать и эту связь. Чем точнее модель соответствует реальным допустимым состояниям приложения, тем больше противоречий TypeScript способен обнаружить до запуска.

## 7. Сужение типов и `discriminated unions`

В предыдущем разделе появились union-типы:

```typescript
type Id = string | number;
```

Такая запись сообщает компилятору:

> Значение может быть строкой или числом.

Но она сразу создаёт новую проблему.

Представим функцию:

```typescript
function printId(id: string | number) {
  console.log(id.toUpperCase());
}
```

TypeScript сообщит об ошибке. У строки метод `toUpperCase()` есть, поэтому на первый взгляд операция кажется разумной. Но `id` может оказаться числом:

```typescript
printId(42);
```

А у числа такого метода нет. Компилятор не может выбрать удобный вариант из union-типа только потому, что конкретная строка кода рассчитана именно на него.

До дополнительной проверки его знание выглядит так:

```text
id → string | number
```

Чтобы выполнить строковую операцию, программе нужно сначала получить новую информацию о значении.

### Обычная JavaScript-проверка меняет знание TypeScript

Проверим тип значения:

```typescript
function printId(id: string | number) {
  if (typeof id === "string") {
    console.log(id.toUpperCase());
  }
}
```

Выражение

```typescript
typeof id === "string"
```

выполняется как обычный JavaScript-код.

Но TypeScript использует его ещё и во время статического анализа.

До `if`:

```text
id → string | number
```

Внутри ветки:

```text
id → string
```

Компилятор исключил вариант `number`, потому что условие уже доказало, что в эту ветку может попасть только строка.

Такое уточнение информации называется **сужением типа**, или narrowing.

> **Сужение типа — это ситуация, когда после проверки TypeScript может исключить часть возможных вариантов и точнее определить тип значения.**

### `typeof`: сужение примитивных типов

Для строк, чисел и логических значений часто достаточно уже знакомого JavaScript-оператора `typeof`.

Например:

```typescript
function formatValue(value: string | number) {
  if (typeof value === "number") {
    return value.toFixed(2);
  }

  return value.toUpperCase();
}
```

В начале функции:

```text
value → string | number
```

В первой ветке:

```text
value → number
```

После неё вариант `number` уже исключён, поэтому оставшийся код работает со строкой:

```text
value → string
```

Компилятор не просто проверяет отдельную строку. Он отслеживает поток выполнения программы.

Поэтому сужение может происходить и после раннего выхода:

```typescript
function printValue(value: string | null) {
  if (value === null) {
    return;
  }

  console.log(value.toUpperCase());
}
```

После

```typescript
if (value === null) {
  return;
}
```

вариант `null` больше не может попасть в оставшуюся часть функции.

Значит, там:

```text
value → string
```

### Проверка `null`

В разделе о базовых типах уже встречался пример:

```typescript
const savedName = localStorage.getItem("name");
```

Результат имеет два возможных варианта:

```text
string | null
```

Поэтому использовать его сразу как строку нельзя:

```typescript
const savedName = localStorage.getItem("name");

console.log(savedName.toUpperCase());
```

TypeScript предупреждает о реальной ситуации: ключ может отсутствовать.

Достаточно сначала проверить значение:

```typescript
const savedName = localStorage.getItem("name");

if (savedName !== null) {
  console.log(savedName.toUpperCase());
}
```

Теперь внутри ветки компилятор знает:

```text
savedName → string
```

Важно, что проверка полезна одновременно на двух уровнях. Во время выполнения она действительно защищает код от `null`. Во время статической проверки она даёт TypeScript новую информацию.

### `in`: проверка нужного свойства

С объектными union-типами удобно проверять наличие свойства.

Представим:

```typescript
type Result =
  | {
      data: string;
    }
  | {
      error: string;
    };
```

У значения одна из двух форм.

Такой код не пройдёт проверку:

```typescript
function printResult(result: Result) {
  console.log(result.data);
}
```

Почему? Потому что свойство `data` существует не во всех вариантах `Result`.

Можно сначала проверить его наличие:

```typescript
function printResult(result: Result) {
  if ("data" in result) {
    console.log(result.data);
  }
}
```

Внутри условия TypeScript понимает, что остался вариант объекта, в котором присутствует `data`.

А в другой ветке:

```typescript
function printResult(result: Result) {
  if ("data" in result) {
    console.log(result.data);
  } else {
    console.log(result.error);
  }
}
```

компилятор уже знает, что первый вариант исключён.

### `instanceof`: какой объект находится перед нами

Для объектов, которые действительно создаются определёнными конструкторами в runtime, можно использовать `instanceof`.

Например:

```typescript
function printDate(value: Date | string) {
  if (value instanceof Date) {
    console.log(value.getFullYear());
  } else {
    console.log(value.toUpperCase());
  }
}
```

До проверки:

```text
value → Date | string
```

В первой ветке:

```text
value → Date
```

Во второй:

```text
value → string
```

Особенно важным `instanceof` станет в следующем разделе при работе с DOM.

### Самый полезный случай: discriminated union

Вернёмся к состояниям интерфейса из предыдущего раздела.

Есть тип:

```typescript
type LoadState =
  | {
      status: "loading";
    }
  | {
      status: "success";
      data: string[];
    }
  | {
      status: "error";
      message: string;
    };
```

У всех вариантов есть общее поле:

```typescript
status
```

Но его значение различается:

```text
"loading"
"success"
"error"
```

Благодаря этому одному полю TypeScript может определить всю форму объекта.

Например:

```typescript
function renderState(state: LoadState) {
  if (state.status === "success") {
    console.log(state.data);
  }
}
```

До проверки:

```text
state →
loading
или success
или error
```

После

```typescript
state.status === "success"
```

остаётся только:

```text
state → {
  status: "success";
  data: string[];
}
```

Поэтому свойство `data` становится доступно.

Рассмотрим другой вариант:

```typescript
function renderState(state: LoadState) {
  if (state.status === "error") {
    console.log(state.message);
  }
}
```

В ветке `error` TypeScript знает, что существует `message`.

Но такой код:

```typescript
function renderState(state: LoadState) {
  if (state.status === "error") {
    console.log(state.data);
  }
}
```

не пройдёт проверку.

Это правильно: согласно нашей модели, состояние ошибки не содержит успешных данных.

Такой union называется **дискриминируемым**, или discriminated union.

В нём есть общее поле с литеральным значением:

```text
status
type
kind
```

или другое поле с аналогичным смыслом.

Именно по нему TypeScript различает варианты.

### Почему это лучше набора необязательных свойств

Можно было бы написать состояние так:

```typescript
interface LoadState {
  status: string;
  data?: string[];
  message?: string;
}
```

Но такая модель разрешает слишком много сочетаний.

Например:

```typescript
const state: LoadState = {
  status: "loading",
  data: ["готовые данные"],
  message: "Ошибка"
};
```

TypeScript не видит противоречия: все свойства формально допустимы.

Хотя для приложения такое состояние может быть бессмысленным.

Discriminated union записывает правила точнее:

```typescript
type LoadState =
  | {
      status: "loading";
    }
  | {
      status: "success";
      data: string[];
    }
  | {
      status: "error";
      message: string;
    };
```

Теперь невозможные комбинации становятся ошибками типов.

И это одна из самых полезных идей TypeScript:

> **Тип может описывать не только отдельные поля, но и связь между ними.**

### `switch` тоже сужает тип

Если состояний несколько, вместо цепочки `if` удобно использовать обычный `switch`:

```typescript
function renderState(state: LoadState) {
  switch (state.status) {
    case "loading":
      console.log("Загрузка...");
      break;

    case "success":
      console.log(state.data);
      break;

    case "error":
      console.log(state.message);
      break;
  }
}
```

В каждой ветке TypeScript знает свою форму `state`.

В `success` доступно:

```typescript
state.data
```

В `error`:

```typescript
state.message
```

А в `loading` ни одного из этих полей нет.

То есть обычное управление потоком JavaScript одновременно становится способом объяснить компилятору, с каким вариантом данных сейчас работает программа.

### Проверка, что обработаны все варианты

В разделе 4 было обещано, что `never` пригодится, когда нужно убедиться, что обработаны все варианты. Вот этот момент.

Добавим в `switch` ветку `default`:

```typescript
function renderState(state: LoadState): string {
  switch (state.status) {
    case "loading":
      return "Загрузка...";
    case "success":
      return `Получено элементов: ${state.data.length}`;
    case "error":
      return state.message;
    default: {
      const unhandled: never = state;
      return unhandled;
    }
  }
}
```

Если все три варианта обработаны, в `default` не может попасть ни одно значение: тип `state` там — `never`, и присваивание проходит проверку.

Теперь представим, что кто-то удалил ветку `case "error"` или добавил в `LoadState` новый вариант и забыл про `switch`. Компилятор сразу покажет, какой вариант остался необработанным:

```text
Type '{ status: "error"; message: string; }' is not assignable to type 'never'.
```

Такая проверка называется проверкой исчерпываемости (exhaustiveness check). Она превращает забытый вариант из бага, который всплывёт у пользователя, в ошибку компиляции.

### Сужение возвращает нас к `unknown`

В разделе 4 внешний результат был намеренно записан как:

```typescript
const raw: unknown = await response.json();
```

Такой тип честно говорит:

> Пока неизвестно, что именно пришло.

Теперь появляется инструмент, который позволяет постепенно превращать неизвестность в знание.

Для простого значения:

```typescript
const raw: unknown = await response.json();

if (typeof raw === "string") {
  console.log(raw.toUpperCase());
}
```

Или для объекта можно начать так:

```typescript
if (
  typeof raw === "object" &&
  raw !== null
) {
  // Теперь известно, что это объект.
}
```

Затем можно проверять его свойства:

```typescript
if (
  typeof raw === "object" &&
  raw !== null &&
  "message" in raw &&
  typeof raw.message === "string"
) {
  console.log(raw.message);
}
```

Каждая проверка добавляет новую информацию.

Получается последовательность:

```text
unknown
   ↓
это не null
   ↓
это объект
   ↓
у него есть message
   ↓
message — строка
   ↓
с этим значением уже можно безопасно работать
```

Именно поэтому `unknown` полезнее `any` для внешних данных.

`any` отключает проверку.

`unknown` заставляет программу **получить необходимое знание прежде, чем использовать значение**.

### Ошибка в `catch` тоже `unknown`

С тем же `unknown` ты столкнёшься при обработке ошибок. В `throw` в JavaScript можно передать что угодно, не только `Error`, поэтому при включённом `strict` переменная в `catch` имеет тип `unknown`:

```typescript
try {
  const response = await fetch("/api/products.json");
  const data: unknown = await response.json();
} catch (error) {
  console.log(error.message); // 'error' is of type 'unknown'.
}
```

Решение то же, что и для любых неизвестных данных, — сузить тип проверкой:

```typescript
} catch (error) {
  const message = error instanceof Error ? error.message : "Неизвестная ошибка";
  console.log(message);
}
```

### Проверка и утверждение — не одно и то же

Иногда TypeScript можно просто убедить:

```typescript
const value = raw as string;
```

После этого компилятор будет рассматривать `value` как строку.

Но в runtime ничего не проверилось.

Если в `raw` лежит число, запись

```typescript
as string
```

не превратит его в строку.

Поэтому важно различать

```text
typeof raw === "string"
```

и

```text
raw as string
```

Первое — настоящая runtime-проверка, которая даёт компилятору доказательство.

Второе — утверждение разработчика:

> «Считай это строкой, я беру ответственность на себя».

В основной работе проекта предпочтительнее получать знание через реальные проверки, а не заставлять компилятор замолчать утверждениями.

### Практика

1. Вернись к union-типу, который появился в предыдущем разделе. Найди код, который работает с этим значением.

До проверки наведи курсор на переменную и посмотри её тип.

Затем добавь условие проверки литерального типа. Снова наведи курсор на тип.

Ответь:

> Как изменился тип внутри ветки?

Попробуй обратиться там к данным успешного результата. Затем намеренно обратись к полю другого состояния, например к сообщению об ошибке.

Запусти:

```bash
npm run typecheck
```

Разбери сообщение компилятора:

- Какой вариант union остался после проверки?
...

- Какого свойства в этом варианте нет?
...

- Почему TypeScript может быть уверен в этом?
...

2. Теперь найди внешнее значение, которое в разделе 4 было оставлено как `unknown`. Добавь runtime-проверки, соответствующие его реальной структуре. Для примитивного значения используй `typeof`.

Для объекта последовательно проверь:

```text
это объект?
не null?
есть ли нужное свойство?
имеет ли оно ожидаемый тип?
```

После каждой проверки наблюдай в редакторе, как меняется тип.

Не заменяй `unknown` на `any` и не используй приведение типа только ради прохождения `typecheck`.

3. Найди в проекте значение, которое может быть `null`.

Например, это может быть результат

```typescript
localStorage.getItem(...)
```

или DOM-операции, которые подробно разберём в следующем разделе.

Попробуй использовать значение без проверки и прочитай сообщение TypeScript.

Затем добавь проверку:

```typescript
if (value !== null) {
  // работа со значением
}
```

Посмотри, какой тип компилятор показывает внутри условия.

В конце сформулируй:

> **Как обычная JavaScript-проверка изменила знание TypeScript о переменной?**

### Если кратко

Union сообщает компилятору:

> Значение может иметь несколько вариантов.

Сужение отвечает на следующий вопрос:

> Какой именно вариант возможен в этой точке программы?

Для этого TypeScript анализирует обычные проверки JavaScript:

```typescript
typeof value === "string"
```

```typescript
value !== null
```

```typescript
"data" in value
```

```typescript
value instanceof Date
```

а также проверки литеральных полей:

```typescript
state.status === "success"
```

Последний вариант особенно полезен для discriminated union: одно поле позволяет сузить тип всего объекта.

В результате TypeScript не просто запоминает объявленный тип переменной. Он отслеживает, **что программа уже успела доказать о значении**.

Это будет особенно заметно в DOM.

Браузер часто возвращает значения с широкими типами или с `null`, потому что заранее не может гарантировать, какой элемент существует на странице.

И в этом случае компилятор не придирается. Он снова требует от программы доказать то, что станет известно только во время выполнения.

## 8. Типизация DOM и перевод проекта на TypeScript

К этому моменту в проекте уже появились:

- типизированные функции;
- интерфейсы для основных данных;
- union-типы;
- проверки внешних значений;
- сужение типов.

Остаётся одна область, где TypeScript особенно часто начинает показывать ошибки после миграции JavaScript-проекта, — это работа с DOM. На первый взгляд такие ошибки могут казаться лишними.

Например:

```typescript
const button = document.querySelector(".button");

button.addEventListener("click", () => {
  console.log("Нажатие");
});
```

JavaScript-код выглядит совершенно привычно.

Но TypeScript может сообщить:

```text
'button' is possibly 'null'.
```

Почему?

### `querySelector` не обещает, что элемент существует

Метод:

```typescript
document.querySelector(".button")
```

ищет первый подходящий элемент на странице.

Но что произойдёт, если элемента с классом `.button` нет?

JavaScript вернёт:

```typescript
null
```

Поэтому честный тип результата выглядит примерно так:

```text
Element | null
```

Компилятор не знает содержимого страницы во время проверки TypeScript-файла.

Он не может доказать, что нужный элемент обязательно существует в runtime.

Поэтому такой код опасен:

```typescript
const button = document.querySelector(".button");

button.addEventListener("click", () => {});
```

Если `button === null`, попытка вызвать

```typescript
button.addEventListener(...)
```

завершится runtime-ошибкой.

Значит, TypeScript здесь не мешает работе.

Он обнаруживает реальную возможность.

### Проверяем, что элемент не `null`

Исправление может быть очень простым:

```typescript
const button = document.querySelector(".button");

if (button !== null) {
  button.addEventListener("click", () => {
    console.log("Нажатие");
  });
}
```

До проверки:

```text
button → Element | null
```

Внутри

```typescript
if (button !== null)
```

остаётся

```text
button → Element
```

Это уже знакомое сужение типа. Можно встретить и более короткую запись:

```typescript
if (button) {
  button.addEventListener("click", () => {});
}
```

В данном случае она тоже исключает `null`.

Но важно понимать не форму записи, а смысл:

> Программа проверила реальную возможность отсутствия элемента.

### Иногда `Element` всё ещё недостаточно

Представим поле формы:

```typescript
const input = document.querySelector(".name-input");
```

После проверки:

```typescript
if (input !== null) {
  console.log(input.value);
}
```

TypeScript может снова сообщить об ошибке.

Теперь проблема уже не в `null`.

Компилятор знает:

```text
input → Element
```

Но у общего `Element` нет свойства `value`.

Почему?

Потому что `.name-input` теоретически может находиться на любом HTML-элементе:

```html
<div class="name-input"></div>
```

```html
<input class="name-input">
```

```html
<section class="name-input"></section>
```

Свойство `value` характерно не для любого `Element`, а для конкретных элементов формы.

Опять возникает вопрос:

> **Что TypeScript знает и откуда?**

Он знает только то, что селектор вернул некоторый `Element`.

Из строки:

```typescript
".name-input"
```

компилятор не может доказать, что это именно `HTMLInputElement`.

### Проверить конкретный DOM-тип можно через `instanceof`

Здесь пригодится механизм из предыдущего раздела:

```typescript
const input = document.querySelector(".name-input");

if (input instanceof HTMLInputElement) {
  console.log(input.value);
}
```

В начале:

```text
input → Element | null
```

После

```typescript
input instanceof HTMLInputElement
```

компилятор знает:

```text
input → HTMLInputElement
```

Такая проверка одновременно решает две задачи.

Она подтверждает, что значение существует.

И подтверждает, что это именно тот вид DOM-элемента, у которого есть `value`.

Поэтому внутри можно безопасно использовать

```typescript
input.value
```

### С другими элементами работает та же логика

Например, для формы:

```typescript
const form = document.querySelector(".form");

if (form instanceof HTMLFormElement) {
  form.addEventListener("submit", (event) => {
    event.preventDefault();
  });
}
```

Для кнопки:

```typescript
const button = document.querySelector(".submit-button");

if (button instanceof HTMLButtonElement) {
  button.disabled = true;
}
```

Для текстового поля:

```typescript
const textarea = document.querySelector(".comment");

if (textarea instanceof HTMLTextAreaElement) {
  console.log(textarea.value);
}
```

Смысл не в том, чтобы выучить все DOM-классы.

Важно понимать механизм:

```text
querySelector
      ↓
Element | null
      ↓
runtime-проверка
      ↓
конкретный тип элемента
      ↓
доступ к его специфическим свойствам
```

### Почему TypeScript не может просто поверить HTML

Может возникнуть вопрос:

> Если элемент точно написан в `index.html`, почему TypeScript не знает об этом?

Потому что TypeScript анализирует TypeScript-код.

DOM формируется во время выполнения в браузере.

Кроме того, страница может измениться:

- элемент может быть удалён из HTML;
- класс может быть переименован;
- элемент может создаваться динамически;
- один и тот же скрипт может работать на разных страницах.

Поэтому утверждение:

> «Этот элемент обязательно существует»

не следует из одного TypeScript-файла.

Либо нужно подтвердить его runtime-проверкой, либо сознательно взять ответственность за такое предположение.

### Приведение типа — это обещание, а не проверка

Иногда встречается такой код:

```typescript
const input =
  document.querySelector(".name-input") as HTMLInputElement;
```

Теперь TypeScript разрешит:

```typescript
input.value;
```

Но что реально произошло? Браузер не проверил, что найден именно `HTMLInputElement`.

Приведение:

```typescript
as HTMLInputElement
```

не изменило объект.

И если селектор вернёт другой элемент или `null`, утверждение разработчика окажется неверным.

Это та же граница, которая уже встречалась с внешними данными:

```text
проверить значение
```

и

```text
пообещать компилятору тип
```

— разные действия.

Поэтому `as` не стоит использовать как универсальное средство удаления ошибок TypeScript.

Если ситуацию можно честно проверить:

```typescript
if (input instanceof HTMLInputElement)
```

такая проверка лучше отражает реальность программы.

У `querySelector` есть ещё одна запись, которую часто принимают за проверку:

```typescript
const input = document.querySelector<HTMLInputElement>(".name-input");
```

Тип `input` станет `HTMLInputElement | null`, и `input.value` после проверки на `null` скомпилируется. Но браузер при этом ничего не проверил: если по селектору найдётся `<div>`, код получит `div` под видом поля ввода. По смыслу это то же утверждение, что и `as HTMLInputElement`, только записанное короче. Исключение — поиск по имени тега: `document.querySelector("input")` TypeScript и без подсказки типизирует как `HTMLInputElement | null`, потому что тег однозначно определяет класс элемента.

### События тоже имеют типы

После миграции проекта TypeScript начинает знать больше и о событиях.

Например:

```typescript
const button = document.querySelector(".button");

if (button instanceof HTMLButtonElement) {
  button.addEventListener("click", (event) => {
    console.log(event);
  });
}
```

Редактор уже способен показать тип `event`.

Во многих случаях вручную аннотировать его не требуется: тип выводится из контекста вызова `addEventListener`.

Это хороший пример принципа из раздела 3:

> Если компилятор уже располагает достаточной информацией, дополнительная аннотация не обязательна.

DOM API знает, какое событие связано с соответствующим обработчиком, и TypeScript использует эту информацию.

### `event.target` и делегирование

Тип самого события TypeScript выводит, а вот `event.target` — нет. У него тип `EventTarget | null`: событие могло прийти от любого узла, и не обязательно от элемента.

Это особенно заметно при делегировании, когда один обработчик висит на контейнере, а клик приходит от вложенного элемента. В «Полке» так удобно обрабатывать кнопки «В корзину»:

```typescript
app.addEventListener("click", (event) => {
  if (!(event.target instanceof Element)) return;

  const button = event.target.closest("button[data-product-id]");
  if (!(button instanceof HTMLButtonElement)) return;

  console.log(button.dataset.productId);
});
```

Здесь две проверки, и обе нужны. Первая доказывает, что `target` — элемент и у него есть `closest`. Вторая нужна, потому что `closest` возвращает `Element | null`: если пользователь кликнул мимо кнопки, подходящего предка нет. Заодно `closest` решает практическую проблему: если внутри кнопки есть `<span>` или иконка, `event.target` будет этим вложенным элементом, а не кнопкой.

Обрати внимание и на `button.dataset.productId`: его тип `string | undefined`, потому что атрибута может не оказаться.

### Не нужно бороться с каждой ошибкой отдельно

При переводе готового JavaScript-проекта на TypeScript ошибок может появиться много.

Например:

```text
Object is possibly 'null'
```

```text
Property 'value' does not exist on type 'Element'
```

```text
Argument of type 'string' is not assignable to parameter of type ...
```

```text
Property '...' does not exist on type ...
```

Если смотреть на весь список сразу, кажется, что TypeScript только мешает миграции.

Гораздо полезнее разбирать ошибки по одной и задавать уже знакомые вопросы:

> Что компилятор знает о значении?

> Откуда он получил эту информацию?

> Какую операцию пытается выполнить код?

> Почему имеющейся информации для неё недостаточно?

> Действительно ли ситуация невозможна в runtime — или код пока просто не обрабатывает её?

Тогда длинное сообщение компилятора превращается из препятствия в объяснение расхождения между моделью и программой.

### Как читать ошибку TypeScript

Представим:

```typescript
const input = document.querySelector(".name");

console.log(input.value);
```

Ошибок здесь может быть сразу несколько.

Первая связана с `null`.

Компилятор сообщает примерно:

```text
'input' is possibly 'null'.
```

Это означает:

```text
ожидание кода:
элемент существует

знание компилятора:
Element | null
```

После проверки:

```typescript
if (input !== null) {
  console.log(input.value);
}
```

одна проблема исчезает.

Но может остаться другая:

```text
Property 'value' does not exist on type 'Element'
```

Теперь:

```text
ожидание кода:
элемент имеет value

знание компилятора:
это только Element
```

Тогда нужна новая информация:

```typescript
if (input instanceof HTMLInputElement) {
  console.log(input.value);
}
```

То есть одна строка исходного кода могла скрывать сразу две договорённости:

```text
элемент точно существует
+
это точно input
```

TypeScript заставляет записать обе честно.

### Почему DOM хорошо показывает смысл `strict`

Без строгих проверок часть таких проблем легко остаётся незамеченной.

Но при

```json
{
  "compilerOptions": {
    "strict": true
  }
}
```

возможность `null` становится частью типа.

Это не означает, что TypeScript требует бессмысленной перестраховки.

Вызов:

```typescript
document.querySelector(...)
```

действительно способен вернуть `null`.

Поэтому строгий режим вынуждает код учитывать реальное поведение браузера.

Именно это делает `strict` полезным режимом разработки, а не дополнительным испытанием после написания программы.

### Практика

Теперь все изученные механизмы нужно собрать в одном месте.

Цель итоговой практики — не написать новый учебный пример, а довести перевод проекта недели 10 до состояния, в котором отдельная проверка типов проходит успешно.

Шаг 1. Проверь основные структуры данных

Просмотри данные, с которыми работает приложение.
Основные сущности должны иметь осмысленные типы или интерфейсы.

Проверь:

- все ли обязательные свойства записаны;
- соответствуют ли типы реальным значениям;
- не скрыта ли возможность `null` или другого варианта;
- нет ли широкого `string` там, где в программе существует небольшой фиксированный набор значений.

Шаг 2. Проверь функции

Просмотри основные функции проекта.

Для параметров должно быть понятно, что функция получает.

Для возвращаемого значения — что функция отдаёт.

Там, где TypeScript уверенно выводит локальные типы самостоятельно, не нужно добавлять лишние аннотации.

Главный вопрос:

> Есть ли в функции значение, о типе которого компилятору приходится только догадываться?

Если есть, найди источник неопределённости и опиши его честнее.

Шаг 3. Проверь `any`

Найди все места, где в проекте появился:

```typescript
any
```

Для каждого задай вопрос:

> Почему здесь отключена проверка?

Если ответ:

> «Иначе TypeScript показывал ошибку»,

это не объяснение.

Вернись к самой ошибке и разбери её.

Внешние данные, тип которых ещё не подтверждён, по возможности оставь `unknown` и добавь необходимые проверки.

Шаг 4. Проверь состояния приложения

Если проект использует строки вроде

```typescript
"loading"
"success"
"error"
```

или другие ограниченные наборы значений, проверь, не стоит ли заменить общий string на литеральный union.

Если разные состояния содержат разные данные, подумай, можно ли выразить их через discriminated union.

Например:

```typescript
type State =
  | {
      status: "loading";
    }
  | {
      status: "success";
      data: Task[];
    }
  | {
      status: "error";
      message: string;
    };
```

Не усложняй модель ради самого TypeScript. Такая структура нужна только там, где она действительно соответствует логике приложения.

Шаг 5. Типизируй работу с DOM

Теперь найди все вызовы:

```typescript
document.querySelector(...)
```

и похожие операции.

Для каждого посмотри, какой тип показывает редактор.

Если значение может быть `null`, не скрывай это.

Добавь проверку:

```typescript
const element = document.querySelector(".element");

if (element !== null) {
  // ...
}
```

Если код использует свойства конкретного HTML-элемента:

```typescript
value
checked
disabled
```

проверь конкретный тип через `instanceof`.

Например:

```typescript
const input = document.querySelector(".task-input");

if (input instanceof HTMLInputElement) {
  console.log(input.value);
}
```

Не копируй этот тип автоматически. Выбери DOM-класс, соответствующий реальному элементу проекта. В «Полке» это `#app` и `.nav__cart-count` (им достаточно `HTMLElement`), поле `#search-input` (`HTMLInputElement`) и кнопки «В корзину» (`HTMLButtonElement`).

Шаг 6. Разбери ошибки, а не скрывай их

Запусти:

```bash
npm run typecheck
```

Выбери три-четыре реальные ошибки, которые появились при миграции.

Для каждой заполни короткий разбор:

```text
Что сообщает компилятор?
...

Какой тип он видит?
...

Какого типа или свойства ожидает код?
...

Откуда TypeScript получил эту информацию?
...

Прав ли компилятор с точки зрения возможного runtime?
...

Как исправить причину, а не только сообщение?
...
```

Не исправляй ошибки добавлением `any` только ради зелёной проверки.

И не используй приведение типов только потому, что оно короче.

Если требуется `as`, должно быть понятно, какое предположение о runtime берёт на себя разработчик.

Шаг 7. Сравни сборку и проверку типов

Оставь в проекте намеренную ошибку типов.

Например, временно передай неправильный аргумент в уже типизированную функцию.

Запусти:

```bash
npm run build
```

А затем:

```bash
npm run typecheck
```

Сравни результат.

Зафиксируй:

> Проверка сборки и проверка типов решают разные задачи.

Если Vite успешно собирает проект, это ещё не означает, что `tsc` не видит ошибок типов.

После эксперимента исправь намеренную ошибку.

Шаг 8. Добейся чистой проверки

Финальная цель:

```bash
npm run typecheck
```

завершается без ошибок.

Но сам по себе зелёный результат ещё не означает, что задача выполнена хорошо.

Перед завершением проверь, не удалось ли получить его ценой повсеместных `any` и `as` или удаления полезных типов.

Чистая проверка должна означать:

> Компилятор получил достаточно честной информации о данных, чтобы не находить противоречий.

### Если кратко

DOM-элементы приходят в программу из внешнего для компилятора мира, поэтому TypeScript честно включает `null` в их типы.

Проверка элемента перед использованием — не борьба с компилятором, а учёт реального поведения браузера.

Приведение через `as` — обещание разработчика, а не проверка: оно уместно только там, где программа уже гарантировала тип сама.

Ошибку TypeScript полезно читать как описание противоречия между двумя частями программы, а не как препятствие, которое нужно как можно быстрее убрать.

## ★ Глубже

Проект переведён, проверка типов проходит. Дальше начинается то, с чем обычно сталкиваются, когда типов в проекте становится много.
Ни один из следующих инструментов не нужен для выполнения основной практики. Это скорее ориентиры: что встретится дальше в реальных проектах и почему некоторые решения вокруг TypeScript устроены именно так.

<a id="раз-компилятор-не-проверяет-ответ-сервера-кто-должен-неужели-писать-if-для-каждого-поля-вручную"></a>

### ❓ Раз компилятор не проверяет ответ сервера — кто должен? Неужели писать `if` для каждого поля вручную?

Можно и вручную.

Если данные приходят как `unknown`, программа может последовательно проверить их:

```typescript
const raw: unknown = await response.json();

if (
  typeof raw === "object" &&
  raw !== null &&
  "id" in raw &&
  "name" in raw &&
  typeof raw.id === "number" &&
  typeof raw.name === "string"
) {
  // Здесь о данных уже известно гораздо больше.
}
```

Такой подход работает и хорошо показывает принцип: TypeScript сам по себе не проверяет реальный JSON, поэтому проверка должна произойти в runtime.

Проблема появляется, когда таких объектов становится много.

Представим, что приложение получает пользователя, список товаров, настройки, комментарии, заказы. Для каждого ответа нужно проверить несколько полей, а иногда ещё вложенные объекты и массивы.

Тогда ручные проверки начинают повторяться.

В реальных проектах для этого часто используют библиотеки **валидации схем**. Один из известных примеров — Zod.

Идея выглядит примерно так:

```text
неизвестные данные
        ↓
схема
        ↓
runtime-проверка
        ↓
проверенное значение
        ↓
дальше приложение работает уже с известным типом
```

Смысл здесь не в конкретной библиотеке.

Главный принцип называется **валидацией на границе**: внешние данные проверяются в момент входа в приложение, а после успешной проверки остальная часть программы уже работает с ними как с доверенными.

Такой вопрос обычно возникает довольно быстро — например, когда сервер изменяет формат ответа, а клиент продолжает ожидать старую структуру.

Если захочется посмотреть глубже, полезные точки входа — [документация Zod](https://zod.dev) и идея **parse, don’t validate** [из одноимённой статьи Алексис Кинг](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/): не разносить проверки по всему приложению, а превращать неизвестные входные данные в проверенную внутреннюю модель как можно раньше.

<a id="компилятор-не-верит-типу-поэтому-можно-просто-написать-as-user"></a>

### ❓ Компилятор не верит типу, поэтому можно просто написать `as User`?

Можно:

```typescript
const user = raw as User;
```

Но важно понимать, что произошло.

`as User` не проверяет объект.

Не добавляет ему недостающие свойства.

Не запускает никакой код в браузере.

Такая запись означает примерно следующее:

> «Компилятор, считай это значение `User`. Здесь ответственность берёт на себя разработчик».

Если предположение оказалось неверным, TypeScript уже не поможет.

Например:

```typescript
interface User {
  name: string;
}

const raw = {
  message: "User not found"
};

const user = raw as User;

console.log(user.name.toUpperCase());
```

Приведение типа не создаст `name`.

Ошибка просто переместится из этапа проверки в runtime.

Поэтому `as` полезно воспринимать не как способ «исправить TypeScript», а как **обещание компилятору**.

Из этого следует хорошее практическое правило:

> Если проблему можно решить настоящей проверкой данных, проверка обычно надёжнее приведения типа.

Особенно подозрительно выглядит ситуация, когда `as` добавляется только ради исчезновения красного подчёркивания.

Есть ещё оператор `satisfies`.

Например:

```typescript
type Config = {
  apiUrl: string;
  retries: number;
};

const config = {
  apiUrl: "/api",
  retries: 3
} satisfies Config;
```

Он решает немного другую задачу: TypeScript проверяет, соответствует ли значение указанному типу, но при этом сохраняет более конкретную информацию о самом значении.

На основной неделе `satisfies` не нужен. Но он часто становится полезным позже, когда появляется желание проверить объект на соответствие контракту, не заставляя компилятор забывать всё, что он уже о нём знает.

Подробнее стоит смотреть [раздел TypeScript Handbook про type assertions](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions) и описание оператора `satisfies` [в заметках к TypeScript 4.9](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator).

<a id="почему-enum-часто-не-советуют-использовать-хотя-он-есть-в-typescript"></a>

### ❓ Почему `enum` часто не советуют использовать, хотя он есть в TypeScript?

Потому что `enum` немного выбивается из привычной модели, которая использовалась на протяжении всей темы.

Обычный тип:

```typescript
type Status =
  | "idle"
  | "loading"
  | "success";
```

нужен компилятору для проверки, а затем исчезает.

В готовом JavaScript самого `Status` уже не будет.

С `enum` ситуация другая:

```typescript
enum Status {
  Idle,
  Loading,
  Success
}
```

Как видно в разделе 6, такая конструкция порождает реальный JavaScript-код.

То есть `enum` — не только описание для компилятора, но ещё и runtime-конструкция.

Из-за этого он отличается от большинства изученных типов.

Кроме того, у числовых `enum` есть особенности, которые не видны по объявлению. Объект работает в обе стороны: `Status.Idle` даёт `0`, а `Status[0]` — строку `"Idle"`. А до TypeScript 5.0 переменной числового `enum` можно было присвоить любое число, например `42`, и компилятор молчал.

Есть и более свежая причина. Node.js умеет запускать `.ts`-файлы, просто стирая типы, но `enum` стереть нельзя: на нём Node остановится с `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`. Ту же границу проверяет флаг компилятора `erasableSyntaxOnly`. Ты вспомнишь об этом, когда впервые запустишь TypeScript-скрипт прямо в Node и получишь ошибку на строке, которая в проекте с Vite работала.

Поэтому для небольшого закрытого набора состояний часто выбирают более простую модель:

```typescript
type Status =
  | "idle"
  | "loading"
  | "success"
  | "error";
```

Она хорошо сочетается с union-типами, сужением и discriminated union.

Это не означает, что `enum` «неправильный» или что его нужно избегать в любом проекте.

Он существует в языке и встречается в кодовых базах, поэтому важно уметь его читать.

Но использовать `enum` автоматически каждый раз, когда появился ограниченный набор значений, тоже не обязательно.

Если тема заинтересовала, дальше можно посмотреть [раздел TypeScript Handbook про `enum`](https://www.typescriptlang.org/docs/handbook/enums.html) и [описание флага `erasableSyntaxOnly`](https://www.typescriptlang.org/tsconfig/#erasableSyntaxOnly) — в нём перечислены конструкции TypeScript, которые нельзя просто удалить при преобразовании в JavaScript.

<a id="после-установки-библиотеки-редактор-сразу-показывает-типы-откуда-typescript-вообще-их-знает"></a>

### ❓ После установки библиотеки редактор сразу показывает типы. Откуда TypeScript вообще их знает?

Из **файлов деклараций**.

Обычно они имеют расширение:

```text
.d.ts
```

Такой файл описывает не реализацию библиотеки, а её типовой интерфейс.

Условно библиотека содержит JavaScript-функцию:

```javascript
export function formatDate(value) {
  // реализация
}
```

А декларация может сообщить TypeScript:

```typescript
export function formatDate(value: Date): string;
```

Теперь компилятор знает:

```text
что принимает функция
что возвращает функция
что библиотека экспортирует
```

хотя сама реализация может находиться в обычном JavaScript.

Многие современные библиотеки поставляют декларации прямо внутри npm-пакета.

Но так было не всегда.

Для большого количества JavaScript-библиотек типы поддерживаются отдельно сообществом. Тогда можно встретить пакет:

```text
@types/имя-библиотеки
```

Например, сама библиотека содержит JavaScript, а пакет из пространства `@types` добавляет информацию, необходимую TypeScript.

Эти декларации собираются в проекте **DefinitelyTyped**.

Связь с уже знакомыми инструментами здесь довольно прямая: как и другие инструменты разработки, пакеты типов обычно устанавливаются как зависимости для разработки.

Иногда библиотека вообще не предоставляет подходящих типов.

Тогда приходится выбирать: найти сторонние декларации, описать необходимую часть самостоятельно или временно работать с менее точным типом.

В реальном проекте этот вопрос всплывает в тот момент, когда после установки пакета TypeScript сообщает, что не может найти для него декларации.

Если понадобится разбираться глубже, точка входа — [раздел TypeScript Handbook про **Declaration Files**](https://www.typescriptlang.org/docs/handbook/declaration-files/introduction.html).

<a id="чем-дальше-тем-больше-кажется-что-типы-это-отдельный-язык-внутри-typescript-так-и-есть"></a>

### ❓ Чем дальше, тем больше кажется, что типы — это отдельный язык внутри TypeScript. Так и есть?

В определённом смысле — да.

На этой неделе типы в основном **описывались**:

```typescript
interface User {
  id: number;
  name: string;
}
```

```typescript
type Status =
  | "loading"
  | "success"
  | "error";
```

Но система типов TypeScript умеет гораздо больше.

Можно строить один тип на основе другого.

Можно описать правило:

```text
«возьми тип некоторого значения
и построй из него новый тип»
```

Можно получать информацию о типах функций, преобразовывать свойства объектов и создавать повторно используемые конструкции для целых групп типов.

То есть на более продвинутом уровне типы действительно начинают напоминать небольшой язык программирования, который работает не в браузере, а внутри компилятора во время проверки.

На этой неделе идти туда не требуется.

Сейчас важнее уверенно различать:

```text
что известно компилятору
откуда он это знает
что проверяется до запуска
что остаётся проверить в runtime
```

А следующий естественный вопрос появится сам.

Представим, что в проекте есть:

```typescript
type ApiUser = ...
type ApiTask = ...
type ApiProduct = ...
```

и для каждого снова приходится описывать похожие операции над типами.

В какой-то момент возникает ощущение:

> «Мы снова пишем одно и то же. Нельзя ли один раз описать правило, по которому строится нужный тип?»

Можно.

Именно отсюда начинается следующая тема — **generics и вычисление типов**.

Если захочется заглянуть вперёд, в TypeScript Handbook можно посмотреть [разделы про generics](https://www.typescriptlang.org/docs/handbook/2/generics.html) и [utility types](https://www.typescriptlang.org/docs/handbook/utility-types.html). Но они не нужны для текущего проекта и не входят в требования этой недели.


## Что дальше

«Полка» теперь живёт на TypeScript, и на неделе 12 в ней появится повторяющийся код вокруг типов: похожие загрузки, похожие проверки, похожие состояния для разных данных. Дженерики и утилитарные типы позволят описать такие правила один раз и переиспользовать их, не теряя проверки.
