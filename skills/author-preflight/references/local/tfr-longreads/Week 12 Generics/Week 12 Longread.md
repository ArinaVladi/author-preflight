# TypeScript: дженерики и утилитарные типы

Ты уже умеешь описывать типы для объектов, функций и ответов API, и компилятор ловит
ошибки раньше, чем они попадут в рантайм. Но стоит написать так пару десятков функций
и типов для настоящего проекта, и код начинает повторяться. Функция, которая забирает
с сервера товар, и функция, которая забирает заказ, различаются одной строкой адреса.
Всё остальное в них совпадает до символа. С типами история та же, но дублируется уже
не логика, а структура. Один интерфейс описывает ответ с карточкой товара, другой —
со страницей каталога, хотя устроены оба одинаково. Третий нужен форме редактирования
и отличается от `Product` только тем, что все поля в нём необязательные.

В обычном коде ты уберёшь такой повтор не задумываясь — вынесешь в функцию или
переменную. С типами работает тот же приём, потому что типы — тоже язык со своими
функциями, условиями и перебором полей. Повторы в логике убирают дженерики, которые
дают написать её один раз и подставить конкретный тип при вызове. Повторы в структуре
снимают утилитарные типы, которые выводят новый тип из старого вместо ручного
копирования. Оба механизма разберём на магазине — от первой функции с одним
параметром типа до типобезопасной обёртки над `fetch`, которая соберёт всё
разобранное вместе.

**Если ты освоишь эту тему:**

- научишься писать функции и структуры данных, которые работают с разными типами
  без дублирования кода;
- сможешь ограничивать параметр типа так, чтобы TypeScript проверял именно то,
  что нужно;
- перестанешь описывать похожие типы вручную — вместо этого будешь выводить их
  из уже существующих через встроенные утилитарные типы;
- научишься безопасно рефакторить код, потому что при смене базового типа компилятор
  сам покажет все производные места, которые нужно обновить;
- поймёшь, что `Partial`, `Omit` и подобные типы — не магия компилятора, а обычные
  типы, которые можно прочитать и написать самостоятельно;
- сможешь читать сообщения компилятора об ошибках в дженериках, не пугаясь их длины.

**Тебе нужно изучить:**

- зачем нужны дженерики и какую проблему дублирования они решают;
- как объявлять дженерик-функции и как TypeScript выводит параметр типа сам;
- как ограничивать параметр типа через `extends` и что дают операторы `typeof`,
  `keyof` и индексированный доступ `T[K]`;
- как параметризовать интерфейсы, типы и классы дженериками;
- как применять встроенные утилитарные типы для преобразования существующих типов;
- как устроены mapped types и как через них собраны `Partial`, `Readonly` и
  подобные;
- что такое conditional types и `infer` и как на них построены `ReturnType`
  и `Awaited`;
- как задавать шаблонные строковые типы через template literal types;
- как типизировать generic-обёртку над `fetch` и не превратить её в замаскированный
  `as`.

Система типов TypeScript устроена как маленький язык программирования: он
выполняется не в рантайме, а во время проверки типов, до запуска кода. У части
механизмов дальше есть прямой аналог в обычном коде, который ты уже писал(а). Это не
совпадение. Перебор ключей, условие и деструктуризация в типах устроены так же, как
в JavaScript.

## Перед началом попробуем угадать ответы

Прежде чем читать дальше, прикинь ответы на четыре вопроса — по ходу лонгрида вернёмся к
каждому.

1. `getProduct` и `getOrder` различаются только адресом и типом ответа. Как свести
   их в одну функцию, не потеряв проверку полей и не скатившись в `any`?
2. Для формы редактирования нужен тип, который повторяет `Product`, но все поля в нём необязательные. Написать второй интерфейс руками? А что случится
   с ним, когда в `Product` добавят новое поле?
3. `Partial<T>` — встроенный тип. Он вшит в компилятор как магия или это обычный
   тип, который ты сможешь написать самостоятельно?
4. У тебя есть функция `getProduct`, которая возвращает товар с сервера. Можно ли
   получить тип того, что она возвращает, не описывая его руками второй раз?

## 1. Дженерики: параметр типа

### Зачем нужен дженерик

В магазине уже есть несколько функций, которые ходят на сервер за данными:

```ts
interface Product {
  id: number;
  name: string;
  price: number;
  category: "electronics" | "clothing" | "books";
}

interface Order {
  id: number;
  customerId: number;
  status: "placed" | "paid" | "shipped" | "delivered";
}

async function getProduct(id: number): Promise<Product> {
  const response = await fetch(`/api/products/${id}`);
  return response.json();
}

async function getOrder(id: number): Promise<Order> {
  const response = await fetch(`/api/orders/${id}`);
  return response.json();
}
```

Тело у обеих одно и то же — сходить по адресу и разобрать JSON. Различаются только
адрес и то, что функция обещает вернуть. Появятся покупатели, отзывы и промокоды, и
таких функций, отличающихся одной строкой, наберётся с десяток.

Напрашивается вынести адрес в параметр:

```ts
async function fetchJson(url: string) {
  const response = await fetch(url);
  return response.json();
}

const product = await fetchJson("/api/products/1");
console.log(product.pirce); // опечатка, но компилятор молчит
```

Дублирование ушло, а вместе с ним ушла и проверка типов. `response.json()` объявлен как
`Promise<any>`, поэтому `product` получает тип `any`, и обращение к любому полю
компилятор пропускает молча. Опечатка `pirce` доживёт до рантайма и проявится как
`undefined` в вёрстке.

Перечислить возможные ответы юнионом — `Promise<Product | Order>` — тоже не выход.
Список придётся расширять под каждую новую сущность. Да и на месте вызова результат
придётся сужать вручную, потому что компилятор не знает, какая из веток пришла.

Нужен способ сказать, что функция одна, но в каждом вызове возвращает свой тип. Для
этого в TypeScript есть дженерики.

> **Дженерик** (generic) — параметр типа, который позволяет функции, интерфейсу или
> типу работать с разными типами данных, оставаясь при этом типобезопасным. TypeScript
> продолжает проверять соответствие типов, просто откладывает выбор конкретного типа
> до момента использования.

```ts
async function fetchJson<T>(url: string): Promise<T> {
  const response = await fetch(url);
  return response.json();
}

const product = await fetchJson<Product>("/api/products/1"); // Product
const order = await fetchJson<Order>("/api/orders/17");      // Order

console.log(product.pirce);
// Error: Property 'pirce' does not exist on type 'Product'
```

`<T>` после имени функции объявляет параметр типа с именем `T`. Дальше `T` используется
в сигнатуре так же, как обычный тип, и `Promise<T>` означает «обещание того типа,
который назовут при вызове». Отличие от обычного параметра функции в том, что
параметром здесь выступает не значение, а сам тип:

```ts
fetchJson("/api/products/1");          // обычный аргумент — значение
fetchJson<Product>("/api/products/1"); // аргумент типа — Product
```

`T` — это просто имя-заполнитель, вместо него мог быть любой другой идентификатор. По
соглашению для одного параметра типа обычно используют `T` (от Type), а если параметров
несколько — короткие заглавные буквы по алфавиту: `T`, `U`, `K`, `V`.

Одну проблему эта версия не решает, и о ней стоит помнить с самого начала. `T` держится
на честном слове вызывающего, потому что проверить, действительно ли сервер прислал
`Product`, здесь некому. Вернёмся к этому в конце лонгрида и соберём версию, которая
берёт тип не из обещания, а из фактической проверки данных.

### Вывод типа параметра

В `fetchJson` тип приходится указывать явно, потому что выводить его не из чего — на
входе только строка. Чаще бывает наоборот, и тогда TypeScript определяет `T` сам.
Витрина режет на страницы и каталог, и отзывы, и историю заказов:

```ts
function getPage<T>(items: T[], page: number, perPage: number): T[] {
  return items.slice((page - 1) * perPage, page * perPage);
}

const catalogPage = getPage(products, 1, 20); // Product[]
const orderPage = getPage(orders, 1, 10);     // Order[]
```

Указывать `<Product>` при вызове не нужно. TypeScript увидел на входе `Product[]`
и вывел из него `T`, а вместе с ним и тип результата. Явная запись
`getPage<Product>(products, 1, 20)` тоже допустима, но избыточна, и на практике её
пишут редко — в основном там, где вывод невозможен, как в `fetchJson`.

### Когда дженерик не нужен

Если функция или тип всегда работают с одним и тем же конкретным типом, оставь
конкретный тип. Дженерик оправдан, когда одна и та же логика должна работать с
разными типами, сохраняя проверку. Если `T` используется в сигнатуре ровно один
раз и нигде не связывает вход с выходом, вероятно, дженерик здесь не нужен —
подойдёт обычный тип или `unknown`.

### Практика

Напиши две generic-функции, которые пригодятся при работе с ответами
сервера. `withFallback<T>(value: T | null | undefined, fallback: T): T` подставляет
значение по умолчанию, когда поле не пришло. `toArray<T>(value: T | T[]): T[]`
приводит к массиву ответ, в котором сервер отдаёт то одиночный объект, то список.
Для каждой объясни, что перестанет проверять компилятор, если заменить `T` на `any`.

### Если кратко

Дженерик — это параметр типа: функция остаётся одной, а тип результата подставляется при вызове. `fetchJson<T>` убирает дублирование и не теряет проверку полей, в отличие от варианта с `any`. Если тип можно вывести из аргументов, как в `getPage`, указывать `<T>` явно не нужно. При этом `T` в `fetchJson` держится на обещании вызывающего: проверить, что прислал сервер, здесь некому. Если функция всегда работает с одним конкретным типом, дженерик не нужен.

## 2. Ограничения дженериков: extends и keyof

### Ограничение через extends

Без ограничений `T` может быть каким угодно типом — а это иногда слишком широко.
Корзина хранит только идентификаторы товаров и количество, а карточки приходят
отдельным запросом. Чтобы отрисовать строку корзины, по каждому `productId` нужно
найти товар, и перебирать ради этого весь каталог на каждую строку незачем. Массив
один раз превращают в `Map` по идентификатору:

```ts
function indexById<T>(items: T[]): Map<number, T> {
  return new Map(items.map((item) => [item.id, item]));
  // Error: Property 'id' does not exist on type 'T'
}
```

TypeScript не пропустит этот код. `T` может быть чем угодно, включая строку или число,
у которых никакого `id` нет. Нужно явно сообщить, что `T` — не любой тип, а тип, у
которого точно есть числовой `id`.

> **Ограничение дженерика** (`extends`) сужает набор типов, которые можно подставить
> вместо параметра типа, до тех, что соответствуют указанной форме.

```ts
function indexById<T extends { id: number }>(items: T[]): Map<number, T> {
  return new Map(items.map((item) => [item.id, item]));
}

const productsById = indexById(products); // Map<number, Product>
const ordersById = indexById(orders);     // Map<number, Order>

productsById.get(1)?.price; // OK — в Map лежит полноценный Product
indexById([1, 2, 3]);       // Error: number не совместим с { id: number }
```

Ограничение сузило `T`, но не стёрло его, и в этом весь смысл. Внутри функции доступен
`id`, потому что его наличие гарантировано. Снаружи в `Map` лежит по-прежнему `Product`
со всеми полями, поэтому `price` читается без приведений. Если бы вместо дженерика
параметр был объявлен как `{ id: number }[]`, функция тоже скомпилировалась бы, но
вернула бы контейнер с безликими объектами и `price` на выходе потерялся бы.

`extends` здесь работает не как наследование интерфейсов, а как условие, по которому
в `T` можно подставить только совместимое с `{ id: number }`. По сути, это та же
проверка аргумента на входе, только проверяется не значение, а тип. Обычная функция
отказывается работать, если ей передали не то. Дженерик так же отказывается
компилироваться, если `T` не подходит под ограничение.

**Когда extends лишний.** Если внутри дженерика `T` используется только как есть —
принял и вернул, ничего не читая из его полей, — ограничение не нужно, как в `getPage`
из предыдущего раздела. Ограничение нужно ровно тогда, когда телу функции требуется
что-то конкретное от `T`.

Ограничение может требовать не только конкретной формы объекта, но и того, чтобы тип
оказался одним из допустимых ключей другого типа, и для этого нужен отдельный
оператор.

### Ключи типа: keyof

Витрина сортируется по цене, названию и остатку на складе. Писать три почти одинаковые
функции не хочется, поэтому имя поля становится аргументом. Но если объявить его просто
как `string`, опечатка снова доживёт до рантайма, а значит, набор допустимых имён нужно
перечислить:

```ts
type ProductKeys = "id" | "name" | "price" | "category"; // дублирует поля Product вручную
```

Если в `Product` добавится поле, про `ProductKeys` придётся вспомнить отдельно.

> **`keyof`** — оператор, который извлекает из типа объединение всех его ключей
> в виде строковых литералов.

```ts
type ProductKeys = keyof Product;
// "id" | "name" | "price" | "category"

function sortProducts(products: Product[], field: ProductKeys): Product[] {
  return [...products].sort((a, b) => (a[field] > b[field] ? 1 : -1));
}

sortProducts(products, "price"); // OK
sortProducts(products, "prise"); // Error: Argument of type '"prise"' is not assignable to parameter of type 'ProductKeys'
```

`keyof Product` пересчитывается автоматически при изменении `Product` — добавил поле,
оно тут же появилось в `ProductKeys`, обновлять ничего вручную не нужно.

### Если кратко

Ограничение `T extends { id: number }` сужает набор допустимых типов, но не стирает `T`: внутри функции доступен `id`, а снаружи сохраняется весь `Product`. Без ограничения TypeScript не даст обратиться к полю, которого у произвольного `T` может не быть. `extends` здесь работает как условие на тип, а не как наследование. Если тело функции ничего не читает из `T`, ограничение не нужно. Оператор `keyof` собирает допустимые имена полей автоматически, поэтому `ProductKeys` обновляется вслед за `Product`.

## 3. Generic интерфейсы и классы

### Generic интерфейсы и типы

Дженериками можно параметризовать не только функции, но и `interface` с `type` — это
особенно полезно для переиспользуемых структур вроде обёртки над ответом API. Через
API магазина проходит и отдельная карточка, и страница каталога. Описывать обёртку
для каждого случая заново незачем.

```ts
interface ApiResponse<T> {
  data: T;
  status: number;
  timestamp: number;
}

type ProductResponse = ApiResponse<Product>;
type CatalogResponse = ApiResponse<Product[]>;

const response: ProductResponse = {
  data: product,
  status: 200,
  timestamp: Date.now(),
};
```

Один интерфейс `ApiResponse<T>` описывает форму любого ответа сервера — независимо
от того, что именно приходит в `data`. Не нужно заводить отдельный `ProductApiResponse`,
`OrderApiResponse` и так далее — достаточно подставить нужный тип в `T`.

### Значения по умолчанию для параметров типа

У `ApiResponse` есть частный случай — эндпоинт вроде `/api/ping`, у которого нет
осмысленных данных в ответе вообще. Городить для него отдельный тип не хочется —
удобнее дать параметру типа значение по умолчанию, которое подставится, если явно
ничего не указали.

```ts
interface ApiResponse<T = unknown> {
  data: T;
  status: number;
  timestamp: number;
}

function fetchPing(): ApiResponse {
  return { data: null, status: 200, timestamp: Date.now() };
  // T здесь unknown — тип по умолчанию
}

function fetchCatalog(): ApiResponse<Product[]> {
  return { data: [], status: 200, timestamp: Date.now() };
  // T здесь явно указан — Product[]
}
```

Значение по умолчанию делает дженерик необязательным при использовании: `ApiResponse`
без параметра всё ещё валиден, просто `T` в нём равен `unknown`.

Тот же приём с параметризацией пригождается и в обычном браузерном коде. Корзина
переживает перезагрузку страницы, потому что лежит в `localStorage`, а обратно оттуда
приходит строка, которую нужно вернуть уже типизированной:

```ts
interface OrderItem {
  productId: number;
  quantity: number;
}

function createStorageItem<T>(key: string, initialValue: T) {
  function get(): T {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initialValue;
  }

  function set(value: T): void {
    localStorage.setItem(key, JSON.stringify(value));
  }

  return { get, set };
}

const cart = createStorageItem<OrderItem[]>("cart", []);

cart.set([{ productId: 1, quantity: 2 }]);
console.log(cart.get()); // OrderItem[]
```

`createStorageItem` работает с любым значением: массивом позиций, строкой, объектом.
При этом `cart.get()` типизирован не как `unknown`, а точно как `OrderItem[]`, потому
что тип подставлен явно при вызове.

### Дженерик-классы

Параметризовать типом можно не только функции и интерфейсы, но и классы — синтаксис
тот же самый: `<T>` сразу после имени класса.

В магазине так удобно хранить последние просмотренные товары. Нужен стек, который
помнит порядок и умеет отдать самый свежий элемент:

```ts
class RecentlyViewed<T> {
  private items: T[] = [];

  add(item: T): void {
    this.items.push(item);
  }

  takeLast(): T | undefined {
    return this.items.pop();
  }

  get size(): number {
    return this.items.length;
  }
}

const viewedProducts = new RecentlyViewed<Product>();

viewedProducts.add(product);
viewedProducts.add({ id: 2, name: "Худи оверсайз", price: 3990, category: "clothing" });

const lastSeen = viewedProducts.takeLast(); // Product | undefined
```

`T` параметризует класс целиком. TypeScript следит, чтобы все места, где встречается
`T` внутри класса — приватное поле `items`, аргумент `add`, возвращаемое значение
`takeLast`, — оставались согласованы между собой. При этом сам класс не привязан к
`Product` и подойдёт для истории просмотра любой другой сущности. Это та же идея, что
у `Map`, с которым мы уже работали, только контейнер ты здесь объявляешь самостоятельно.

Параметр типа класса относится только к его инстансам. Статические поля и методы
(объявленные через `static`) использовать `T` не могут — на момент их вычисления класс
ещё ни разу не создан ни с одним конкретным типом.

**Когда дженерик-класс избыточен.** Иногда класс или интерфейс всегда работает с одним
конкретным типом — скажем, история просмотров нужна только для `Product`. Тогда параметр
типа лишний, потому что конкретный интерфейс на две строки читается проще
параметризованного. Дженерик оправдан там, где структура действительно
переиспользуется для разных данных, как `ApiResponse<T>` — для любого ответа сервера.

### Практика

Найди в своём проекте два-три типа, которые различаются только
составом полей — например, отдельные интерфейсы ответа для разных сущностей. Замени их
одним параметризованным типом или интерфейсом. Затем напиши небольшой generic-класс
`Store<T>` с методами `get(id)`, `set(item)`, `getAll()` и примени его к одной из
сущностей проекта.

### Если кратко

Дженериками параметризуют не только функции, но и интерфейсы, типы и классы: `ApiResponse<T>` описывает форму любого ответа сервера. Значение по умолчанию (`T = unknown`) делает параметр типа необязательным. В `createStorageItem<T>` и `RecentlyViewed<T>` один параметр согласует все места, где встречается `T`. Статические члены класса параметр типа использовать не могут. Если структура всегда работает с одним типом, параметр лишний.

## 4. Встроенные утилитарные типы

Всё, что разобрано выше, — это ровно тот механизм, на котором построены встроенные
утилитарные типы TypeScript. `Partial<Product>`, `Pick<Product, "id">` и
`ReturnType<typeof fn>` — это дженерик-типы, просто объявленные не тобой, а самим
TypeScript и доступные глобально, без импортов.

Магазин вырос. Админке для PATCH-запроса нужен тот же `Product`, но все поля
опциональные. Витрине — тот же `Product`, но без закупочной цены, которую видит только
внутренняя система. Форме добавления товара — без `id`, который присвоит сервер.

Можно каждый раз описывать новый интерфейс вручную, но тогда достаточно изменить одно
поле в `Product`, чтобы вслед за ним пришлось обновлять все производные типы. Именно
это дублирование и убирают утилитарные типы.

> **Утилитарные типы** — это встроенные инструменты TypeScript для преобразования
> существующих типов. Они доступны глобально, без импортов.

Базовый тип, который будет использоваться во всех примерах ниже, — уже знакомый
`Product`, только теперь с полным набором полей:

```ts
interface Product {
  id: number;
  name: string;
  description: string;
  category: "electronics" | "clothing" | "books";
  price: number;
  stock: number;
  supplierCost: number;
}
```

Поле `supplierCost` — закупочная цена. Она нужна внутренним отчётам и не должна
уезжать к клиенту ни при каких условиях.

### Синтаксис утилитарных типов

Записываются они так же, как любой дженерик-тип, — через угловые скобки:
`Partial<Product>`, `Pick<Product, "id" | "name">`. Внутри TypeScript подставляет
переданный тип на место параметра, точно так же, как в дженериках, которые только что разобрали, — просто сам параметр объявлен не тобой, а стандартной
библиотекой TypeScript.

```ts
type ProductUpdate = Partial<Product>;
//                           ^^^^^^^ — передаём тип Product как аргумент, как в любом дженерике
```

Дальше утилитарные типы удобно разбирать тремя группами: те, что преобразуют объект,
те, что работают с юнионами, и те, что выводят тип из уже написанного кода.

### Группа 1. Преобразование объекта: Partial, Required, Readonly, Pick, Omit, Record

Начнём с самых частых задач — изменить обязательность или изменяемость полей
уже существующего типа.

> **`Partial<T>`** — делает все поля типа `T` опциональными.

Типичный сценарий — PATCH-запрос, в котором админка отправляет только изменённые поля,
а не всю карточку целиком:

```ts
type ProductUpdate = Partial<Product>;
// {
//   id?: number;
//   name?: string;
//   description?: string;
//   category?: "electronics" | "clothing" | "books";
//   price?: number;
//   stock?: number;
//   supplierCost?: number;
// }

function updateProduct(id: number, patch: Partial<Product>): Promise<Product> {
  return fetch(`/api/products/${id}`, {
    method: "PATCH",
    body: JSON.stringify(patch),
  }).then((r) => r.json());
}

updateProduct(1, { price: 3990 }); // OK — только цена
updateProduct(1, { stock: 0 });    // OK — только остаток
```

> **`Required<T>`** — делает все поля обязательными, убирая `?`.

Обратное преобразование нужно там, где тип с опциональными полями пора зафиксировать.
Форма добавления товара разрешает заполнять поля постепенно, но перед отправкой
на сервер все они обязаны быть заполнены:

```ts
interface ProductDraft {
  name?: string;
  price?: number;
  category?: "electronics" | "clothing" | "books";
}

type ReadyProductDraft = Required<ProductDraft>;
// { name: string; price: number; category: "electronics" | "clothing" | "books" }

function submitProduct(draft: ReadyProductDraft) {
  // здесь все поля точно есть — можно отправлять без проверок на undefined
}
```

> **`Readonly<T>`** — запрещает изменение полей после создания объекта.

```ts
type ImmutableProduct = Readonly<Product>;

const frozenProduct: ImmutableProduct = {
  id: 1,
  name: "Беспроводные наушники",
  description: "Активное шумоподавление, 30 часов автономной работы",
  category: "electronics",
  price: 4990,
  stock: 23,
  supplierCost: 2100,
};

frozenProduct.price = 100;
// Error: Cannot assign to 'price' because it is a read-only property
```

`Readonly` удобен для конфигураций, констант и данных, которые не должны меняться
после инициализации, — например, для объектов состояния в сторе.

Все три типа меняют свойства уже имеющихся полей, но чаще нужна не вся структура
целиком, а только её часть. Плитке каталога достаточно `id`, `name` и `price` —
незачем тащить всё остальное.

> **`Pick<T, K>`** — создаёт новый тип, включая только перечисленные ключи `K`
> из типа `T`.

```ts
type ProductCard = Pick<Product, "id" | "name" | "price">;
// { id: number; name: string; price: number }

async function getCatalog(): Promise<ProductCard[]> {
  return fetch("/api/products").then((r) => r.json());
}
```

`Omit` устроен зеркально и перечисляет не нужные поля, а лишние.

> **`Omit<T, K>`** — создаёт тип, исключая перечисленные ключи из `T`.

Самый частый сценарий — убрать внутренние данные перед отправкой клиенту:

```ts
type PublicProduct = Omit<Product, "supplierCost">;
// { id: number; name: string; description: string; category: ...; price: number; stock: number }

type NewProduct = Omit<Product, "id">;
// Тип для добавления товара — id присвоит сервер, клиент его не передаёт
```

> **`Pick` vs `Omit`:** если нужно оставить несколько полей из большого типа —
> удобнее `Pick`. Если нужно убрать одно-два поля из большого типа — удобнее `Omit`.

Ведут себя `Pick` и `Omit` при этом несимметрично, о чём легко забыть. У `Pick`
опечатка в имени поля даёт ошибку компиляции, потому что TypeScript не найдёт такого
ключа. У `Omit` опечатка ошибкой не станет: TypeScript просто ничего не исключит,
и `supplierCost` уедет клиенту, никем не замеченный. Поэтому список в `Omit` стоит
перепроверять особенно внимательно.

Последний тип в этой группе не выбирает поля из существующего типа, а строит новый
объект по ключам. Мы уже писали `categoryLabels` вручную, а потом доставали из него
ключи через `keyof typeof`. Но форму такого словаря можно объявить сразу, не дожидаясь,
пока TypeScript выведет её из значения.

> **`Record<K, T>`** — создаёт тип объекта, где каждый ключ из `K` имеет значение
> типа `T`.

```ts
type CategoryLabels = Record<Category, string>;
// { electronics: string; clothing: string; books: string }

const categoryLabels: CategoryLabels = {
  electronics: "Электроника",
  clothing: "Одежда",
  books: "Книги",
};
```

От подхода через `typeof` это отличается принципиально. `Record` задаёт форму заранее,
и TypeScript проверит, что перечислены все ключи из `Category` и ни одного лишнего.
Забытые `books` станут ошибкой ещё до того, как словарь где-то используют. У `typeof`
порядок обратный. Тип выводится из уже написанного объекта, поэтому о пропущенном
ключе компилятор не узнает — он просто смотрит, что получилось.

### Группа 2. Работа с юнионами: Exclude, Extract, NonNullable

Юнионы тоже можно трансформировать: добавлять и убирать варианты.

> **`Exclude<UnionType, ExcludedMembers>`** — удаляет из юниона указанные члены.

```ts
type OrderStatus =
  | "placed"
  | "paid"
  | "shipped"
  | "delivered"
  | "cancelled"
  | "refunded";

type ActiveOrderStatus = Exclude<OrderStatus, "cancelled" | "refunded">;
// "placed" | "paid" | "shipped" | "delivered"
```

> **`Extract<Type, Union>`** — оставляет только члены юниона, которые совместимы
> со вторым аргументом.

```ts
type OrderEvent = "placed" | "paid" | "shipped" | "refunded" | "reviewed";
type MoneyEvent = Extract<OrderEvent, "paid" | "refunded">;
// "paid" | "refunded"
```

> **`NonNullable<T>`** — удаляет `null` и `undefined` из типа.

```ts
type MaybeProduct = Product | null | undefined;
type DefiniteProduct = NonNullable<MaybeProduct>;
// Product
```

`NonNullable` особенно полезен после проверок, когда ты уже знаешь, что значение не
`null`, а TypeScript всё ещё видит его как `T | null`.

### Группа 3. Типы из существующего кода: ReturnType, Parameters, Awaited

Иногда нужно не описывать тип вручную, а извлечь его из уже существующей функции.
Это особенно удобно, когда функция уже написана и менять её сигнатуру нельзя.

> **`ReturnType<T>`** — извлекает тип возвращаемого значения функции.

Форма состояния формы добавления товара уже есть в самой функции, которая его
собирает. Хочется получить её тип без дублирования:

```ts
function createProductFormState() {
  return {
    name: "",
    price: 0,
    category: null as Category | null,
  };
}

type ProductFormState = ReturnType<typeof createProductFormState>;
// { name: string; price: number; category: Category | null }
```

Теперь `ProductFormState` всегда актуален, потому что при изменении функции тип
обновляется сам, без ручной синхронизации. Об этом и был четвёртый вопрос из введения,
где тип возвращаемого значения `getProduct` не нужно описывать второй раз, потому что
`ReturnType<typeof getProduct>` берёт его прямо из функции.

> **`Parameters<T>`** — извлекает типы параметров функции в виде кортежа.

Полезно, когда нужно переиспользовать сигнатуру уже существующей функции — например,
при создании обёртки:

```ts
function createProduct(name: string, price: number, category: Category): Product {
  // ...
}

type CreateProductParams = Parameters<typeof createProduct>;
// [name: string, price: number, category: Category]

function createProductAndLog(...args: Parameters<typeof createProduct>): Product {
  const newProduct = createProduct(...args);
  console.log("Товар добавлен", newProduct.name);
  return newProduct;
}
```

> **`Awaited<T>`** — раскрывает тип значения внутри `Promise`, рекурсивно.

```ts
type A = Awaited<Promise<string>>;          // string
type B = Awaited<Promise<Promise<number>>>; // number
```

Особенно полезен в паре с `ReturnType` — чтобы получить не `Promise<Product>`, а сам
`Product`:

```ts
async function getProduct(id: number): Promise<Product> {
  return fetch(`/api/products/${id}`).then((r) => r.json());
}

type ResolvedProduct = Awaited<ReturnType<typeof getProduct>>;
// Product — а не Promise<Product>
```

### Комбинирование утилитарных типов

Утилитарные типы можно вкладывать друг в друга: это позволяет выражать сложные
трансформации в одну строку, не дублируя поля вручную. Соберём сервисный слой
каталога — ровно то, ради чего всё это затевалось в начале лонгрида:

```ts
type CreateProductRequest = Omit<Product, "id">;
// Новый товар — id присвоит сервер

type UpdateProductRequest = Partial<Omit<Product, "id" | "supplierCost">>;
// Обновление — все поля опциональны, id и закупочную цену менять с клиента нельзя

type PublicProductResponse = Readonly<Omit<Product, "supplierCost">>;
// Публичный ответ — без закупочной цены, поля нельзя мутировать на клиенте

type CatalogPageResponse = Pick<Product, "id" | "name" | "price">[];
// Выдача каталога — только те поля, что нужны плитке

interface ProductService {
  create(data: CreateProductRequest): Promise<PublicProductResponse>;
  update(id: number, data: UpdateProductRequest): Promise<PublicProductResponse>;
  findById(id: number): Promise<PublicProductResponse | null>;
  findAll(): Promise<CatalogPageResponse>;
  delete(id: number): Promise<void>;
}
```

Все типы выведены из одного `Product`. Если завтра в интерфейс добавится поле
`rating` — оно автоматически появится во всех производных типах, ничего не нужно
обновлять вручную. Второй вопрос из введения был как раз об этом. Интерфейс, написанный
руками, о новом поле не узнает, и чинить его придётся тоже руками. А
`CreateProductRequest` и остальные производные типы получат поле сами, потому что
выведены из `Product`, а не скопированы с него.

### Практика

В своём проекте возьми один базовый интерфейс с четырьмя-пятью полями.
Выведи из него тип для формы редактирования (все поля необязательны), тип для
публичного ответа API (без внутренних или чувствительных полей) и тип-словарь, где
ключами служат допустимые значения одного из полей. Затем добавь в базовый интерфейс
новое поле и проверь, какие из производных типов обновились сами, а какие — нет,
если бы были описаны вручную.

### Если кратко

Утилитарные типы — это дженерик-типы, объявленные самим TypeScript и доступные без импорта. Первая группа преобразует объект: `Partial`, `Required` и `Readonly` меняют свойства полей, `Pick` и `Omit` выбирают поля, `Record` строит словарь по ключам. Вторая работает с юнионами (`Exclude`, `Extract`, `NonNullable`), третья достаёт типы из кода (`ReturnType`, `Parameters`, `Awaited`). Утилитарные типы можно вкладывать друг в друга, и тогда все производные типы выводятся из одного `Product`. Опечатка в списке `Omit` ошибкой не станет, поэтому такие списки стоит перепроверять.

## 5. Mapped types

`Partial<Product>`, `Readonly<Product>`, `Pick<Product, "id">` — они ведут себя так
предсказуемо и удобно, что легко поверить, будто это встроенная магия компилятора,
отдельная от всего, что мы разбирали раньше. На самом деле это обычные типы, объявленные
в стандартной библиотеке TypeScript, и их можно прочитать, а значит, и написать самому.

Инструмент, на котором они построены, называется mapped type. У него есть прямой
аналог в коде, который ты уже писал(а) много раз, — метод `map`, который перебирает
элементы массива и для каждого возвращает новое значение. Mapped type делает то же
самое, только перебирает не элементы массива, а ключи типа.

> **Mapped type** — тип, который строится перебором ключей другого типа, где для
> каждого ключа `K` из `keyof T` описывается, каким будет соответствующее поле в новом
> типе.

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};
```

Читается это почти как цикл. Для каждого ключа `K` из `keyof T` поле в новом типе
получает тип `T[K]` и модификатор `?`, который делает его необязательным. Оба
механизма уже знакомы: перебор ключей даёт `keyof`, а тип значения по ключу
даёт индексированный доступ. Собственно, это и есть настоящая реализация `Partial<T>`
из стандартной библиотеки TypeScript, только под другим именем, чтобы не столкнуться
со встроенным.

```ts
type ProductPatch = MyPartial<Product>;
// { id?: number; name?: string; description?: string; category?: ...; ... }
```

Применим `MyPartial` к `Product` — и результат совпадает с тем, что раньше давал
встроенный `Partial<Product>`. TypeScript прошёл по всем ключам и перед каждым типом
поставил `?`.

Модификатор `?` можно не только добавлять, но и снимать — конструкцией `-?`. Так
устроен противоположный `Partial` тип, `Required`, разобранный раньше:

```ts
type MyRequired<T> = {
  [K in keyof T]-?: T[K];
};
```

Тот же приём работает и с `readonly`: `readonly` добавляет модификатор, `-readonly`
снимает его. Вот так на самом деле выглядит `Readonly<T>` из стандартной библиотеки:

```ts
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};
```

`Partial`, `Required` и `Readonly` — не три независимых механизма, а один и тот же
mapped type с разными модификаторами перед двоеточием. Как только становится видна
эта реализация, встроенные утилитарные типы перестают быть чёрным ящиком, и их можно
комбинировать, изменять и писать свои под задачи, которых в стандартной библиотеке нет.

В магазине такая необходимость уже возникала. Форма добавления товара держит цену и
остаток как строки, пока продавец их печатает, и приводит к числам только перед
отправкой. Готового утилитарного типа, который делал бы все поля строками,
в TypeScript нет, но написать его не сложнее, чем `MyPartial`:

```ts
type Stringify<T> = {
  [K in keyof T]: string;
};

type ProductFormFields = Stringify<Product>;
// { id: string; name: string; description: string; category: string; price: string; ... }
```

Здесь тип поля вообще не зависит от `T[K]` — какое бы поле ни было в исходном типе,
в результате оно всегда `string`. Перебор ключей от этого не меняется, меняется
только то, что мы решили поставить после двоеточия.

**Когда писать свой mapped type не стоит.** Нужная трансформация часто уже есть среди
встроенных — `Partial`, `Readonly`, `Pick`, `Omit`, `Record`. Тогда бери готовое, а не
переписывай то же самое своими словами. Самописный тип читает меньше людей, чем
встроенный, который все уже знают. Свой mapped type имеет смысл писать, когда нужная
трансформация одноразовая или специфичная для проекта, как `Stringify` выше.

Третий вопрос из введения был о том, вшита ли `Partial` в компилятор как магия, и
ответ теперь виден: это обычный дженерик-тип на mapped type, три строки кода, которые
ты только что написал(а) самостоятельно.

### Практика

Напиши свои версии `Partial` и `Readonly` под другими именами, не
глядя на пример выше. Затем напиши mapped type `Nullable<T>`, который делает каждое
поле `T | null`, и примени его к черновику карточки товара.

### Если кратко

Mapped type строится перебором ключей другого типа, как `map` перебирает элементы массива. `Partial`, `Required` и `Readonly` — один и тот же приём с разными модификаторами: `?`, `-?` и `readonly`. Поэтому встроенные утилитарные типы — не магия компилятора: их можно прочитать и написать самому. Свой mapped type, как `Stringify`, имеет смысл писать, когда трансформация специфична для проекта. Если нужное уже есть среди встроенных, бери готовое.


## 6. Conditional types и infer

### Условие и infer

`ReturnType` и `Awaited` из предыдущего раздела устроены не так, как `Partial`. Они не
переставляют модификаторы полей, а принимают решение в зависимости от того, что за тип
им передали. `ReturnType<typeof getProduct>` должен вернуть тип возвращаемого
значения — но откуда TypeScript вообще знает, что у типа функции есть возвращаемое
значение, и как он его достаёт? Здесь работает другой механизм — conditional type.

> **Conditional type** — тип, который выбирает один из двух вариантов в зависимости от того, выполняется ли условие `T extends U`.

Прямой аналог conditional type — тернарный оператор, только вычисляется он не в
рантайме, а компилятором во время проверки типов.

```ts
type IsString<T> = T extends string ? true : false;

type A = IsString<"hello">; // true
type B = IsString<number>;  // false
```

Читается так же, как обычный тернарник: `T extends string ? true : false` — «если `T`
совместим со `string`, результат `true`, иначе `false`». `extends` здесь означает не
наследование и не ограничение, как в constraint, а именно проверку условия: совместим
ли один тип с другим.

Более практичная задача — получить тип элемента массива, если `T` — массив, и оставить
`T` как есть в остальных случаях:

```ts
type ElementType<T> = T extends (infer U)[] ? U : T;

type A = ElementType<Product[]>; // Product
type B = ElementType<string>;    // string
```

Здесь появляется новое ключевое слово `infer`, аналог которого в обычном коде —
деструктуризация с извлечением значения. Когда пишешь `const [first] = items`, ты не
описываешь, что такое `first`, а просишь JavaScript «назови первым элементом то, что
там есть, и дай мне». `infer U` делает то же самое на уровне типов: «если `T` — это
массив чего-то, назови это что-то `U` и дай мне», а дальше `U` можно использовать
в ветке `true` точно так же, как обычную переменную.

Если `T` — `Product[]`, TypeScript сопоставляет его с шаблоном `(infer U)[]`, видит,
что `U` — это `Product`, и возвращает `Product`. Если `T` — не массив, например
`string`, шаблон `(infer U)[]` не подходит, условие не выполняется, и возвращается
сама `T` без изменений.

Теперь можно вернуться к `ReturnType` и `Awaited`, которые применялись в предыдущем
разделе как готовый инструмент, и посмотреть, как они устроены внутри. Вот упрощённая
версия `ReturnType` из стандартной библиотеки TypeScript:

```ts
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
```

`T extends (...args: any[]) => infer R` — условие проверяет, что `T` вообще является
типом функции с произвольными аргументами. Если да, `infer R` достаёт тип того, что
эта функция возвращает, и в ветке `true` он становится результатом. Если `T` — не
функция, условие не выполняется, и результатом становится `never` — тип, у которого
нет ни одного значения, сигнал, что вызов был некорректен.

`Awaited` устроен похоже, только достаёт значение не из типа функции, а из типа
`Promise`:

```ts
type MyAwaited<T> = T extends Promise<infer V> ? V : T;
```

Если `T` — `Promise<Product>`, `infer V` достаёт `Product`. Если `T` — не `Promise`,
например уже готовый `Product`, условие не выполняется, и `Awaited` просто возвращает
`T` без изменений, поэтому `Awaited<Product>` — это тоже `Product`.

`ReturnType` и `Awaited`, которые в разделе про utility types выглядели как два
самостоятельных инструмента, собраны одним приёмом. Условие проверяет форму типа, а
`infer` достаёт из этой формы нужную часть.

### Когда это уже головоломка

Вложенные ветки, несколько `infer` в одном условии и condition внутри condition легко
доводят условный тип до состояния, в котором его не прочитает никто, включая автора
через месяц. Здесь стоит остановиться раньше, чем кажется нужным. Цель этого
раздела — уметь прочитать и написать одно простое условие с одним `infer`, как
`ElementType` выше. Если для объяснения типа требуется больше пары предложений,
вероятнее всего, проще и честнее описать нужную структуру обычным `type` или
`interface`, не пытаясь вывести её условным типом.

### Практика

Напиши conditional type `Unwrap<T>`, который для массива возвращает тип
элемента (как `ElementType` выше), а для всего остального — сам `T`. Затем
самостоятельно, не подглядывая в примеры выше, распиши по шагам, что происходит,
когда компилятор вычисляет `Awaited<Promise<Product>>`: какое условие проверяется, что
делает `infer`, что становится результатом.

### Если кратко

Conditional type выбирает один из двух вариантов по условию `T extends U`, как тернарный оператор, только на уровне типов. `infer` достаёт часть типа и даёт ей имя, как деструктуризация: так устроены `ElementType`, `ReturnType` и `Awaited`. Если условие не выполняется, результатом становится вторая ветка — `T` или `never`. Одно простое условие с одним `infer` читается легко. Вложенные ветки быстро превращаются в головоломку, и тогда проще описать структуру обычным `type` или `interface`.

## 7. Template literal types

Корзина шлёт события — товар добавили, убрали, корзину очистили. Такие строки уже
описывались как union литералов, когда разбирали `Extract`. Но на практике их сами по себе используют редко. Чаще это часть более длинной строки, например имени канала,
в который публикуется событие — `cart:added`, `cart:removed`. Описывать каждый канал
вручную — то же дублирование, с которым дженерики борются с самого начала лонгрида,
только на уровне строк.

> **Template literal type** — строковый тип, собранный из подстановок других типов, синтаксически похожий на шаблонную строку JavaScript.

```ts
type CartEvent = "added" | "removed" | "cleared";
type CartChannel = `cart:${CartEvent}`;
// "cart:added" | "cart:removed" | "cart:cleared"
```

Аналог здесь прямой — та же шаблонная строка `` `cart:${event}` ``, которую ты писал(а) в
обычном коде десятки раз. Только на месте значения `event` стоит тип `CartEvent`,
и на выходе получается не одна строка, а union из всех возможных подстановок.

```ts
function publish(channel: CartChannel, payload: OrderItem) {
  // ...
}

publish("cart:added", { productId: 1, quantity: 2 });   // OK
publish("cart:add", { productId: 1, quantity: 2 });
// Error: Argument of type '"cart:add"' is not assignable
// to parameter of type 'CartChannel'
```

Опечатка в названии канала — обычно баг, который проявляется в рантайме, когда
подписчик молча не получает событие, потому что подписан на другую строку. Здесь она
становится ошибкой компиляции, ровно как это уже было с ключами объекта в разделе
про `keyof`.

Template literal type — инструмент нишевый и пригождается там, где строка
действительно несёт структуру, как имена событий, ключи в `localStorage` из
`createStorageItem`, маршруты и CSS-классы. Там, где строка — это просто текст
без внутренней структуры, template literal type не нужен, обычный `string` подходит
лучше.

### Практика

В своём проекте найди хотя бы одно место, где строки состоят из
постоянного префикса и переменной части: ключи кеша, названия событий, маршруты.
Опиши их template literal type и найди в коде место, где сейчас такая строка
собирается вручную через конкатенацию или шаблонную строку без проверки типов.

### Если кратко

Template literal type собирает строковый тип из подстановок и выглядит как шаблонная строка JavaScript. Если подставить union, как `CartEvent`, на выходе получится union из всех вариантов — имена каналов `cart:added`, `cart:removed` и `cart:cleared`. Опечатка в таком имени становится ошибкой компиляции, а не молчаливым багом в рантайме. Приём нужен там, где строка несёт структуру: события, ключи, маршруты. Для обычного текста лучше подходит `string`.

## 8. Капстоун: типобезопасный fetch-wrapper

### От fetchJson к fetchJsonValidated

Пора собрать всё вместе на обёртке над `fetch`, вокруг которой строился магазин
из недели 7. Она убирает копии кода запроса для каждого эндпоинта и возвращает результат
нужного типа.

На неделе 7 запрос к серверу и обработка сетевой ошибки писались отдельно для
каждого случая. На неделе 11 стало ясно, что ответ сервера нельзя типизировать через
`as`: компилятор в это поверит, а рантайм может и обмануть. Сейчас есть все
инструменты для того, чтобы решить обе проблемы разом.

Вернёмся к `fetchJson`, с которой лонгрид начинался:

```ts
async function fetchJson<T>(url: string): Promise<T> {
  const response = await fetch(url);
  return response.json();
}

const product = await fetchJson<Product>("/api/products/1"); // выглядит как Product
```

Дублирование она убрала, и результат типизирован как `Product`. Но откуда взялся `T`?
Мы передали его сами, явным образом через `<Product>`, как обещание, а не как проверку.
Внутри функции ничего не смотрит на то, что реально пришло в `response.json()`, и `T`
нигде не участвует в вычислении, он просто подставлен в сигнатуру. Если сервер по
ошибке вернёт `{ error: "not found" }`, TypeScript всё равно будет уверен, что
`product` — это `Product`, потому что мы сами сказали ему в это поверить.

Это тот же `as Product` из недели 11, только спрятанный внутри generic-обёртки: от
этого он выглядит убедительнее, но остаётся настолько же небезопасным.

Прежде чем чинить эту проблему, добавим вторую вещь, которой не хватает наивной
версии, — обработку сетевой ошибки и неуспешного статуса без исключений, тем же
способом, что уже разбирался на неделе 11:

```ts
type FetchResult<T> =
  | { status: "success"; data: T }
  | { status: "network-error"; error: Error }
  | { status: "bad-status"; code: number };

async function fetchJsonSafe<T>(url: string): Promise<FetchResult<T>> {
  let response: Response;
  try {
    response = await fetch(url);
  } catch (error) {
    return { status: "network-error", error: error as Error };
  }

  if (!response.ok) {
    return { status: "bad-status", code: response.status };
  }

  const data = (await response.json()) as T;
  return { status: "success", data };
}
```

Результат — discriminated union из трёх вариантов, тот же приём, что применялся на
неделе 11 к результату валидации. Вызывающий код обязан проверить поле `status`,
прежде чем добраться до `data`, — иначе TypeScript не даст обратиться к полю,
которого может не быть.

Проблема с `as T` внутри никуда не делась — она просто переехала на одну функцию
глубже. Честный вариант — не позволять вызывающему просто продиктовать `T`, а
потребовать функцию-проверку, которая действительно посмотрит на данные:

```ts
async function fetchJsonValidated<T>(
  url: string,
  validate: (data: unknown) => T
): Promise<FetchResult<T>> {
  let response: Response;
  try {
    response = await fetch(url);
  } catch (error) {
    return { status: "network-error", error: error as Error };
  }

  if (!response.ok) {
    return { status: "bad-status", code: response.status };
  }

  const raw: unknown = await response.json();
  const data = validate(raw); // здесь T берётся из проверки, а не из обещания
  return { status: "success", data };
}

function validateProduct(raw: unknown): Product {
  // здесь настоящая проверка — обращение к полям raw, throw при несовпадении
  // ...
  return raw as Product; // финальный as допустим только внутри самой проверки
}

const result = await fetchJsonValidated("/api/products/1", validateProduct);
```

В `fetchJson<T>` тип `T` не следует ни из чего, кроме желания вызывающего. В
`fetchJsonValidated` он выводится из возвращаемого типа `validate` — тем же механизмом,
что и в `getPage` в начале лонгрида. А `validate` обязана действительно
проверить `raw`, прежде чем что-то вернуть. Единственный оставшийся `as` сидит внутри
самой проверки, и на неделе 11 уже разбиралось, что там ему и место.

Дальше любого конкретного утилитарного типа с этой недели стоит унести то, что
generic сам по себе ничего не проверяет, а только переносит и связывает типы.
Настоящая проверка данных всегда происходит в конкретном месте — в `validate`, в
`parse`, в схеме — и никакой дженерик её не заменяет, сколько бы уровней обёртки ни
было сверху.

### Чистка типов проекта

Теперь, когда `fetchJsonValidated` готов, стоит пройтись по остальным типам проекта.
Копии почти одинаковых интерфейсов заменяются дженерик-структурами вроде
`ApiResponse<T>` или `Store<T>`. Производные типы для форм, публичных ответов и
словарей выражаются через `Partial`, `Omit`, `Pick` и `Record` вместо ручного
перечисления полей.

### Чтение ошибок в дженериках

Сообщения компилятора про дженерики длиннее и запутаннее, чем про обычные типы:
TypeScript честно показывает всю цепочку подстановок. Разбирать такое сообщение
целиком не нужно, достаточно прочитать первую строку и найти, какое ограничение не
выполнено, потому что проблема обычно именно в этом, а не в чём-то более экзотическом.
Ошибка вида `Type 'string' does not satisfy the constraint 'keyof Product'` почти
всегда значит, что передан ключ, которого нет в объекте, и дальше можно не читать.

### Практика

Возьми `fetchJsonValidated` и примени к двум эндпоинтам своего проекта,
написав для каждого свою функцию `validate`. Затем сравни две версии — с
`fetchJson<T>` и с `fetchJsonValidated` — и сформулируй словами (не кодом), в какой
момент каждая из них перестаёт быть надёжной.

### Если кратко

В `fetchJson<T>` тип `T` — это обещание вызывающего, а не проверка: если сервер вернёт другое, TypeScript всё равно поверит. `fetchJsonSafe` добавляет обработку сетевой ошибки и статуса через discriminated union, но `as T` в нём остаётся. `fetchJsonValidated` берёт `T` из функции `validate`, которая действительно смотрит на данные. Дженерик сам ничего не проверяет, он только переносит и связывает типы. Настоящая проверка всегда происходит в конкретном месте: в `validate`, `parse` или схеме.

## Если кратко

TypeScript — это JavaScript со статической типизацией. Компилятор проверяет типы
в редакторе, до запуска кода, что позволяет ловить ошибки раньше, делает сигнатуры
функций самодокументируемыми и даёт IDE точное понимание формы каждого объекта.

Дженерики — способ писать функции, интерфейсы, типы и классы, которые работают
с разными типами данных, не теряя проверку типов и не дублируя код под каждый
конкретный случай. Параметр типа `T` подставляется в момент использования —
TypeScript выводит его сам из аргументов или принимает явно.

Рядом с дженериками стоят три оператора уровня типов, где `typeof` достаёт тип из уже
существующего значения, `keyof` — объединение ключей типа, а `T[K]` — тип значения по
конкретному ключу. По отдельности каждый простой, а вместе — как в `K extends keyof T`:
они и позволяют писать функции вроде `getProperty`, которые работают с любым объектом,
но не теряют точность.

Утилитарные типы продолжают ту же идею на более высоком уровне и представляют собой
готовые дженерик-типы, встроенные в TypeScript. `Partial`, `Readonly` и подобные им
устроены через mapped types — перебор ключей типа, тот же приём, что и `map` для
массива. `ReturnType`, `Awaited` и подобные устроены через conditional types и `infer` —
тернарник и деструктуризация на уровне типов. Они не создают новые данные, а
преобразуют уже существующие типы под конкретную задачу. На протяжении всего
лонгрида это был один и тот же `Product` — от первой `fetchJson<T>` до
`fetchJsonValidated` в самом конце. Базовый тип описан один раз, всё остальное выведено
из него.

За синтаксисом легко упустить, что не всё, что можно выразить дженериком или условным
типом, стоит так выражать. Тип должен объяснять данные, а не демонстрировать, что умеет
автор. Конкретный интерфейс на две строки, который читается с первого взгляда, почти
всегда честнее универсальной конструкции на десять строк с двумя уровнями condition
и вложенным `infer` — даже если вторая формально даёт больше гибкости.

<a id="глубже"></a>

## ★ Глубже

Модель из основной части темы — простые дженерики, `keyof`/`typeof`, mapped и
conditional types в один уровень вложенности — достаточна для повседневной работы.
Но несколько вопросов она не закрывает. Почему функции и массивы ведут себя по-разному
при подстановке типа. Можно ли применить `Partial` к вложенным полям. Что делать, если
редактор начал тормозить на сложных типах. Как различить на уровне компилятора два
похожих по форме идентификатора. Раздел не обязательный.

<a id="массив-собак-можно-передать-туда-где-ждут-массив-животных-а-функцию-для-собак-туда-где-ждут-функцию-для-животных-передать-нельзя-почему-есть-разница"></a>

### ❓ Массив собак можно передать туда, где ждут массив животных, а функцию для собак туда, где ждут функцию для животных, передать нельзя. Почему есть разница?

Это вариантность. Интуиция «раз собака — это животное, то и всё с собаками подходит
вместо всего с животными» работает с контейнерами, но ломается на функциях. Функция,
умеющая работать с любым животным, безопасно заменит функцию для собак. Наоборот — нет,
потому что ей могут передать кошку. TypeScript в некоторых местах намеренно допускает
небезопасный вариант ради удобства — из-за этого компилятор иногда пропускает то, что
по-хорошему должен был отклонить.

<a id="можно-сделать-partial-который-заходит-вглубь-вложенных-объектов"></a>

### ❓ Можно сделать `Partial`, который заходит вглубь вложенных объектов?

Можно, если написать тип, который вызывает сам себя и для каждого поля применяет себя
же, когда поле оказывается объектом, и оставляет его как есть в остальных случаях. Так
пишут `DeepPartial` и `DeepReadonly`. У рекурсии в типах есть предел, и на глубоких или
циклических структурах компилятор сдаётся и сообщает, что тип слишком сложный.
Рекурсивные типы работают, но это уже граница разумного — часто честнее описать нужную
структуру руками.

<a id="редактор-начал-думать-по-несколько-секунд-на-каждое-действие--это-из-за-типов"></a>

### ❓ Редактор начал думать по несколько секунд на каждое действие — это из-за типов?

Вполне может быть. Проверка типов — это вычисление, и сложные типы (длинные цепочки
условных типов, большие объединения, рекурсия, вычисления над строками) компилятор
считает заново при каждой проверке. В большом проекте это ощущается как тормозящий
редактор и медленный CI. Читаемость и скорость типа — тоже критерии при выборе, а
не только строгость.

<a id="customerid-и-orderid--обе-строки-и-я-их-путаю-можно-это-запретить"></a>

### ❓ `CustomerId` и `OrderId` — обе строки, и я их путаю. Можно это запретить?

Можно, приём называется branded (или nominal) types и состоит в том, что к типу
добавляют невидимое служебное поле-метку, из-за которого две одинаковые по форме
строки перестают быть взаимозаменяемыми. В рантайме это по-прежнему обычная строка,
метка существует только для компилятора. Ценно это там, где путаница идентификаторов
стоит дорого, — в сферах денег, прав доступа, ключей сущностей.

<a id="насколько-далеко-это-вообще-заходит-я-знаю-типы-которые-что-то-вычисляют"></a>

### ❓ Насколько далеко это вообще заходит: я знаю типы, которые что-то вычисляют?

Заходит далеко, потому что система типов TypeScript тьюринг-полна, и в типах писали
арифметику, разбор строк и даже игры. Как упражнение это прочищает голову, а как код в
проекте почти всегда оказывается плохой идеей, потому что такие типы медленно
проверяются, плохо читаются и ломаются от любого изменения. Тип должен объяснять
данные, а не демонстрировать возможности автора.

## Что дальше

Теперь у тебя есть и типы, и способ не повторяться в них, но уровнем выше остаётся
вопрос о том, как организован сам код. Пока это набор файлов, которые выросли как
выросли, и чем больше проект, тем заметнее, что у него нет структуры. На следующей
неделе — о том, как раскладывать код по ответственностям и какие решения для этого
придуманы до нас.
