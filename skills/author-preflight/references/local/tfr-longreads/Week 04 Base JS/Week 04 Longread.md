# Тема 4. JavaScript: как язык думает

Три недели страница была статичной: HTML задавал структуру, CSS — внешний вид. Чтобы страница ожила: реагировала на клики, считала, менялась, проверяла формы, отправляла запросы, нужен язык. В браузере этот язык один — **JavaScript**.

JavaScript есть в каждом браузере мира. Он создавался, чтобы быстро оживлять страницы, и характер у него под стать задаче: он динамический, гибкий и часто «прощающий». Там, где более строгий язык остановился бы с ошибкой, JavaScript может попытаться привести типы и продолжить выполнение.

Отсюда и сила языка, и его странности.

Эта неделя не про синтаксис. Ты уже знаешь Python и Go, поэтому переменные, условия, циклы и функции не должны быть сюрпризом. Главная ловушка в другом: JavaScript выглядит как знакомый язык, но ведёт себя по своим правилам.

Мы разберём:

1) как запускать код и смотреть состояние программы в DevTools;
2) как работают `const`, `let`, `var`, scope, hoisting и strict mode;
3) как JavaScript связывает имена и значения;
4) почему числа иногда ведут себя неожиданно;
5) как работает приведение типов и почему по умолчанию нужен `===`;
6) как функции становятся значениями и откуда берётся `this`;
7) что такое замыкания и почему они так важны во фронтенде.

---

## Актуализация: запусти это в голове

Открой DevTools → **Console**. Это место, где JavaScript можно запускать сразу, без отдельного файла. Всё, что встречается в лонгриде, можно проверять там же.

Но сначала не запускай. Предскажи.

### 1. Что выведет?

```js
console.log(0.1 + 0.2 === 0.3);
```

А почему?

### 2. Что выведет?

```js
console.log([] == ![]);
```

Да, это легальный JavaScript.

### 3. Что выведет?

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

Три раза подряд: что именно?

### 4. Что выведет?

```js
console.log(typeof null);
console.log(NaN === NaN);
```

Если ответы тебя удивили, это нормально. В этом и есть суть недели.

JavaScript выглядит как знакомый язык, но ведёт себя по своим правилам. Научиться видеть эти правила — главная цель темы.

К вопросам вернёмся дальше:

- `0.1 + 0.2 === 0.3` — в разделе про числа;
- `[] == ![]` — в разделе про приведение типов;
- `var` в цикле — в разделе про замыкания;
- `typeof null` и `NaN === NaN` — в разделах про типы, числа и сравнение.

## 1. Инструменты: Console, ошибки и Debugger

В первой неделе мы уже открывали DevTools и смотрели Network. Теперь соседняя вкладка — **Console** — станет рабочим местом для экспериментов с JavaScript.

Console похожа на REPL: пишешь выражение, нажимаешь Enter, сразу видишь результат. Если нужно ввести несколько строк, можно использовать Shift + Enter для переноса строки, а Enter — для запуска, когда код готов.

Но важно не застрять только на `console.log`. Для тем про область видимости, `this` и замыкания особенно полезен **Debugger**: он показывает не только результат, но и состояние программы во время выполнения.

### Как читать ошибки в Console

В JavaScript сообщения об ошибках обычно короче, чем traceback в Python. Чаще всего первая строка уже говорит, что произошло.

| Ошибка | Что обычно означает |
|---|---|
| `ReferenceError` | Имени нет или к нему нельзя обратиться сейчас |
| `TypeError` | Значение есть, но операция для него невозможна |
| `SyntaxError` | Код не разобран как JavaScript |

Например, если обратиться к переменной, которой нет, будет `ReferenceError`.

```js
unknownVariable;
```

Если попытаться вызвать число как функцию, будет `TypeError`.

```js
const x = 10;
x();
```

В Go похожие проблемы часто ловятся ещё компилятором: нельзя использовать необъявленное имя или вызвать `int` как функцию. JavaScript в браузере выполняется динамически, поэтому многие ошибки проявляются во время выполнения.

### Debugger: смотреть не только вывод, но и состояние

Для этой недели особенно полезны три инструмента DevTools:

- **breakpoint** — остановка выполнения на выбранной строке;
- **Scope** — панель с видимыми переменными;
- **Call Stack** — цепочка вызовов функций.

Минимальный пример

```js
function createCounter() {
  let count = 0;

  return function () {
    count++;
    console.log(count);
  };
}

const counter = createCounter();
counter();
```

Если поставить breakpoint на строку `count++`, браузер остановит выполнение внутри возвращённой функции. В панели **Scope** можно увидеть переменную `count`. В Chrome DevTools она будет находиться в разделе вроде **Closure**.

Это важный момент: замыкание перестаёт быть абстрактным словом и становится тем, что видно глазами.

### Мини-практика

1. В Console выполни любое выражение с числами.
2. Намеренно вызови `ReferenceError`, обратившись к необъявленной переменной.
3. Намеренно вызови `TypeError`, попробовав вызвать число как функцию.
4. Прочитай первую строку ошибки и объясни, что именно пошло не так.

### Вывод

Console — это место, где гипотезу о коде можно проверить за секунды, а первая строка ошибки почти всегда называет причину: `ReferenceError` — имени нет или к нему рано обращаться, `TypeError` — значение есть, но операция для него невозможна, `SyntaxError` — код вообще не разобран. Но вывода мало там, где важно состояние программы: для областей видимости, `this` и замыканий нужен Debugger с панелями Scope и Call Stack. Дальше по теме мы будем возвращаться к ним постоянно.

## 2. Объявления: `const`, `let`, `var`, scope и hoisting

Любая программа работает с именами: `user`, `count`, `price`, `result`. В JavaScript важно понимать не только то, как переменная называется, но и где это имя доступно, когда к нему можно обратиться и можно ли записать в него другое значение.

В современном JavaScript почти всегда используют `const` и `let`.

```js
const language = "JavaScript";
let year = 1995;

year = 1996;
```

`const` означает, что в эту переменную нельзя записать другое значение. `let` используют, если значение действительно будет меняться. Старый способ объявления — `var`. Он всё ещё существует из-за обратной совместимости: огромное количество старого веб-кода написано с `var`, и браузеры не могут просто перестать его поддерживать.

### Область видимости

Область видимости — это часть программы, где имя доступно. У `let` и `const` область видимости блочная: переменная живёт внутри ближайших фигурных скобок. У `var` область видимости функциональная: блок `if` или `for` сам по себе его не ограничивает.

```js
if (true) {
  var a = 10;
  let b = 20;
  const c = 30;
}

console.log(a);
console.log(b);
console.log(c);
```

`console.log(a)` выведет `10`, потому что `var` не ограничен блоком `if`. А на `b` выполнение остановится с `ReferenceError`: переменная `b` существовала только внутри блока. До `console.log(c)` программа уже не дойдёт.

В Python нет блочной области видимости для `if`: переменная, созданная внутри `if`, остаётся доступной снаружи. В Go блоки имеют значение: переменная, объявленная внутри `{ ... }`, снаружи недоступна. Современный JavaScript с `let` и `const` в этом смысле ближе к Go, а старый `var` — отдельное историческое поведение.

Ещё один важный термин — **лексическая область видимости**. Это значит, что доступность имени определяется тем, где код написан, а не тем, откуда функция потом будет вызвана. Эта идея станет особенно важной в разделе про замыкания.

### Hoisting и TDZ

Перед выполнением кода JavaScript подготавливает области видимости. Это называют **hoisting**: объявления как будто «всплывают». Но `var`, `let` и `const` всплывают по-разному.

```js
console.log(city);
var city = "Tallinn";
```

Этот код не даёт `ReferenceError`. Он выводит `undefined`, потому что объявление `var city` уже известно движку, но присваивание `"Tallinn"` ещё не выполнилось.

С `let` и `const` — иначе.

```js
console.log(country);
let country = "Estonia";
```

Здесь будет `ReferenceError`. Переменная уже есть во внутренней модели области видимости, но до строки объявления она находится в **TDZ** — Temporal Dead Zone. В этот период к ней нельзя обращаться.

Это сделано не для странности, а для безопасности. Старое поведение `var` слишком легко маскировало ошибки: программа продолжала работать с `undefined`, хотя разработчик часто ожидал уже настоящее значение. `let` и `const` делают такую ошибку заметной раньше.

### Строгий режим

В старом JavaScript можно было случайно создать глобальную переменную простым присваиванием.

```js
x = 10;
console.log(x);
```

В некоторых окружениях такой код сработает. Это опасно: опечатка превращается в новую глобальную переменную. Строгий режим запрещает такое поведение.

```js
"use strict";

x = 10;
```

В строгом режиме будет `ReferenceError`. В современных JavaScript-модулях strict mode включён автоматически, но в обычных скриптах его можно включить строкой `"use strict"`.

### Мини-практика

Предскажи, что произойдёт, потом проверь в Console.

```js
{
  console.log(score);
  let score = 100;
}
```

Теперь сравни с `var`.

```js
{
  console.log(score);
  var score = 100;
}
```

Объясни разницу через TDZ и hoisting.

### Вывод

Для нового кода правило простое: используй `const` по умолчанию, `let`, когда значение действительно меняется, `var`, только если читаешь или поддерживаешь старый код. Разница между ними не косметическая: она определяет область видимости, момент доступности имени и то, насколько рано JavaScript покажет ошибку.

## 3. Типы и значения

В JavaScript тип принадлежит значению, а не переменной. Переменная — это имя, которое сейчас связано с каким-то значением. Если переменная объявлена через `let`, в неё можно сначала положить число, потом — строку, потом — объект.

```js
let x = 10;
x = "10";

console.log(x);
console.log(typeof x);
```

`console.log(x)` выведет строку `10` без кавычек, потому что `console.log` печатает строковое содержимое. Если ввести просто `x` в Console как выражение, DevTools обычно покажет значение как строку, например, `'10'` или `"10"`. `typeof x` вернёт `"string"`.

В Go такой код невозможен: переменная имеет статический тип, и в переменную типа `int` нельзя записать строку. JavaScript проверяет типы во время выполнения, поэтому он гибче, но меньше защищает от ошибок заранее.

### Основные типы

В JavaScript есть примитивные типы: `number`, `string`, `boolean`, `undefined`, `null`, `symbol`, `bigint`. Есть и объектные типы: объекты, массивы и функции.

```js
console.log(typeof 42);
console.log(typeof "hello");
console.log(typeof true);
console.log(typeof undefined);
console.log(typeof 10n);
console.log(typeof {});
console.log(typeof []);
console.log(typeof function () {});
console.log(typeof null);
```

Результаты будут такими: для числа — `"number"`, строки — `"string"`, булева значения — `"boolean"`, `undefined` — `"undefined"`, `10n` — `"bigint"`, объекта и массива — `"object"`, функции — `"function"`, а для `null` — неожиданно тоже `"object"`.

`typeof null === "object"` — историческая ошибка языка. Её не исправляют, потому что JavaScript обязан сохранять обратную совместимость с вебом: слишком много старого кода могло бы сломаться.

### Примитивы и объекты

Примитивы ведут себя как самостоятельные значения. Если скопировать число из одной переменной в другую, они дальше живут независимо.

```js
let a = 10;
let b = a;

b = 20;

console.log(a);
console.log(b);
```

Будет выведено `10` и `20`.

С объектами иначе: переменная хранит ссылку на объект. При присваивании копируется не сам объект, а ссылка.

```js
const user1 = { name: "Anna" };
const user2 = user1;

user2.name = "Bob";

console.log(user1.name);
console.log(user2.name);
```

Обе строки выведут `Bob`, потому что `user1` и `user2` указывают на один и тот же объект.

По этой же причине два одинаково выглядящих объекта не равны друг другу.

```js
const a = {};
const b = {};
const c = a;

console.log(a === b);
console.log(a === c);
```

Первое сравнение даст `false`, второе — `true`. `{}` и `{}` создают два разных объекта, а `c = a` копирует ссылку на уже существующий объект.

Похожая идея есть и в Python с изменяемыми объектами: если две переменные ссылаются на один список, изменение через одну переменную видно через другую.

### Мини-практика

Предскажи вывод.

```js
let number = 10;
let copy = number;

copy = 20;

const first = { value: 10 };
const second = first;

second.value = 20;

console.log(number);
console.log(copy);
console.log(first.value);
console.log(second.value);
console.log(first === second);
console.log({ value: 20 } === { value: 20 });
```

Объясни отдельно, где копируется значение, а где копируется ссылка.

### Вывод

JavaScript не закрепляет тип за переменной, поэтому одна и та же переменная может хранить значения разных типов. Примитивы копируются как значения, а объекты, массивы и функции передаются через ссылки. Это важно для сравнения, мутаций и будущей работы с интерфейсом: элемент страницы тоже будет объектом, и разные переменные могут ссылаться на один и тот же узел.

## 4. Числа в JavaScript

На первый взгляд числа должны быть самой простой частью языка. Но именно с них часто начинается удивление: `0.1 + 0.2` оказывается не совсем `0.3`, `NaN` не равен самому себе, а большие целые числа могут «слипаться».

В JavaScript почти все обычные числа имеют тип `number`. И целые, и дробные значения хранятся как 64-битные числа с плавающей точкой по стандарту IEEE 754.

Вернёмся к первому вопросу из актуализации.

```js
console.log(0.1 + 0.2);
console.log(0.1 + 0.2 === 0.3);
```

Первый вывод будет `0.30000000000000004`, второй — `false`.

Это не уникальная причуда JavaScript. В Python и Go с числами с плавающей точкой можно встретить ту же проблему. Десятичные дроби вроде `0.1` и `0.2` не всегда можно точно представить в двоичной системе, поэтому они хранятся приблизительно. JavaScript кажется особенно странным потому, что исторически в нём долго не было отдельного обычного целочисленного типа: и `1`, и `3.14` были значениями одного типа `number`.

### Как сравнивать дробные числа

Дробные числа лучше сравнивать не через точное равенство, а через допустимую погрешность.

```js
const a = 0.1 + 0.2;
const b = 0.3;

console.log(Math.abs(a - b) < Number.EPSILON);
```

Для простых случаев такой проверки достаточно. В реальных финансовых расчётах обычно вообще не используют дробные `number`: деньги хранят в минимальных единицах, например в центах или копейках.

### `NaN`

`NaN` означает Not a Number. Он появляется, когда операция должна дать число, но не может получить корректный числовой результат.

```js
const value = Number("abc");

console.log(value);
console.log(value === NaN);
console.log(Number.isNaN(value));
```

Первый вывод — `NaN`, второй — `false`, третий — `true`. Особенность `NaN` в том, что он не равен ничему, даже самому себе. Поэтому проверять его нужно через `Number.isNaN`.

Это отвечает на вторую часть четвёртого вопроса из актуализации: `NaN === NaN` даёт `false`.

### `Infinity`

В JavaScript есть специальные числовые значения `Infinity` и `-Infinity`.

```js
console.log(1 / 0);
console.log(-1 / 0);
console.log(typeof Infinity);
```

Результат: `Infinity`, `-Infinity` и `"number"`. Это тоже часть модели IEEE 754: бесконечность — это не ошибка выполнения, а специальное числовое значение.

<a id="plus-zero-and-minus-zero"></a>

### `+0` и `-0`

В JavaScript есть `+0` и `-0`. В большинстве случаев они ведут себя как один и тот же ноль.

```js
console.log(+0 === -0);
```

Результат будет `true`.

Но различие можно увидеть, если делить на них.

```js
console.log(1 / +0);
console.log(1 / -0);
```

Будет `Infinity` и `-Infinity`.

Обычно в повседневном коде это не важно, но полезно знать: у равенства и чисел в JavaScript есть тонкие исторические и IEEE 754-детали.

### Безопасные целые числа

Обычный `number` не может точно представить любые большие целые числа. Безопасный диапазон ограничен от `Number.MIN_SAFE_INTEGER` до `Number.MAX_SAFE_INTEGER`.

```js
console.log(Number.MAX_SAFE_INTEGER);
console.log(Number.MAX_SAFE_INTEGER + 1);
console.log(Number.MAX_SAFE_INTEGER + 2);
console.log(Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2);
```

Последнее сравнение даст `true`, потому что за пределами безопасного диапазона разные математические целые могут представляться одним и тем же значением `number`.

Проверять числа помогают методы `Number.isInteger` и `Number.isSafeInteger`.

```js
console.log(Number.isInteger(10));
console.log(Number.isInteger(10.5));
console.log(Number.isSafeInteger(Number.MAX_SAFE_INTEGER));
console.log(Number.isSafeInteger(Number.MAX_SAFE_INTEGER + 1));
```

Для очень больших целых есть `bigint`, но подробно к нему лучше возвращаться тогда, когда действительно нужны точные большие целые.

### Мини-практика

Предскажи вывод и объясни.

```js
const result = 0.1 + 0.2;
const value = Number("JavaScript");
const big = Number.MAX_SAFE_INTEGER + 1;

console.log(result === 0.3);
console.log(Math.abs(result - 0.3) < Number.EPSILON);
console.log(value === NaN);
console.log(Number.isNaN(value));
console.log(Number.isSafeInteger(big));
```

### Вывод

Странности чисел в JavaScript в основном связаны не с «магией JS», а с IEEE 754 и историческим решением использовать один числовой тип для большинства задач. Для дробных значений нужна погрешность, для денег — целые минимальные единицы, для больших целых — `bigint`, а для `NaN` — `Number.isNaN`.

## 5. Приведение типов и сравнения

Одна из главных причин неожиданного поведения JavaScript — неявное приведение типов. Язык часто старается продолжить выполнение программы, даже если в выражении встретились значения разных типов.

Это прямое следствие его браузерной природы: скрипт на странице не должен был падать при каждой мелкой нестыковке, он должен был попытаться «сделать что-нибудь разумное».

Но цена такой гибкости — непредсказуемость, если не знать правил.

### Явное и неявное приведение

Явное приведение — это операция, при которой программист сам пишет, к какому типу привести значение.

```js
console.log(Number("42"));
console.log(String(42));
console.log(Boolean(""));
console.log(Boolean("JavaScript"));
```

Неявное приведение происходит, когда JavaScript делает это сам внутри операции.

```js
console.log("5" + 2);
console.log("5" - 2);
console.log(true + 1);
console.log(null + 1);
```

`"5" + 2` даст `"52"`, потому что `+` со строкой часто превращается в конкатенацию. `"5" - 2` даст `3`, потому что `-` не умеет вычитать строки и приводит операнды к числам. `true + 1` даст `2`, потому что `true` становится `1`. `null + 1` даст `1`, потому что `null` при числовом приведении становится `0`.

В Python выражение вроде `"5" + 2` даст `TypeError`. В Go смешивание строки и числа без явного преобразования тоже не пройдёт. JavaScript, наоборот, часто выбирает продолжить выполнение.

### Truthy и falsy

Когда JavaScript ждёт логическое значение, он приводит значение к `true` или `false`.

Falsy-значения:

- `false`,
- `0`,
- `-0`,
- `0n`,
- пустая строка,
- `null`,
- `undefined`,
- `NaN`.

Всё остальное обычно truthy, включая пустые массивы и пустые объекты.

```js
console.log(Boolean(""));
console.log(Boolean("0"));
console.log(Boolean([]));
console.log(Boolean({}));
```

Выводы будут `false`, `true`, `true`, `true`.

<a id="loose-and-strict-equality"></a>

### `==` и `===`

`===` сравнивает значения без приведения типов. `==` может сначала привести типы, а потом сравнить.

```js
console.log(5 == "5");
console.log(5 === "5");
console.log(null == undefined);
console.log(null === undefined);
```

Первое сравнение даёт `true`, потому что строка `"5"` приводится к числу. Второе — `false`, потому что типы разные. `null == undefined` — специальный случай нестрогого равенства: они равны при `==`, но не равны при `===`.

Практическое правило простое: по умолчанию используй `===`. Нестрогое равенство нужно только в осознанных случаях, например `value == null`, если ты специально хочешь поймать и `null`, и `undefined`.

<a id="array-loose-equality"></a>

### Почему `[] == ![]` даёт `true`

Вернёмся ко второму вопросу из актуализации.

```js
console.log([] == ![]);
```

Этот пример полезен не потому, что такой код стоит писать, а потому, что он показывает цепочку неявных преобразований.

Сначала `![]` становится `false`, потому что пустой массив — truthy, а отрицание truthy-значения даёт `false`. Получается `[] == false`.

При сравнении через `==` булево значение приводится к числу: `false` становится `0`, значит, выражение превращается в `[] == 0`.

Дальше JavaScript сравнивает объект и число, поэтому массив нужно привести к примитиву. Для массива сначала пробуется `valueOf()`, но он возвращает сам массив, то есть не примитив. Потом вызывается `toString()` и пустой массив превращается в пустую строку. Получается `"" == 0`.

Пустая строка при числовом приведении становится `0`, поэтому финально сравнивается `0 == 0` и результат — `true`.

Проверить отдельные шаги можно так.

```js
console.log(Boolean([]));
console.log(![]);
console.log(Number(false));
console.log([].valueOf());
console.log([].toString());
console.log(Number(""));
console.log([] == ![]);
```

Главный вывод здесь не «запомни, что `[] == ![]` истинно», а «не заставляй читателя держать в голове цепочку неявных приведений». Используй `===`.

### `typeof null`

Мы уже видели следующее.

```js
console.log(typeof null);
```

Результат — `"object"`. Это историческая ошибка первой версии языка. Её нельзя просто исправить, потому что JavaScript почти не ломает обратную совместимость: слишком много старого кода в интернете может зависеть от такого поведения.

Практический вывод: если проверяешь объект, отдельно отсеивай `null`.

```js
const value = null;

console.log(typeof value === "object");
console.log(value !== null && typeof value === "object");
```

### Мини-практика

Предскажи результат и объясни, где было приведение типов.

```js
console.log("10" + 5);
console.log("10" - 5);
console.log(Boolean("0"));
console.log("0" == false);
console.log("0" === false);
console.log(null == undefined);
console.log(null === undefined);
```

### Вывод

Приведение типов — часть характера JavaScript: язык старается быть живучим и продолжать работу на странице. Это удобно для коротких скриптов, но опасно в большом коде. Поэтому явные преобразования лучше неявных, а `===` почти всегда лучше `==`.

## 6. Функции и `this`

Функции в JavaScript — значения. Их можно записывать в переменные, передавать в другие функции, возвращать из функций и вызывать позже. Это одна из причин, почему JavaScript хорошо подошёл браузеру: обработчики действий пользователя, таймеры, запросы и реакции на события строятся вокруг функций.

Есть три распространённые формы записи функции.

```js
function sumDeclaration(a, b) {
  return a + b;
}

const sumExpression = function (a, b) {
  return a + b;
};

const sumArrow = (a, b) => a + b;

console.log(sumDeclaration(2, 3));
console.log(sumExpression(2, 3));
console.log(sumArrow(2, 3));
```

Все три вызова вернут `5`, но поведение у форм не одинаковое.

### Hoisting функций

Function declaration всплывает целиком, поэтому такую функцию можно вызвать до объявления.

```js
sayHi();

function sayHi() {
  console.log("Hi");
}
```

Function expression и arrow function, записанные в `const` или `let`, живут по правилам этих переменных. До строки объявления они находятся в TDZ.

```js
sayHi();

const sayHi = function () {
  console.log("Hi");
};
```

Этот код даст `ReferenceError`.

### Обычные и стрелочные функции

Стрелочные функции удобны для коротких функций, но у них нет собственного `this` и собственного `arguments`.

У обычной функции есть специальный объект `arguments`.

```js
function showArguments() {
  console.log(arguments);
}

showArguments(1, 2, 3);
```

У стрелочной функции своего `arguments` нет. В современном коде вместо него обычно используют rest-параметры.

```js
const showArgs = (...args) => {
  console.log(args);
};

showArgs(1, 2, 3);
```

Разница важна не потому, что нужно активно пользоваться `arguments`, а потому что стрелочная функция — это не просто короткая запись обычной. У неё другая модель.

### `this` определяется вызовом

В обычной функции `this` определяется не местом объявления, а способом вызова.

```js
"use strict";

const user = {
  name: "Anna",
  sayHello() {
    console.log(this.name);
  }
};

user.sayHello();

const fn = user.sayHello;
fn();
```

В первом вызове `this` равен `user`, потому что функция вызвана как метод: `user.sayHello()`. Во втором вызове функция та же самая, но вызвана как обычная функция: `fn()`. В strict mode `this` будет `undefined` и попытка прочитать `this.name` приведёт к `TypeError`.

Это важное отличие от Python, где метод явно принимает `self`, и от Go, где receiver указан в объявлении метода. В JavaScript функция может быть «одолжена» разным объектам, а `this` будет определён в момент вызова. Исторически это хорошо подходило для гибких браузерных сценариев, но создаёт частую ошибку «потерянного `this`».

### Стрелочная функция как метод

```js
const user = {
  name: "Anna",
  sayHello: () => {
    console.log(this.name);
  }
};

user.sayHello();
```

Стрелочная функция не получает `this` из объекта `user`. Она берёт `this` из внешнего окружения, где была создана. Поэтому такой метод не должен ожидать, что `this === user`.

Если внутри метода нужен `this`, используй обычную функцию или короткий синтаксис метода.

```js
const user = {
  name: "Anna",
  sayHello() {
    console.log(this.name);
  }
};

user.sayHello();
```

### Мини-практика

Предскажи вывод.

```js
"use strict";

const user = {
  name: "Anna",
  showName() {
    console.log(this.name);
  }
};

const admin = {
  name: "Bob",
  showName: user.showName
};

user.showName();
admin.showName();

const fn = user.showName;
fn();
```

Объясни, почему функция одна и та же, но `this` меняется.

### Вывод

Функции в JavaScript — значения, поэтому их легко передавать и вызывать позже. Но из-за этого важно различать, как функция создана и как вызвана. Function declaration всплывает целиком, function expression и arrow function зависят от переменной, обычные функции получают `this` при вызове, а стрелочные функции собственного `this` не имеют.

## 7. Замыкания

Если функция может быть возвращена из другой функции и вызвана позже, возникает вопрос: что происходит с переменными внешней функции? Исчезают ли они после завершения вызова?

Ответ JavaScript: не всегда. Если внутренняя функция продолжает использовать переменные внешней области видимости, JavaScript сохраняет эти переменные. Это и есть замыкание.

```js
function createCounter() {
  let count = 0;

  return function () {
    count++;
    console.log(count);
  };
}

const counter = createCounter();

counter();
counter();
counter();
```

Вызовы выведут `1`, `2`, `3`. Внешняя функция `createCounter` уже завершилась, но возвращённая функция продолжает помнить переменную `count`.

Важно: замыкание захватывает переменную, а не просто значение в момент создания. Функция не фотографирует `count = 0`, а сохраняет доступ к самой переменной `count`.

В Python есть похожая идея: функции тоже могут помнить переменные внешней области, и там тоже можно встретить ловушку позднего связывания в циклах. Поэтому мысль «замыкается переменная, а не снимок значения» не уникальна для JavaScript.

### Как увидеть замыкание в DevTools

Поставь breakpoint на строку `count++` и вызови `counter()`. Когда выполнение остановится, открой панель **Scope**. Там будет видно окружение функции, включая переменную `count`. В Chrome DevTools она обычно находится в разделе **Closure**.

Это лучший способ понять замыкания: не только прочитать определение, но и увидеть захваченную переменную глазами.

### Несколько независимых окружений

Каждый вызов внешней функции создаёт новое окружение.

```js
function createCounter() {
  let count = 0;

  return function () {
    count++;
    console.log(count);
  };
}

const a = createCounter();
const b = createCounter();

a();
a();
b();
a();
```

Вывод будет `1`, `2`, `1`, `3`. Счётчики независимы, потому что `a` и `b` замкнули разные переменные `count`.

### Реальный пример: debounce

Замыкания постоянно встречаются во фронтенде. Например, debounce откладывает выполнение функции до тех пор, пока вызовы не прекратятся на некоторое время. Это нужно, например, в поисковой строке: пользователь печатает пять букв, а запрос на сервер хочется отправить один раз — после паузы.

```js
function debounce(callback, delay) {
  let timerId;

  return function (...args) {
    clearTimeout(timerId);

    timerId = setTimeout(() => {
      callback(...args);
    }, delay);
  };
}

const search = debounce((query) => {
  console.log("Ищем:", query);
}, 500);

search("j");
search("ja");
search("jav");
search("java");
search("javascript");
```

В итоге выполнится только последний поиск: `"javascript"`. Переменная `timerId` живёт во внешней функции `debounce`, но возвращённая функция продолжает её помнить. Это приватное состояние: снаружи мы не можем напрямую обратиться к `timerId`, но функция имеет к нему доступ.

### `var` в цикле: возвращаемся к вопросу из актуализации

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

Вывод будет `3`, `3`, `3`.

Причина в том, что `var` имеет функциональную область видимости: в цикле есть одна общая переменная `i`. `setTimeout` откладывает выполнение функций; сначала цикл заканчивается, `i` становится `3`, и только потом все три функции читают одну и ту же переменную.

С `let` результат другой.

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

Теперь вывод будет `0`, `1`, `2`, потому что `let` в цикле создаёт новую привязку `i` для каждой итерации.

Важно не заучить пример `var + setTimeout`, а понять идею: несколько функций могут смотреть на одну и ту же захваченную переменную, а могут — на разные переменные, если область видимости создаёт новые привязки.

### Мини-практика

Предскажи вывод.

```js
function createPair() {
  let first = 0;
  let second = 10;

  return {
    incFirst() {
      first++;
      console.log(first);
    },
    decSecond() {
      second--;
      console.log(second);
    },
    showBoth() {
      console.log(first, second);
    }
  };
}

const pair = createPair();

pair.incFirst();
pair.incFirst();
pair.decSecond();
pair.showBoth();

console.log(pair.first);
console.log(pair.second);
```

Объясни:

- какие переменные захвачены замыканием;
- почему методы видят одни и те же `first` и `second`;
- почему `pair.first` и `pair.second` не дают доступа к этим переменным.

### Вывод

Замыкание — это функция вместе с переменными внешнего окружения, которые она продолжает помнить. Эта механика используется в счётчиках, обработчиках событий, debounce, приватном состоянии и библиотеках. Во фронтенде замыкания встречаются постоянно: почти каждая функция, созданная внутри другой функции, что-то «помнит» из места, где была создана.

## Практика: комбинируем темы

Здесь задания объединяют несколько тем сразу. Работай по схеме: предсказал → проверил → объяснил.

### 1. Scope, `const` и ссылка

```js
const user = { name: "Anna" };

if (true) {
  const user = { name: "Bob" };
  user.name = "Kate";
  console.log(user.name);
}

console.log(user.name);
```

Объясни, почему здесь два разных `user`, почему `const` не запрещает менять свойство объекта и какие значения будут выведены.

### 2. Приведение типов и сравнение

```js
console.log("10" + 5);
console.log("10" - 5);
console.log(Boolean("0"));
console.log("0" == false);
console.log("0" === false);
```

Объясни, где JavaScript приводит к строке, где к числу, где к boolean и почему `==` и `===` дают разные результаты.

### 3. Числа и `NaN`

```js
const value = Number("JavaScript");
const sum = 0.1 + 0.2;

console.log(value === NaN);
console.log(Number.isNaN(value));
console.log(sum === 0.3);
console.log(Math.abs(sum - 0.3) < Number.EPSILON);
```

Объясни отдельно поведение `NaN` и поведение дробных чисел.

```js
"use strict";

const admin = {

user.showName();
admin.showName();

const fn = user.showName;
fn();
```

Объясни, почему функция одна и та же, но `this` меняется.

## Если кратко

JavaScript — динамический язык: тип имеет значение, а не переменная. Поэтому одна и та же переменная может хранить значения разных типов, если она объявлена через `let`.

`const` запрещает переприсвоить переменную, но не делает объект неизменяемым. Если `const user` хранит ссылку на объект, свойства этого объекта всё ещё можно менять.

`let` и `const` имеют блочную область видимости и TDZ. `var` имеет функциональную область видимости и старое поведение hoisting, при котором переменная до присваивания видна как `undefined`.

Примитивы копируются как значения. Объекты, массивы и функции сравниваются по ссылкам. Поэтому `{}` не равно `{}`, а две переменные, указывающие на один объект, видят одни и те же изменения.

Числа типа `number` хранятся в формате IEEE 754. Поэтому дробная арифметика может быть неточной, `NaN` не равен самому себе, есть `Infinity`, `+0` и `-0`, а большие целые числа выходят за безопасный диапазон. Это не только проблема JavaScript: с floating point сталкиваются и в Python, и в Go.

JavaScript часто выполняет неявное приведение типов. Это часть его «прощающего» характера как языка для браузера, но из-за этого `==` может давать неожиданные результаты. По умолчанию используй `===`.

Функции в JavaScript — значения. Их можно передавать, возвращать и вызывать позже. Обычные функции получают `this` при вызове, и `this` зависит от способа вызова. Стрелочные функции собственного `this` и собственного `arguments` не имеют.

Замыкание — это функция, которая продолжает помнить переменные внешней области видимости. Замыкания лежат в основе счётчиков, фабрик функций, приватного состояния и многих фронтенд-паттернов.

## Финальный синтез: что это за язык

Теперь вернёмся к вопросу из начала:

> как JavaScript думает?

JavaScript — это динамичный, повсеместный и очень практичный язык. Он появился как способ быстро оживлять страницы в браузере, поэтому он легко запускается, встроен в пользовательскую среду и часто старается продолжить выполнение вместо того, чтобы сразу упасть.

Эта практичность объясняет многое:

- приведение типов выросло из желания быть гибким и не ломать страницу из-за мелкой нестыковки;
- `var` и `typeof null` остались из-за обратной совместимости со старым вебом;
- числа ведут себя по правилам IEEE 754, а не по школьной десятичной арифметике;
- функции как значения идеально подошли для реакций на действия пользователя;
- `this`, зависящий от вызова, позволяет одной функции быть методом разных объектов, но создаёт ошибку «потерянного `this`»;
- замыкания дают функциям память и позволяют хранить состояние между вызовами.

JavaScript хорош там, где нужно оживить интерфейс, отреагировать на пользователя, изменить страницу, проверить форму, отправить запрос, обновить данные без перезагрузки. Он работает везде, где есть браузер.

Но у него есть границы. Для больших кодовых баз часто добавляют TypeScript, потому что динамическая типизация хуже ловит ошибки заранее. Для денег не используют дробные `number`. Для тяжёлых вычислений выбирают специальные инструменты или другие языки.

Главная мысль недели:

> странности JavaScript не случайны. Они выросли из его роли: быстро оживлять веб, работать везде и не ломать старый код.

## ★ Глубже

Базовой модели хватает, чтобы не путаться в приведении, числах, `this` и замыканиях. Но у JavaScript глубокое дно, и есть вопросы, которые однажды тебя зацепят.

Раздел необязательный. Если тяжело идёт основное, спокойно пропускай.

<a id="все-говорят-используй--а-правила--вообще-стоит-учить-наизусть"></a>

### ❓ Все говорят «используй `===`». А правила `==` вообще стоит учить наизусть?

Нет, и это хорошая новость. Алгоритм нестрогого равенства реально существует и реально запутанный, но смысл недели не в том, чтобы его вызубрить, а в том, чтобы почти никогда к нему не обращаться.

Почти всегда правильный ответ — `===`. Единственное место, где `==` иногда используют осознанно, — проверка `x == null`, которая разом ловит и `null`, и `undefined`.

Ты вспомнишь это, когда наткнёшься на чужой код с `==` и захочешь понять, баг это или намерение.

Куда смотреть дальше:

- [MDN: Equality comparisons and sameness](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Equality_comparisons_and_sameness);
- [MDN: Equality](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Equality);
- [MDN: Strict equality](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Strict_equality).

<a id="typeof-null--это-правда-object-почему-не-починят"></a>

### ❓ `typeof null` — это правда `"object"`? Почему не починят?

Правда. Это баг из самой первой версии JavaScript: внутреннее представление `null` совпало по тегу с объектами. Исправить нельзя: слишком много кода в мире уже полагается на это поведение, и «починка» сломала бы интернет.

JavaScript вообще почти ничего не выбрасывает из языка ради обратной совместимости. Это многое объясняет в его странностях.

Тебя это укусит, когда напишешь проверку вроде `typeof value === "object"` и удивишься, что `null` тоже туда попал.

Куда смотреть дальше:

- [MDN: typeof](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/typeof);
- [MDN: null](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/null).

<a id="почти-всегда-норм-а-есть-способ-сравнить-честнее"></a>

### ❓ `===` почти всегда норм. А есть способ сравнить «честнее»?

Да, это `Object.is`.

`===` почти везде делает то, что нужно, но есть два тонких случая: `NaN === NaN` даёт `false`, а `+0 === -0` даёт `true`. `Object.is` ведёт себя иначе.

```js
console.log(NaN === NaN);
console.log(Object.is(NaN, NaN));

console.log(+0 === -0);
console.log(Object.is(+0, -0));
```

В обычном коде форм и кнопок `Object.is` почти не нужен. Но он всплывёт, когда будешь писать сравнение состояний, мемоизацию или разбираться с библиотечным кодом.

Куда смотреть дальше:

- [MDN: Object.is](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/is).

<a id="замыкание-держит-переменные-а-не-утекает-ли-из-за-этого-память"></a>

### ❓ Замыкание держит переменные. А не утекает ли из-за этого память?

Может. Раз замыкание держит ссылку на переменные своего окружения, эти переменные не освобождаются, пока жива функция.

Обычно это именно то, что нужно. Но если замыкание случайно захватило что-то большое — огромный массив или тяжёлый объект — и при этом долго живёт, память не вернётся.

```js
function createHandler() {
  const bigData = new Array(1_000_000).fill("data");

  return function () {
    console.log(bigData.length);
  };
}

const handler = createHandler();
handler();
```

Ты вспомнишь это, когда вкладка со временем начнёт тяжелеть, интерфейс будет тормозить, и придётся идти во вкладку **Memory** в DevTools.

Куда смотреть дальше:

- [MDN: Closures](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Closures);
- [Chrome DevTools Memory](https://developer.chrome.com/docs/devtools/memory-problems).

<a id="если-01--02-неточно-как-вообще-считать-деньги"></a>

### ❓ Если `0.1 + 0.2` неточно, как вообще считать деньги?

Не во float.

Для денег обычная практика — хранить и считать в наименьших единицах: не `10.99`, а `1099` центов. Складывать целые числа, а форматировать уже при выводе пользователю.

```js
const priceInCents = 1099;
const deliveryInCents = 525;

console.log(priceInCents + deliveryInCents);
```

А когда нужны действительно большие точные целые, за пределами `Number.MAX_SAFE_INTEGER`, есть отдельный тип `bigint`.

```js
const big = 9007199254740993n;

console.log(big);
console.log(typeof big);
```

`BigInt` не смешивается автоматически с обычными числами, и это хорошо: JavaScript заставляет явно решить, в какой числовой модели ты работаешь.

Ты вспомнишь это в первом же проекте, где есть цены, балансы или счётчики на миллиарды.

Куда смотреть дальше:

- [MDN: Number](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number);
- [MDN: BigInt](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/BigInt);
- [MDN: Number.MAX_SAFE_INTEGER](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER).

<a id="как-лучше-смотреть-область-видимости-this-и-замыкания-через-consolelog-или-debugger"></a>

### ❓ Как лучше смотреть область видимости, `this` и замыкания: через `console.log` или Debugger?

Для результата подойдёт `console.log`. Для понимания лучше Debugger.

Поставь breakpoint внутри функции и смотри панели **Scope** и **Call Stack**. Для замыканий особенно полезен раздел **Closure** в Scope: там видно переменные, которые функция удерживает.

Ты вспомнишь это, когда `this` внезапно окажется `undefined`, обработчик увидит старое значение или замыкание будет хранить не то, что ты ожидаешь.

Куда смотреть дальше:

- [Chrome DevTools JavaScript debugging](https://developer.chrome.com/docs/devtools/javascript);
- [MDN: debugger statement](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/debugger).

## Самопроверка

Ответь без запуска кода. Важно не угадать, а объяснить.

### 1. Область видимости

```js
if (true) {
  const name = "Anna";
  let age = 20;
  var city = "Tallinn";
}

console.log(city);
console.log(name);
```

Почему одна переменная доступна снаружи блока, а другая — нет?

### 2. `const` и объект

```js
const user = {
  name: "Anna"
};

user.name = "Bob";

console.log(user.name);
```

Почему `const` не запрещает изменить свойство объекта?

### 3. TDZ

```js
{
  console.log(score);

  let score = 100;
}
```

Почему это не то же самое, что `var`?

### 4. Объекты и ссылки

```js
const first = { value: 10 };
const second = first;
const third = { value: 10 };

second.value = 20;

console.log(first.value);
console.log(first === second);
console.log(first === third);
```

Объясни через ссылки.

### 5. Числа

```js
const result = 0.2 + 0.4;

console.log(result);
console.log(result === 0.6);
```

Почему результат может удивить и как сравнить такие числа безопаснее?

### 6. Безопасные целые

```js
const value = Number.MAX_SAFE_INTEGER + 1;

console.log(Number.isInteger(value));
console.log(Number.isSafeInteger(value));
```

Почему число может быть целым, но небезопасным?

### 7. Приведение типов

```js
console.log("10" + 5);
console.log("10" - 5);
console.log("" == false);
console.log("" === false);
```

Где JavaScript приводит типы, а где нет?

### 8. `this`

```js
"use strict";

const user = {
  name: "Anna",
  showName() {
    console.log(this.name);
  }
};

const admin = {
  name: "Bob",
  showName: user.showName
};

admin.showName();
```

Почему функция та же самая, но `this` указывает на `admin`?

### 9. Замыкание

```js
function createMultiplier(multiplier) {
  return function (number) {
    return number * multiplier;
  };
}

const double = createMultiplier(2);
const triple = createMultiplier(3);

console.log(double(5));
console.log(triple(5));
```

Почему `double` и `triple` помнят разные значения `multiplier`?
