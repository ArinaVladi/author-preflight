# Продвинутые механизмы JavaScript

К этому моменту мы прошли язык почти целиком. Разобрали, как JavaScript себя ведёт: приведение типов, всплытие ошибок, поведение операторов. Разобрали объектную модель и прототипы. Разобрали DOM: как код взаимодействует со страницей. Разобрали асинхронность и сеть: как код ждёт ответа, не замораживая интерфейс. Этого достаточно, чтобы писать работающие интерфейсы.

Но если открыть исходный код любого фреймворка или библиотеки, там обнаружатся механизмы, которых мы ещё не касались. Библиотека умеет проходиться `for...of` по объектам, которые совсем не похожи на массив. Она перехватывает чтение и запись свойств, хотя ты не просил её об этом. Она хранит данные так, что они не мешают сборщику мусора, даже если ты забыл их удалить. Всё это не случайные трюки, а конкретные механизмы языка: протокол итерации, генераторы, `Map` и `Set`, `WeakMap` и `WeakSet`, `Symbol`, `Proxy` и `Reflect`, модули. Эта неделя завершает блок перед контрольной по JS, и у неё двойная задача: открыть капот у инструментов, которыми предстоит пользоваться дальше, и собрать всю картину языка в одну модель.

По традиции небольшой квиз перед началом.

1. Ты пишешь `for...of` по своему объекту, не по массиву. Что нужно объекту, чтобы это заработало? А что нужно для `[...obj]`?
2. Вот генератор:
   ```js
   function* nums() {
     let i = 0;
     while (true) yield i++;
   }
   ```
   Зависнет ли программа при его вызове? Почему?
3. Нужен словарь, где ключами будут не строки, а объекты. Подойдёт обычный объект `{}`? Что случится с ключом-объектом?
4. Объект обёрнут в `Proxy` с ловушкой `get`. Что произойдёт в момент, когда кто-то прочитает `proxy.name`?

Если ты освоишь эту тему, ты сможешь:

- написать собственный итерируемый объект и объяснить, почему `for...of`, spread и деструктуризация работают с помощью одного и того же механизма;
- писать генераторы, в том числе бесконечные, и понимать, почему бесконечный генератор не блокирует программу;
- выбирать между объектом, `Map` и `Set` для конкретной задачи и обосновывать выбор, а не действовать по привычке;
- объяснить, почему кеш на `WeakMap` не приводит к утечке памяти, а кеш на обычном `Map` иногда может;
- использовать `Symbol` там, где важно, чтобы ключ гарантированно не столкнулся с чужим;
- реализовать перехват операций над объектом через `Proxy` и объяснить, как на этом механизме устроена реактивность фреймворков;
- организовать код в ES-модули и применить динамический импорт для ленивой загрузки;
- сформулировать, что за язык JavaScript, что он решает хорошо, что плохо и почему вокруг этих ограничений вырос весь современный инструментарий.

## 1. Протокол итерации

Мы уже давно пишем `for (const item of array)`, `for (const char of string)`, `[...array]`, `const [a, b] = array`. Всё это работает настолько привычно, что вопрос о том, почему это вообще работает, обычно не возникает.

Попробуем то же самое на собственном объекте:

```js
const rangeObj = { from: 1, to: 5 };

for (const num of rangeObj) {
  console.log(num);
}
```

Этот код упадёт с ошибкой `TypeError: rangeObj is not iterable`. Это удивляет, если считать `for...of` универсальным синтаксисом, способным перебрать любой объект без исключений. На самом деле это не так: `for...of` перебирает не любой объект, а только тот, что подчиняется конкретному протоколу.

> **Итерируемый объект (iterable)** — объект, у которого есть метод с ключом `Symbol.iterator`, возвращающий итератор.
>
> **Итератор (iterator)** — объект с методом `next()`, который при каждом вызове возвращает `{ value, done }`: очередное значение и флаг, закончилась ли последовательность.

Массив, строка, `Map`, `Set` следуют этому протоколу, поэтому по ним можно писать `for...of`. Обычный объект ему не следует: `{ from: 1, to: 5 }` не подчиняется протоколу просто потому, что мы не реализовали для него `Symbol.iterator`.

Здесь `Symbol.iterator` не название метода в привычном смысле, а конкретное значение особого типа `symbol`, встроенное в язык (подробнее о том, что такое `Symbol`, чуть дальше, пока достаточно знать, что это специальный, зарезервированный движком ключ). Когда `for...of` встречает объект, он не перебирает его свойства напрямую. Он вызывает `obj[Symbol.iterator]()`, получает в ответ итератор и дальше раз за разом вызывает у этого итератора `next()`, пока не получит `done: true`.

Перепишем объявление `rangeObj`, добавив ему этот метод:

```js
const rangeObj = {
  from: 1,
  to: 5,
  [Symbol.iterator]() {
    let current = this.from;
    const last = this.to;
    return {
      next() {
        if (current <= last) {
          return { value: current++, done: false };
        }
        return { value: undefined, done: true };
      }
    };
  }
};

for (const num of rangeObj) {
  console.log(num);
}
// 1 2 3 4 5
```

**Разбор.** `for...of` вызывает `rangeObj[Symbol.iterator]()`. Этот метод выполняется один раз и возвращает объект с `next()`, который замыкается на переменных `current` и `last`. Первый вызов `next()`: `current` равен 1, это не больше `last` (5), поэтому возвращается `{ value: 1, done: false }`, а `current` увеличивается до 2. Тело цикла выполняется со значением 1. Второй вызов `next()` повторяет то же самое с `current = 2` и так далее. Когда `current` становится равным 6, условие `current <= last` не выполняется, и `next()` возвращает `{ value: undefined, done: true }`. На этом цикл останавливается.

Важно, что это тот же механизм, что и у встроенных типов. Можно получить итератор массива вручную и убедиться, что он устроен так же:

```js
const arr = [10, 20, 30];
const it = arr[Symbol.iterator]();
it.next(); // { value: 10, done: false }
it.next(); // { value: 20, done: false }
```

**Вывод.** `for...of` не обладает встроенной способностью перебирать любые объекты сам по себе: он делегирует эту работу конкретному методу `Symbol.iterator`, который объект обязан предоставить. Это отвечает и на вторую часть первого вопроса из начала темы: spread (`[...rangeObj]`) и деструктуризация (`const [a, b] = rangeObj`) устроены точно так же, оба вызывают `Symbol.iterator` и читают значения через `next()`. Это один протокол, а не три разных механизма, которые случайно ведут себя похоже.

**Практика.** Реализуй итерируемый объект `Playlist`, хранящий массив треков (`{ title, duration }`), так, чтобы `for...of` перебирал треки по порядку, а `[...playlist]` возвращал массив треков. Дополнительно: сделай так, чтобы деструктуризация `const [first, second] = playlist` доставала первые два трека.

Это уже отвечает на первый вопрос из начала темы: обычному объекту нужен метод `[Symbol.iterator]`, возвращающий итератор с `next()`; без него ни `for...of`, ни spread по объекту работать не будут.

## 2. Генераторы: ленивая последовательность без ручного `next()`

Мы вручную написали метод `[Symbol.iterator]()`, который держит замыкание на `current` и `last` и вручную собирает объект `{ value, done }` на каждом шаге. Для простого диапазона это терпимо, но стоит логике усложниться (например, нужно отфильтровать значения по условию, перемежать два источника или остановиться по внешнему сигналу), и ручное отслеживание состояния быстро превращается в путаницу из переменных и условий.

Генераторы решают именно эту задачу: они дают возможность писать логику последовательности как обычный код сверху вниз, а протокол итератора реализуется автоматически.

Генератор объявляется через `function*`, а точки, где он отдаёт значение, помечаются `yield`:

```js
function* range(from, to) {
  for (let i = from; i <= to; i++) {
    yield i;
  }
}

for (const num of range(1, 5)) {
  console.log(num);
}
// 1 2 3 4 5
```

Это тот же результат, что и у ручной реализации из раздела 1, но без явного объекта-итератора. Причина в том, что вызов функции-генератора не выполняет её тело сразу. `range(1, 5)` возвращает специальный объект-генератор: он сам является итератором (у него есть `next()`) и сам является итерируемым (у него есть `[Symbol.iterator]`, возвращающий сам себя). Поэтому генератор можно сразу использовать в `for...of`.

**Разбор.** Первый вызов `next()` начинает выполнение тела функции с самого начала и доходит до первого `yield i` при `i = 1`. В этот момент выполнение **приостанавливается**, значение 1 возвращается наружу как `{ value: 1, done: false }`, а всё состояние функции (включая значение `i` и то, на каком шаге цикла она находится) сохраняется. Следующий вызов `next()` не начинает функцию заново, а продолжает выполнение ровно с того места, где она остановилась: цикл увеличивает `i` до 2 и доходит до следующего `yield`. Так продолжается, пока цикл `for` не завершится: тогда функция доходит до конца тела, и итоговый `next()` возвращает `{ value: undefined, done: true }`.

Если ты писал генераторы на Python, идея та же: функция с `yield` выполняется не сразу целиком, а по частям, до следующего `yield`. Различия в деталях (в JS нужно явно вызывать `.next()`, а значения оборачиваются в `{ value, done }`), но ментальная модель одна и та же.

У сохранённого состояния есть обратная сторона. Генератор, дошедший до конца тела, не возвращается к началу, и каждый следующий `next()` отдаёт `{ value: undefined, done: true }`. Его `[Symbol.iterator]()` возвращает тот же самый объект, а не новый итератор, поэтому второй проход продолжается с того места, где закончился первый:

```js
const g = range(1, 3);
[...g]; // [1, 2, 3]
[...g]; // []
```

С `rangeObj` из раздела 1 такого не происходит. Каждый `for...of` вызывает его `[Symbol.iterator]()` и получает свежий итератор, у которого `current` снова равен `from`. Генератор же одноразовый итератор. Если последовательность нужно пройти несколько раз, хранить стоит не сам генератор, а функцию, которая его создаёт. В цикле выше так и сделано, потому что каждый вызов `range(1, 5)` даёт новый генератор с собственным состоянием.

Теперь вернёмся ко второму вопросу из начала темы.

```js
function* nums() {
  let i = 0;
  while (true) {
    yield i++;
  }
}
```

Что здесь произойдёт при вызове `nums()`? Сравним с обычной функцией:

```js
function numsBad() {
  let i = 0;
  while (true) {
    i++;
  }
  return i; // никогда не будет достигнуто
}

numsBad(); // программа зависает прямо здесь
```

Обычная функция выполняется от начала до конца за один непрерывный проход. Если внутри бесконечный цикл, вызов функции никогда не завершится: программа зависнет в этот же момент.

С генератором всё иначе:

```js
const gen = nums(); // не зависает: тело ещё ни разу не выполнялось
gen.next(); // { value: 0, done: false }
gen.next(); // { value: 1, done: false }
gen.next(); // { value: 2, done: false }
```

`nums()` только создаёт объект-генератор — тело функции ещё не запускалось. Каждый `next()` выполняет ровно один шаг до очередного `yield` и снова останавливается. Программа никогда не пытается пройти весь бесконечный цикл разом. Она выполняет его по одному витку за раз, ровно столько раз, сколько мы сами попросили. Это и есть ленивость: значения производятся по требованию, а не заранее.

Здесь легко сделать поспешный вывод: если генератор ленивый, о бесконечности можно вообще не думать. Это ошибка. Ленивость защищает от зависания только сам вызов и `next()`. Она не защищает от неосторожного потребления:

```js
for (const n of nums()) {
  console.log(n);
}
// зациклится навсегда
```

`for...of` не останавливается сам: он продолжает звать `next()`, пока не получит `done: true`, а для `nums()` это никогда не случится. Безопасным бесконечный генератор становится только тогда, когда мы сами решаем, сколько значений взять: через `break` или ограниченное число вызовов `next()`.

```js
for (const n of nums()) {
  if (n > 4) break;
  console.log(n);
}
// 0 1 2 3 4
```

Это и есть полный ответ на второй вопрос: вызов и создание бесконечного генератора не вешают программу, потому что тело выполняется по шагам, а не целиком. Но потребление без ограничителя всё равно зависнет: генератор делает бесконечность безопасной для *определения*, а не освобождает от необходимости думать о её *потреблении*.

После `break` генератор не просто ставится на паузу. Когда `for...of` прерывается досрочно через `break`, `return` или исключение, он вызывает у итератора метод `return()`. У генератора этот метод завершает выполнение так, будто на месте текущего `yield` стоит `return`. Блоки `finally` внутри генератора при этом выполняются, поэтому там удобно освобождать ресурсы. Продолжить такой генератор уже нельзя:

```js
const gen = nums();
for (const n of gen) {
  if (n > 2) break;
}
gen.next(); // { value: undefined, done: true }
```

Метод `gen.return(value)` можно вызвать и вручную, и тогда он вернёт `{ value, done: true }`. Парный ему `gen.throw(error)` бросает исключение прямо в точке, где генератор остановился. Если вокруг этого `yield` есть `try...catch`, генератор может обработать ошибку и продолжить работу. Если обработчика нет, исключение вылетает наружу из вызова `throw()`, а генератор завершается.

У генераторов есть и другой инструмент: делегирование через `yield*` другому итерируемому объекту.

```js
function* chain(...iterables) {
  for (const it of iterables) {
    yield* it;
  }
}

for (const x of chain([1, 2, 3], 'ab', range(10, 12))) {
  console.log(x);
}
// 1 2 3 a b 10 11 12
```

`yield* it` — это, по сути, сокращённая запись команды пройти по `it` и отдать наружу каждое его значение, причём `it` может быть чем угодно итерируемым: массивом, строкой, другим генератором. Это ещё раз показывает, что генератор не отдельный от протокола итерации механизм, а его удобная реализация: генератор умеет как производить значения (`yield`), так и потреблять любой другой источник значений (`yield*`), не выходя за рамки одного и того же протокола из раздела 1.

**Вывод.** Генератор — это функция, которая может приостанавливаться на `yield` и возобновляться с сохранённым состоянием. Это даёт ленивость: последовательность, в том числе бесконечная, производится по одному значению за раз, только когда её запрашивают. Генератор автоматически реализует протокол итерации, поэтому он самый простой способ сделать объект итерируемым: вместо ручного объекта с замыканием и `next()`, как в разделе 1, достаточно написать функцию с `yield` и циклом внутри.

**Практика.** Напиши генератор `fibonacci(count)`, отдающий первые `count` чисел Фибоначчи (0, 1, 1, 2, 3, 5, ...), и отдельно бесконечный генератор `evenNumbers()`, выдающий последовательные чётные числа начиная с 0.

## 3. Map и Set: когда объект и массив не справляются

Мы много раз использовали обычный объект как словарь — набор пар «ключ — значение». Пока ключи строковые, это работает:

```js
const words = ['react', 'vue', 'react', 'svelte', 'vue', 'react'];
const counts = {};

for (const word of words) {
  counts[word] = (counts[word] || 0) + 1;
}
// { react: 3, vue: 2, svelte: 1 }
```

Здесь всё честно. Проблема начинается, когда ключом должна быть не строка, а сам объект. Представим, что нужно посчитать клики по каждой кнопке интерфейса, а кнопки представляют собой объекты конфигурации:

```js
const saveBtn = { id: 'save' };
const cancelBtn = { id: 'cancel' };

const clicksObj = {};
clicksObj[saveBtn] = 5;
clicksObj[cancelBtn] = 2;

console.log(clicksObj);
```

Что выведется? Не то, что интуитивно ожидается. Ключи объекта (за исключением символов, о которых пойдёт речь в разделе 5) могут быть только строками. Если в качестве ключа передать объект, JavaScript неявно приводит его к строке через вызов `toString()`. Для обычного объекта это всегда одна и та же строка: `'[object Object]'`. Поэтому `clicksObj[saveBtn]` и `clicksObj[cancelBtn]` оказываются одним и тем же ключом, и второе присваивание просто перезаписывает первое:

```js
console.log(clicksObj);
// { '[object Object]': 2 }
```

Это прямой ответ на третий вопрос из начала темы: обычный объект для ключей-объектов не подходит, потому что любой нестроковый ключ превращается в одну и ту же служебную строку и разные объекты сталкиваются друг с другом.

`Map` устроен иначе: он хранит пары «ключ — значение» как отдельную структуру данных, а не как свойства объекта, поэтому ключи не проходят через приведение к строке и остаются собой.

```js
const clicksMap = new Map();
clicksMap.set(saveBtn, 5);
clicksMap.set(cancelBtn, 2);

clicksMap.get(saveBtn); // 5
clicksMap.get(cancelBtn); // 2
clicksMap.size; // 2
```

**Разбор.** `saveBtn` и `cancelBtn` остаются разными ключами, потому что `Map` сравнивает ключи не через строковое приведение, а по алгоритму, близкому к `===` (с одним отличием: в `Map` `NaN` считается равным самому себе, в отличие от `===`, где `NaN !== NaN`; это редкая деталь, но при отладке она может сбить с толку). У `Map` есть честное свойство `size`, а порядок перебора всегда совпадает с порядком добавления записей. На пятой неделе, разбирая объекты и прототипы, мы упоминали `Object.create(null)`: способ избавиться от унаследованных ключей вроде `toString` или `constructor`, которые могут случайно столкнуться с ключом словаря. `Map` решает эту же проблему иначе: у него вообще нет отдельного слота под свойства объекта, это специальная структура для пар «ключ — значение», поэтому вопрос об унаследованных ключах для `Map` просто не возникает.

Соседняя проблема — не пары «ключ — значение», а просто уникальность значений. Наивная дедупликация массива через `indexOf` работает, но не бесплатно:

```js
function dedupe(arr) {
  return arr.filter((item, index) => arr.indexOf(item) === index);
}
```

Для каждого элемента здесь заново ищется его первое вхождение по всему массиву, то есть при росте массива время работы растёт квадратично. `Set`, коллекция, которая по определению хранит только уникальные значения, решает это прямо:

```js
const unique = [...new Set(arr)];
```

`new Set(arr)` перебирает `arr` (снова через протокол итерации из раздела 1!) и добавляет каждое значение, автоматически отбрасывая повторы: `Set` не позволяет двум одинаковым значениям существовать в нём одновременно. Затем `[...set]` превращает результат обратно в массив, и это снова работает благодаря тому, что `Set` итерируем.

Третий типичный сценарий: кеш по ключу.

```js
const cache = new Map();

function expensiveCalc(n) {
  if (cache.has(n)) {
    return cache.get(n);
  }
  const result = n ** 2; // условно тяжёлые вычисления
  cache.set(n, result);
  return result;
}
```

`has` проверяет, есть ли запись с таким ключом, `get` и `set` читают и пишут значение. Ничего экзотического, но именно то, чего объекту как словарю не хватает, когда ключом может оказаться не строка, а, например, ссылка на DOM-узел или объект конфигурации запроса.

Выбор между инструментами определяется задачей, а не модой:

- нужен словарь со строковыми ключами, известными заранее, и важно, чтобы он легко превращался в JSON: подойдёт обычный объект;
- ключи не строки, их набор заранее не известен или важна гарантия порядка и точный размер: подойдёт `Map`;
- нужна коллекция уникальных значений: подойдёт `Set`;
- важен порядок и доступ по числовому индексу: подойдёт массив.

Стоит знать и о недавнем дополнении: с 2024 года `Set` умеет напрямую выполнять операции над множествами: `union`, `intersection`, `difference`, `symmetricDifference`, `isSubsetOf`, `isSupersetOf`, `isDisjointFrom`. Эти методы стабильно поддерживаются во всех современных браузерах и рантаймах, так что вместо ручного `[...a].filter(x => b.has(x))` для пересечения двух множеств можно написать `a.intersection(b)` напрямую.

**Вывод.** Объект и массив представляют собой универсальные структуры, но у этой универсальности есть цена: ключи объекта всегда приводятся к строке, а поиск уникальности в массиве требует ручного перебора. `Map` и `Set` устраняют именно эти ограничения: `Map` становится настоящим словарём для ключей любого типа, а `Set` — настоящей коллекцией уникальных значений. Когда данные по своей природе являются словарём или множеством, а не просто набором свойств, специализированная структура убирает целый класс возможных ошибок.

**Практика.** У тебя есть список заказов вида `{ id, customerId }`. Нужно: посчитать, сколько заказов у каждого клиента (ключ: `customerId`), и отдельно получить список уникальных `customerId`. Реши обе задачи, выбрав между объектом, `Map` и `Set`, и обоснуй выбор для каждой части.

## 4. WeakMap и WeakSet: когда обычная ссылка становится утечкой

В прошлом разделе мы построили кеш на `Map`, где ключом было число. А что, если ключом должен быть объект, который живёт не вечно (например, DOM-элемент или экземпляр компонента, создаваемый и удаляемый десятки раз за сессию)? Если использовать для такого кеша обычный `Map` и не вычищать записи вручную, возникает проблема, знакомая по шестой неделе: объект-ключ никогда не будет собран сборщиком мусора, даже если он давно удалён из DOM и больше нигде не используется. Дело в том, что `Map` продолжает держать на него ссылку.

Механизм сборки мусора в двух словах: движок периодически освобождает память объектов, до которых нельзя добраться ни по одной цепочке ссылок из корня программы. Если объект всё ещё лежит ключом в `Map`, он остаётся достижимым, а значит, память не освобождается, сколько бы раз объект логически ни считался удалённым из приложения. При активном использовании такого кеша это классическая утечка памяти: со временем в памяти накапливаются объекты, которые формально уже никому не нужны.

```js
const metadataCache = new Map();

function attachMetadata(el, data) {
  metadataCache.set(el, data);
}

// узел удалён из DOM, ссылок на него больше нигде нет,
// но metadataCache всё ещё держит его как ключ,
// и сборщик мусора не может его забрать
```

`WeakMap` и `WeakSet` решают это, храня ссылки на объекты-ключи *слабо*: такая ссылка не мешает сборщику мусора освободить объект, если на него больше нет ни одной обычной ссылки. Как только это происходит, соответствующая запись в `WeakMap` исчезает вместе с объектом сама по себе, без явного `delete`, хотя момент этого исчезновения не находится под твоим контролем и не определён точно.

```js
const metadataCache = new WeakMap();

function attachMetadata(el, data) {
  metadataCache.set(el, data);
}

function getMetadata(el) {
  return metadataCache.get(el);
}
```

API выглядит так же, как у `Map` (`set`, `get`, `has`, `delete`), но поведение с памятью принципиально другое: если `el` больше нигде не хранится, и он, и его запись в кеше становятся доступны для сборки мусора автоматически, без ручной очистки.

Ровно поэтому у `WeakMap` и `WeakSet` есть ограничения, которые на первый взгляд выглядят как недостаток, а на деле являются прямым следствием их природы. Ключами могут быть только объекты: примитивные значения нельзя удерживать слабой ссылкой, потому что они не отслеживаются сборщиком мусора индивидуально, у них просто нет отдельной судьбы, которую можно было бы освободить. И `WeakMap`/`WeakSet` не перебираются: нет `keys()`, `values()`, `size`, `for...of` по ним не работает. Это тоже не случайность: содержимое может измениться в любой момент, когда сборщик мусора решит забрать очередной ключ, а стабильный список того, что лежит внутри в конкретный момент времени, в таких условиях не имел бы смысла.

Второй частый сценарий: приватное состояние, привязанное к конкретному экземпляру объекта.

```js
const privateData = new WeakMap();

class Counter {
  constructor() {
    privateData.set(this, { count: 0 });
  }
  increment() {
    const data = privateData.get(this);
    data.count += 1;
    return data.count;
  }
}
```

**Разбор.** `privateData` объявлен в замыкании модуля и снаружи не виден: обратиться к состоянию можно только через методы `Counter`, которые знают об этой переменной. Каждый экземпляр `Counter` использует `this` как ключ в `privateData`, поэтому у разных экземпляров данные не пересекаются. Когда экземпляр `Counter` больше никому не нужен и на него не осталось ссылок, он и его запись в `privateData` собираются вместе, без утечки. Это был распространённый способ получить настоящую приватность до появления приватных полей класса (`#count`, пятая неделя); сегодня для классов чаще проще написать `#count` напрямую, а `WeakMap` остаётся полезным там, где нужно прикрепить данные к объекту, которым ты не управляешь напрямую (например, к чужому экземпляру или к DOM-узлу).

**Вывод.** Задача та же, что у `Map` в прошлом разделе: связать объект с дополнительными данными. Разница в управлении временем жизни: `Map` держит ключи сильно и никогда сама их не отпустит, `WeakMap` держит их слабо и отпускает автоматически вместе с самим объектом. Это оплачивается итерируемостью и `size`, но для кешей и приватного состояния они и не нужны.

**Практика.** Перепиши кеш `expensiveCalc` из раздела 3 так, чтобы он принимал в качестве ключа не число, а произвольный объект-конфигурацию и не препятствовал сборке мусора, если этот объект больше не используется. Объясни, почему `Map` в этой версии задачи привёл бы к утечке, а `WeakMap` — нет.

## 5. Symbol: ключ, который гарантированно ни с чем не столкнётся

В разделе 1 мы уже использовали `Symbol.iterator`, не объясняя, что такое `Symbol` сам по себе. Пора закрыть этот пробел.

Представим, что пишется небольшая библиотека, которая помечает уже обработанные объекты, чтобы не обрабатывать их повторно:

```js
function markProcessed(item) {
  item.__processed = true;
}
```

Проблема в том, что `__processed` — обычная строка, и ничто не мешает этому имени столкнуться с настоящим свойством объекта, которое по каким-то причинам называется так же, или с таким же служебным ключом другой библиотеки. Такое столкновение не бросит ошибку: оно тихо перезапишет чужие данные или собственную метку, и обнаружить это будет сложно именно потому, что ничего явно не сломалось.

`Symbol()` создаёт новое значение, которое гарантированно не равно никакому другому символу, даже созданному с тем же самым описанием:

```js
const s1 = Symbol('id');
const s2 = Symbol('id');
s1 === s2; // false
```

Строка `'id'` здесь не идентификатор, а просто пояснение для отладки, видимое в `console.log` или в `.toString()`. Оно не участвует в сравнении. Уникальность гарантирует само значение символа, а не его описание.

Это делает `Symbol` подходящим ключом для служебных пометок:

```js
const processedFlag = Symbol('processed');

function markProcessed(item) {
  item[processedFlag] = true;
}
```

Прочитать или перезаписать `item[processedFlag]` можно, только имея ссылку именно на это значение `processedFlag`, — строкой `'processed'` до него не добраться, потому что `'processed' !== processedFlag`. Есть и практическое следствие: символьные ключи не попадают в обычные способы перечисления свойств: `for...in`, `Object.keys()`, `JSON.stringify()` их не видят. Увидеть их можно только явно, через `Object.getOwnPropertySymbols()`. Это ровно то, что нужно от служебной метки: она не должна мешать обычному перебору данных объекта.

Теперь мы можем точнее сказать, что происходит в разделе 1. `Symbol.iterator` — это не просто зарезервированное имя метода в привычном смысле, а конкретное значение типа `symbol`, встроенное в сам язык, к которому обращается механизм `for...of`, spread и деструктуризации. Когда мы писали `[Symbol.iterator]() { ... }` внутри `rangeObj`, мы использовали это встроенное значение как вычисляемый ключ свойства, точно таким же способом, каким выше использовали собственный `processedFlag`, только символ в этом случае предоставлен не нами, а движком.

Такие предопределённые символы называются **well-known symbols**: это точки, через которые движок разрешает настраивать поведение объекта в конкретных ситуациях. `Symbol.iterator` настраивает поведение при итерации. Есть и другие: `Symbol.toPrimitive` позволяет объекту самому решить, во что он превращается при неявном приведении к примитиву (например, при `+obj` или в шаблонной строке), а `Symbol.hasInstance` переопределяет поведение `instanceof` для класса. Общий принцип один и тот же: язык резервирует конкретное символьное значение как точку расширения, а объект, реализуя метод с этим ключом, подключается к соответствующему встроенному механизму.

**Вывод.** `Symbol` решает проблему коллизии ключей за счёт гарантии уникальности: значение символа не совпадает ни с одним другим значением, даже похожим внешне. Well-known symbols используют этот же принцип для того, чтобы дать самому языку набор безопасных, не пересекающихся с обычными именами точек настройки поведения объектов. И `Symbol.iterator` из раздела 1 оказывается ровно таким случаем, а не отдельным исключением.

**Практика**

Разработчик пишет небольшую систему логирования. Каждый созданный объект должен получить уникальный служебный идентификатор, но этот идентификатор не должен становиться частью обычных данных объекта.

Создай функцию `attachId(object)`, которая:

* использует `Symbol` для создания ключа;
* сохраняет в объекте уникальный идентификатор;
* возвращает созданный символьный ключ;
* позволяет получить идентификатор объекта через этот ключ.

Проверь работу функции на нескольких объектах: у каждого должен быть свой идентификатор. Затем попробуй получить эти идентификаторы через обычный перебор свойств и через `Object.getOwnPropertyNames()`. Обрати внимание, что вернёт этот метод.

## 6. Proxy и Reflect: перехват операций над объектом

На пятой неделе мы разбирали геттеры и сеттеры: свойство можно определить так, что при чтении или записи вызывается функция вместо простого хранения значения. Это работает, но требует объявить `get`/`set` для каждого конкретного свойства заранее, по имени. А что, если нужно реагировать на чтение или запись *любого* свойства объекта, включая те, что появятся в будущем, причём одним и тем же кодом и без изменения самого объекта?

С такой задачей постоянно сталкиваются интерфейсные фреймворки, которым нужно заметить изменение данных и обновить интерфейс. Разработчик пишет `state.count++`, и где-то дальше по цепочке часть интерфейса, зависящая от `count`, обновляется без явного вызова какой-то функции, которая обновляла бы всё сразу. Как фреймворк вообще узнаёт, что что-то изменилось?

`Proxy` оборачивает объект и позволяет описать **ловушки** (traps): функции, которые перехватывают фундаментальные операции над объектом: чтение свойства, запись, проверку `in`, удаление и другие. Когда код обращается не к исходному объекту, а к прокси, вместо операции по умолчанию выполняется соответствующая ловушка, и именно она решает, что происходит на самом деле.

```js
const target = { name: 'Alice' };

const handler = {
  get(target, key) {
    console.log(`Читаем свойство ${key}`);
    return target[key];
  }
};

const proxy = new Proxy(target, handler);

console.log(proxy.name);
// Читаем свойство name
// Alice
```

Что произойдёт, если убрать `return target[key]` и оставить в ловушке только `console.log`?

```js
const handler = {
  get(target, key) {
    console.log(`Читаем свойство ${key}`);
    // забыли вернуть значение
  }
};

const proxy = new Proxy(target, handler);
console.log(proxy.name); // undefined
```

Здесь легко ошибиться, ожидая, что чтение всё равно доберётся до настоящего значения само по себе. Это не так: ловушка полностью подменяет операцию, а не дополняет её. Результатом `proxy.name` становится именно то, что вернула функция `get`: в данном случае ничего, то есть `undefined`, хотя в `target` значение `'Alice'` никуда не делось.

Это и есть точный ответ на четвёртый вопрос из начала темы: в момент чтения `proxy.name` вызывается `handler.get(target, 'name', proxy)`, и то, что вернёт эта функция, становится результатом чтения — не автоматически, а только если ловушка сама явно прочитала и вернула значение.

На практике вместо ручного `target[key]` внутри ловушки используют `Reflect`: встроенный объект со статическими методами, которые зеркалят те же фундаментальные операции (`Reflect.get`, `Reflect.set`, `Reflect.has`, `Reflect.deleteProperty` и другие) и выполняют их корректно, так, как это происходило бы по умолчанию, в том числе в более тонких случаях с наследованием и вложенными прокси, которые вручную легко реализовать чуть неточно. У `get`-ловушки есть и третий параметр, `receiver`, который стоит просто передавать дальше в `Reflect.get`, не вникая в детали: это страховка на случай, если прокси участвует в цепочке прототипов или обёрнут в другой прокси.

```js
const handler = {
  get(target, key, receiver) {
    console.log(`Читаем свойство ${key}`);
    return Reflect.get(target, key, receiver);
  }
};
```

Разберём три реальных сценария, где это применяется.

**Логирование доступа.** Пример выше уже им является: ловушка `get` фиксирует каждое чтение свойства, не трогая исходный объект и не требуя добавлять `console.log` в каждое место, где к объекту обращаются.

**Валидация при записи**

```js
function createValidatedUser(initial) {
  return new Proxy(initial, {
    set(target, key, value) {
      if (key === 'age' && (typeof value !== 'number' || value < 0)) {
        throw new TypeError('age должен быть неотрицательным числом');
      }
      return Reflect.set(target, key, value);
    }
  });
}

const user = createValidatedUser({ name: 'Bob', age: 30 });
user.age = 31; // проходит
user.age = -5; // TypeError
```

Каждая запись `user.someProp = value` — это фундаментальная операция `[[Set]]`, которую перехватывает ловушка `set`. Проверка выполняется до того, как значение реально попадёт в объект: если условие нарушено, мы бросаем исключение и `Reflect.set` вообще не вызывается, то есть запись не происходит. Стоит знать: ловушка `set` обязана вернуть булево значение, сообщающее об успехе операции; `Reflect.set` делает это за нас корректно; если из `set`-ловушки в строгом режиме (а модули и классы всегда в строгом режиме) вернуть `false`, движок сам бросит `TypeError`.

**Реактивность.** Это ключевой случай, ради которого стоило разобраться с предыдущими двумя.

```js
function reactive(target, onChange) {
  return new Proxy(target, {
    set(obj, key, value) {
      const oldValue = obj[key];
      const result = Reflect.set(obj, key, value);
      if (oldValue !== value) {
        onChange(key, value, oldValue);
      }
      return result;
    }
  });
}

const state = reactive({ count: 0 }, (key, value) => {
  console.log(`${key} изменился на ${value}, нужно обновить интерфейс`);
});

state.count++;
// count изменился на 1, нужно обновить интерфейс
```

**Разбор.** `state.count++` — это сокращение для `state.count = state.count + 1`. Сначала происходит чтение `state.count` (ловушка `get` здесь не задана, поэтому чтение проходит по умолчанию, без изменений — ловушка нужна только для операций, которые ты явно перехватываешь), возвращается 0, вычисляется 1, и затем выполняется запись `state.count = 1`. Вот она уже перехватывается нашей ловушкой `set`. Внутри мы запоминаем старое значение до записи, выполняем настоящую запись через `Reflect.set` (чтобы данные в `target` реально обновились), сравниваем старое и новое значение и, если они отличаются, вызываем `onChange`. Именно `onChange` становится тем самым местом, где реальный фреймворк запустил бы перерисовку конкретной части интерфейса, зависящей от `count`.

Если заменить `console.log` на запись в DOM, перерисовка появится на самом деле. Возьмём счётчик товаров в шапке магазина:

```js
const badgeEl = document.querySelector('#cart-count');

const cart = reactive({ count: 0 }, (key, value) => {
  if (key === 'count') badgeEl.textContent = value;
});

cart.count++; // на странице сразу появится 1
```

Код, который кладёт товар в корзину, меняет только `cart.count` и ничего не знает о DOM. Элемент при этом обновляется сам, без ручного вызова функции рендера. Это уже минимальная реактивность.

Стоит сразу обозначить границы этого примера: настоящие фреймворки дополнительно отслеживают, какая именно часть интерфейса читает какое именно свойство (это называется отслеживанием зависимостей и обычно делается во время самого рендера), чтобы обновлять только то, что действительно зависит от изменившегося значения, а не всё разом. Здесь этого нет: есть один общий колбэк `onChange` на любое изменение. И ещё: если внутри `state` окажется вложенный объект, наш простой `reactive` не перехватит изменения его свойств, для этого пришлось бы рекурсивно оборачивать в `Proxy` и вложенные объекты тоже. Но сам принцип, который делает возможным автоматическое обнаружение изменений, а именно перехват `set`, уже здесь, и это его минимальная, но честная реализация.

Кроме `get` и `set`, у `Proxy` есть и другие ловушки. `has` перехватывает оператор `in`, а `deleteProperty` перехватывает оператор `delete`. Есть и более редкие: `ownKeys`, `defineProperty`, `getPrototypeOf`, каждая под свою фундаментальную операцию. На практике подавляющее большинство задач решается через `get` и `set`: они покрывают чтение и запись, а это как раз то, на чём строятся и логирование, и валидация, и реактивность.

**Вывод.** Логирование, валидация и реактивность решают одну и ту же задачу: перехватить операцию над объектом, не меняя сам объект и не зная заранее весь набор его свойств. `Proxy` обобщает то, что геттеры и сеттеры делают для одного конкретного, заранее названного свойства, на любую операцию с любым свойством, известным или ещё не существующим. `Reflect` даёт корректную реализацию операции по умолчанию, чтобы ловушка могла добавить своё поведение, не сломав исходный контракт.

**Практика**

Есть объект, который хранит настройки приложения. Нужно защитить его от случайного удаления важных свойств.

Реализуй функцию `protect(target)`, которая возвращает `Proxy` и:

* запрещает удалять свойства, отмеченные как защищённые;
* позволяет удалять остальные свойства;
* при попытке удалить защищённое свойство выводит сообщение в консоль;
* корректно работает с объектами, у которых свойства могут находиться в прототипе.

 > `target` — изначальный объект для защиты

Для реализации используй `Proxy` и `Reflect`. Обрати внимание, что проверять наличие свойства только через `target.hasOwnProperty()` недостаточно: подумай, какой способ проверки учитывает всю цепочку прототипов.

## 7. ES-модули: связи между файлами вместо общего пространства имён

До сих пор код в примерах жил в одном файле или, в лучшем случае, в нескольких файлах, подключённых через `<script>`, где всё, что объявлено на верхнем уровне, оказывается в одном общем пространстве имён, а порядок подключения файлов приходится помнить и поддерживать вручную. С ростом приложения это превращается в две конкретные проблемы: имена начинают сталкиваться друг с другом, а зависимости между файлами становятся неявными — код в одном файле полагается на то, что другой файл уже загрузился раньше, но нигде это явно не написано.

ES-модули делают связи между файлами явными. `export` отмечает то, что файл готов отдать наружу, `import` в другом файле явно забирает нужное.

```js
// mathUtils.js
export function add(a, b) {
  return a + b;
}
export function multiply(a, b) {
  return a * b;
}
export const PI = 3.14159;
```

```js
// main.js
import { add, multiply, PI } from './mathUtils.js';
console.log(add(2, 3));
```

Это именованный экспорт: у модуля может быть сколько угодно именованных экспортов, и импортирующий код обязан обращаться к ним по тем же именам (или переименовывать явно через `as`). Есть и другой вид: экспорт по умолчанию, максимум один на модуль.

```js
// user.js
export default class User {
  constructor(name) {
    this.name = name;
  }
}
```

```js
// main.js
import User from './user.js';
```

Раз экспорт по умолчанию один и однозначный, при импорте ему можно дать любое локальное имя: путаницы не возникнет.

Важная деталь: набор `export`/`import` в модуле определяется статически — то есть виден уже при чтении исходного текста, а не вычисляется во время выполнения произвольным кодом. Именно поэтому инструменты сборки способны заранее построить точный граф зависимостей между файлами и, например, обнаружить и выбросить экспортированный, но нигде фактически не используемый код. Сама возможность такого анализа существует только благодаря этой статичности.

Модули связаны и с тем, что мы разбирали на шестой неделе: `<script type="module" src="main.js"></script>` по умолчанию ведёт себя как `defer` (не блокирует разбор страницы и выполняется после её загрузки) и всегда работает в строгом режиме. Ещё один нюанс: сколько бы раз один и тот же модуль ни импортировали из разных файлов, его тело выполняется только один раз: при повторных импортах используется уже готовый результат.

Статический импорт хорош, когда всё нужно сразу. Но что, если часть функциональности используется редко (тяжёлая библиотека графиков, код модального окна, админ-панель) и грузить это для каждого посетителя не хочется?

Здесь пригодится то, что мы уже знаем о промисах с седьмой недели. `import()` — не оператор верхнего уровня, а выражение, которое можно вызвать в любом месте кода, и оно возвращает промис, разрешающийся объектом пространства имён загруженного модуля:

```js
button.addEventListener('click', async () => {
  const { default: Chart } = await import('./chart.js');
  const chart = new Chart(canvasEl);
  chart.render(data);
});
```

**Разбор.** Пока пользователь не нажмёт кнопку, ничего, связанное с `chart.js`, не загружается, не парсится и не выполняется. В момент клика вызывается `import('./chart.js')`: начинается загрузка модуля (по сети, если он ещё не закеширован), и выполнение асинхронной функции приостанавливается на `await` до завершения загрузки. Как только модуль загружен, результатом становится его объект экспортов, из которого мы достаём `default`, класс `Chart`, который в `chart.js`, скорее всего, объявлен как `export default class Chart {...}`. Только после этого класс используется. Это и есть ленивая загрузка на уровне языка: инструмент сборки видит вызов `import()` и может автоматически вынести `chart.js` (и всё, от чего он зависит) в отдельный файл, который загрузится только тогда, когда действительно понадобится.

**Вывод.** Статические `export`/`import` строят явный, анализируемый граф зависимостей между файлами вместо неявного порядка `<script>`-тегов и общего глобального пространства имён. Динамический `import()` расширяет эту модель на загрузку, решение о которой принимается уже во время выполнения, и делает это через промис-based-механизм асинхронности, который мы уже знаем по работе с сетью.

**Практика.** Раздели код небольшого модуля (например, работу с корзиной покупок) на 2–3 файла: один с именованными экспортами утилитарных функций, другой с экспортом по умолчанию основного класса. Затем добавь кнопку, по клику на которую через динамический `import()` подгружается ещё один модуль (например, код экспорта в PDF), который не загружается, пока кнопку не нажали.

## Если кратко

Пять недель назад мы начали с вопроса, как JavaScript себя ведёт: что происходит при сложении числа со строкой, как работает всплытие ошибок, что значит асинхронный код. С тех пор мы дошли до перехвата фундаментальных операций над объектом через `Proxy`.

> JavaScript — динамический, прототипный, событийный язык с однопоточной моделью выполнения, изначально созданный для браузера.

Каждая часть этого определения не абстрактная характеристика, а прямая ссылка на то, что мы уже разобрали. **Динамический**: типы определяются во время выполнения, а не заранее. **Прототипный**: объектная модель строится на цепочке прототипов, а не на классах в классическом смысле. **Событийный и однопоточный**: интерфейс реагирует на события, а асинхронный код выполняется через очередь задач на одном-единственном потоке, который также отвечает за рендеринг страницы, поэтому тяжёлая синхронная работа блокирует и то, и другое. **Созданный для браузера**: DOM, `window`, `document`, загрузка скриптов существуют потому, что язык изначально создавался для одной конкретной среды.

Из этой природы прямо следует, что язык хорошо решает и с чем справляется плохо.

Хорошо получается:

- интерактивный интерфейс и реакция на действия пользователя;
- работа с сетью без блокировки интерфейса за счёт событийной модели и промисов;
- работа почти везде, где есть браузер;
- быстрое написание кода без обязательной подготовительной компиляции;
- гибкость вплоть до перехвата фундаментальных операций над объектом, как мы только что видели на `Proxy`.

Плохо получается:

- числовая точность: числа хранятся по стандарту IEEE 754, из-за чего, например, `0.1 + 0.2` не равно ровно `0.3`;
- тяжёлые вычисления: один поток означает, что затратная синхронная операция замораживает и обработку событий, и отрисовку;
- безопасность в больших кодовых базах: динамическая типизация означает, что многие ошибки, которые статически типизированный язык поймал бы на этапе компиляции, в JS всплывают только во время выполнения, иногда у конечного пользователя.

Именно из этих ограничений вырос весь инструментарий, с которым предстоит работать дальше. TypeScript возвращает языку статическую проверку типов, которой ему не хватает по своей природе. Фреймворки берут на себя управление DOM и реактивностью, и, как мы теперь понимаем, делают это не магией, а вполне конкретными механизмами этой недели: `Proxy` для перехвата изменений данных, итераторы и генераторы для эффективного прохода по спискам при рендере. Сборщики (бандлеры) существуют, чтобы собрать модули, о которых шла речь в разделе 7, в оптимизированный код для продакшена. Web Workers дают возможность вынести тяжёлые вычисления в отдельный поток, не замораживая основной: это прямое следствие того, что сам JavaScript однопоточен.

**Итоговая практика.** Вот кусок кода, доставшийся в наследство от предыдущей команды:

```js
function processOrders(orders) {
  var uniqueIds = [];
  var counts = {};
  for (var i = 0; i < orders.length; i++) {
    var id = orders[i].id;
    if (uniqueIds.indexOf(id) === -1) {
      uniqueIds.push(id);
    }
    counts[id] = (counts[id] || 0) + 1;
  }
  return { uniqueIds: uniqueIds, counts: counts };
}
```

Отрефактори этот код, используя механизмы из сегодняшней темы. Для каждого изменения объясни, какую конкретно проблему оно решает, а не просто ссылайся на то, что так современнее. И отдельно ответь: есть ли здесь место, где новый инструмент ничего не улучшит, и лучше оставить как есть? Если `id` в этой задаче всегда строка или число, подумай, действительно ли `counts` обязан стать `Map`, или обычный объект и так делает свою работу корректно.

## ★ Глубже

Итераторы, `Proxy`, модули у тебя уже работают. Но в продвинутом JS есть куда копать дальше. Этот раздел необязательный: перед контрольной полезнее закрепить основное, а сюда стоит вернуться, когда будет время и интерес.

**Значит ли перехват через `Proxy`, что именно так работает реактивность Vue? А React работает так же?** В Vue это действительно так: его реактивность в третьей версии построена ровно на этом: объект оборачивается в `Proxy`, и при записи фреймворк узнаёт об изменении и обновляет зависящую от него часть интерфейса. Vue 2, для сравнения, использовал `Object.defineProperty` с геттерами и сеттерами для каждого свойства заранее (тот самый ограниченный подход, от которого мы отталкивались в начале раздела 6), и переход на `Proxy` в третьей версии как раз и снял эти ограничения. React устроен принципиально иначе: он не следит за изменениями через перехват операций, а полагается на то, что ты сам сообщаешь об изменении (`setState` или аналог), после чего сравнивает новое дерево интерфейса со старым и обновляет только то, что действительно отличается. Поняв `Proxy`, ты понимаешь один из двух основных подходов к реактивности не как готовый рецепт, а на уровне базового механизма. Это всплывёт в первую же неделю работы с фреймворком. Хороший разбор дан в документации Vue, раздел [Reactivity in Depth](https://vuejs.org/guide/extras/reactivity-in-depth.html).

**`Proxy` перехватывает вообще всё? Есть слепые зоны?** Почти всё, но не всё. Приватные поля класса (`#field`, пятая неделя) `Proxy` не перехватывает: они привязаны к внутреннему слоту самого объекта, а не проходят через операции чтения/записи свойств, которые ловит `Proxy`. Если метод класса читает `this.#field`, а `this` внутри вызова оказывается прокси, а не исходным экземпляром, движок бросит ошибку, потому что у прокси нет нужного внутреннего слота, даже если у обёрнутого объекта он есть. Похожая история со встроенными типами вроде `Map` или `Date`: их методы завязаны на внутренние слоты, которых у `Proxy`-обёртки формально нет, поэтому просто обернуть `Map` в `Proxy` и продолжить вызывать `.get()`/`.set()` не получится: это ломается с ошибкой о несовместимом получателе. Отсюда практическое правило: `Proxy` мощный, но не абсолютный. Список точных инвариантов и ограничений есть на [MDN, страница Proxy](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Proxy).

**Слышал про `Symbol.asyncIterator` и `for await...of`. Это что?** Это асинхронная итерация, мост между этой неделей и седьмой. Обычный итератор из раздела 1 отдаёт значения сразу, синхронно. Асинхронный итератор — это объект с методом `[Symbol.asyncIterator]()`, чей `next()` возвращает не `{ value, done }` напрямую, а промис, который разрешается таким объектом. `for await...of` дожидается каждого такого промиса по очереди, прежде чем перейти к следующему значению. Это удобно, когда данные приходят частями и не сразу: постранично из сети или по кускам из потока. Пригодится, когда понадобится читать данные, приходящие не целиком за один раз. Подробнее можно почитать на MDN, на страницах про [асинхронные итераторы](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/for-await...of) и `Symbol.asyncIterator`.

**Генераторы — только для ленивых последовательностей или из них выжимают что-то ещё?** Выжимают. `yield` умеет не только отдавать значение наружу, но и принимать значение обратно: выражение `const x = yield produced` получает то, что передали в следующий вызов `next(значение)`. Это делает генератор двусторонним каналом связи с внешним кодом. На этом когда-то строили управление асинхронностью до появления `async`/`await`: библиотеки вроде `co` автоматически продвигали генератор вперёд шаг за шагом, трактуя каждое `yield`-нутое значение как промис, который нужно дождаться, а потом передать результат обратно через `next()`. `async`/`await`, по сути, формализует ровно этот же паттерн уже на уровне синтаксиса языка. В повседневной работе это редко нужно напрямую, но объясняет, откуда вырос современный `async`/`await`.

**Модули есть в браузере нативно. Тогда зачем вообще нужны бандлеры?** Ответ здесь со временем менялся. Раньше бандлеры были обязательны: браузеры не умели модули вовсе, а множество мелких файлов грузились медленно из-за накладных расходов на каждый запрос. Сейчас браузеры умеют ES-модули нативно, и инструменты вроде Vite используют это прямо в разработке, без пересборки на каждое изменение. Но для продакшена бандлеры всё ещё нужны: минификация, объединение файлов там, где это по-прежнему выгодно, устранение неиспользуемого кода (то самое, что стало возможным благодаря статичности `import`/`export` из раздела 7), управление разбиением на части при динамическом импорте, обработка не-JS-ресурсов вроде CSS и изображений. Это всплывёт, как только дойдёшь до сборки настоящего проекта.

- [Iterators and generators — MDN Guide](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Iterators_and_generators) — более развёрнутое руководство с примерами `function*` и `yield*`.
- [Map — MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Map) и [Set — MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Set) — полный список методов, включая недавние `union`, `intersection`, `difference` и другие операции над множествами.
- [WeakMap — MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakMap) и [WeakSet — MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakSet) — детали про слабые ссылки и ограничения API.
- [Symbol — MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Symbol) — полный список well-known symbols, не только `Symbol.iterator`.
- [Proxy — MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Proxy) — список всех доступных ловушек и их точная сигнатура, включая инварианты, о которых шла речь в разделе ★.
- [Reflect — MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Reflect) — справочник по статическим методам, зеркалящим ловушки `Proxy`.
- [import — MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import) — статический импорт, синтаксис именованного и дефолтного импорта, включая варианты с переименованием.
- [Reactivity in Depth — Vue.js](https://vuejs.org/guide/extras/reactivity-in-depth.html) — официальное объяснение того, как Vue использует `Proxy` для реактивности, от команды, которая это реализовала.
